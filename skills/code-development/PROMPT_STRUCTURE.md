## 2026-09-21 开发前证据选择与跨 Skill 回传

在每个新的开发工作时段、当天首次继续持续项目或上下文切换后恢复实现时，首次修改生产代码前检查当前用户结果、完整运行路径、状态和决定的责任归属，并指出仍会改变实现方向的未知。状态分散时路由到 `workflow-state-distiller`，现象不足以判断原因、目标或参照时路由到 `xy-axis-thinking`；产品未知、外部未知和本地事实分别交给产品过程、研究或本地调查与最小实验。只有目标行为、主要路径和验收依据足以决定修改时才进入生产实现。

产品结果、责任归属、状态来源或执行主路径变化时重新选择证据，特别是新增持久状态、后台进程、调度器、模型职责、重试、兜底、兼容或第二条路径之前。证据必须更新受影响的规格、架构判断和验收，再由代码过程消费。详细方法放在 `references/acceptance-design.md`；行为案例覆盖状态恢复、产品信息、外部研究、本地实验、结构责任变化和普通局部缺陷，避免把生产编码当作默认调查方式，也避免把所有修改扩大成完整产品流程。

## 2026-09-15 条件式规格机制

整体任务规格保持可修正，进入实现或委派后的阶段合同在负责人更新前保持稳定。相互依赖且会改变路线的用户决定可以集中询问，其他未知继续渐进解决。项目预计长期维护，并且跨多个任务或多名参与者、建立入口确能减少信息散失时，可以建立由项目入口索引的简洁规格目录；短期和普通任务不新增目录。

高风险的数据、权限、不可回滚状态、核心架构和正式发布等变更，按需要展开规格、设计、阶段合同、分层验证、经授权的独立评审和真实入口验收。低风险任务仍沿最短闭环，不恢复 Spec Kit CLI、固定模板或所有任务完整生命周期。五个新增行为案例验证这些触发边界及短期协作反例。

## 骨架正文

把用户要求落实为可以实际使用、并有相应证据的代码结果。由同一实现责任人连续掌握使用路径的调查、判断、修改、运行和修正，按反馈推进。

从用户要获得的结果、修改边界和可观察验收路径开始。沿真实入口、调用关系、状态和依赖取得足以解释当前行为的证据。核实当前实现与使用版本，目标行为和接入方式清楚后进入实现。只有会改变重要接口、架构或用户结果的未知需要先行设计或实验。

开始修改前确认必须保留的行为、相关测试和已有未提交改动，保护用户已有工作。从与目标有关的入口逐步追踪调用与数据关系，先形成足以解释行为的系统理解，再深入决定实现的局部，不以通读仓库代替有方向的调查。

成品形态、核心价值或完成标准尚有实质分歧时，说明选择及影响，由用户决定。普通实现选择在已有授权内持续完成。需求变化后先修正会误导后续工作的权威说明。

先取得能够验证关键判断的最小完整结果，使代表性输入经过真实入口、核心处理、必要状态与依赖产生输出。每次变更包含同一行为所需的实现、验证和说明，增加接口时接通真实调用者，及时运行并修正。

核心结果失败时，先区分局部缺陷与路线问题。当前方法持续增加补偿却不能推进目标时，重新判断是否继续、缩小或换路。改变已约定的形态、要求或明显投入时，将依据和影响交给用户。

实现复杂度服从当前已证实需求。优先复用项目和平台的可靠能力，依据权威要求完成必要修改，保留合同要求的安全、数据保护、兼容和可访问性。未经需求或证据支持，不扩大实现和维护范围。

一次性操作直接实现，几行相似代码不必提前抽象。内部和框架已经提供可靠保证时直接使用，校验放在真实系统边界。局部修复保持局部，确认失效的代码删除，不留下没有实际用途的兼容痕迹。

用能够证明目标行为、也能捕获目标错误的证据判断完成。核验当前交付候选，按修改后果选择测试、集成或真实用户流程。测试依据来自要求和实际接口。声明真实宿主、模型或完整用户流程可用时，取得对应路径证据。

首次正常流程可运行时完成一次代表性实际操作，发现入口和集成问题后及时修正。测试失败先查清原因，不能扩大修改范围来掩盖失败。多部分修改整合后取得必要的跨模块证据，交付前确认这些证据对应当前候选。

按风险进行实现者复核和评审，处理实际发现与决定性证据缺口。自查与独立评审分别表述。全部完成标准已有证据支持，且剩余未知不会改变结论时结束验证。

交付约定入口下可使用的产物，说明结果、关键变化、验证和限制。未来维护依赖无法从代码与测试恢复的信息时，更新已有权威资料。保持当前成品、使用说明和维护依据一致。
