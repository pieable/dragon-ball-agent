# 用状态模型检查行为并解释结果

当正确性取决于操作顺序、并发、重试、取消或恢复，而且正常路径测试难以覆盖组合时，考虑 TLA+ / TLC 与 pstack `/statechart`。需要让业务负责人看清状态如何变化、错误怎样发生时，也可以用它把检查结果交回设计讨论。简单流程直接用转换表、Mermaid 或现有测试；单纯画图不必引入形式化工具。

## 先确定模型代表什么

从当前规格、真实入口和实现中选一个能独立判断的流程。列明对象、状态归属、事件、前置条件、写入与外部副作用，以及需要检查的规则；每项重要规则能追到需求或已确认决定。区分描述当前代码的模型与讨论候选设计的模型。待确认政策作为显式假设或分别建模，不用现有样例替业务方作决定。

把始终必须成立的规则写成不变量（INVARIANT），例如同一订单不得重复核销；涉及“最终完成”的性质另行表达 PROPERTY，并说明公平性及外部成功前提。模型中的原子步骤应对应真实事务或受保护的边界；真实代码存在读后写间隙时，不把整段操作合并成一个原子动作来消除竞争。

保留足以暴露目标错误的最小范围，记录参与者、数据范围、时间抽象、外部系统假设和省略项。约束状态空间是验证范围，不是产品运行限制。代码、规则或原子边界变化后，重新检查对应模型是否仍匹配。

## 复用工具并运行

参考基线为 [pstack v0.15.36，提交 0f77cd5](https://github.com/cursor/plugins/tree/0f77cd5/pstack/skills/statechart)。使用时读取该版本的 [SKILL.md](https://github.com/cursor/plugins/blob/0f77cd5/pstack/skills/statechart/SKILL.md)、脚本和[渲染说明](https://github.com/cursor/plugins/blob/0f77cd5/pstack/skills/statechart/references/render.md)。优先复用项目已安装的版本并记录差异；没有时只获取所需工具及许可证，固定实际提交，不默认安装整套插件或跟随 main。模型、源码、原始输出和复现入口保存在项目约定的实验目录，临时依赖按现有工具目录管理。

工具输入是 TLA+ 模型、TLC 配置和可选的视图映射，入口为：

```text
<statechart>/scripts/statechart SPEC.tla --config SPEC.cfg --view view.mjs --out NEW_OUTPUT_DIR
```

v0.15.36 使用可执行 TypeScript 的运行环境、Java 和 TLC；默认通过 mise 取得 Java/TLC，也可显式配置已有工具。上游启动与进程清理使用 `/bin/sh`，Windows 上先核对已有 WSL/Linux 环境。需要本机适配时，将改动与上游工具区分，验证正常、失败及相关清理路径；不要把适配运行称为上游原样运行。安装和外部操作沿当前授权，不自动更改系统环境。

该版本要求输出目录为空或全新。主要产物是 `chart.mmd`、`report.md`、`tlc.out` 及部分规则的单独日志。用真实 TLC 输出判断检查是否完成、哪些规则成立、哪些被违反或尚未检查；图文件存在、退出码为零或没有红色标记都不能单独作为完成依据。

工具的完整图预算为 500 个模型状态；更大时仅画反例路径，没有违反规则时可能无图。部分重跑有 100,000 状态预算，报告会标出未检查规则。按实际运行结果报告这些边界，需要扩大检查时调整模型或工具路线，不把预算当成业务限制。

## 将结果变成可判断的状态图

用读者看到或关心的内容命名状态和箭头，条件直接放在相关变化旁。视图可以是平面、层级或并行区域；选择能保持关键行为且便于比较的表示。合并状态或隐藏步骤时，保留反例经过的关键区别、触发条件和可达关系，说明省略了什么。

区分所有对应模型状态都违反规则的 `breaks` 与只有部分违反的 `mayBreak`。解释每个标记对应哪条规则，给出带编号的具体反例路径；时序性质的循环反例按实际报告解释，不把所有失败都笼统称作最短路径。图用于显示检查所得行为；用户据此判断规则和预期是否正确。

需要图片时按该版参考用 Pele 渲染 SVG，保留 Mermaid 来源。中文标签、箭头、条件、图例和关键路径应在实际尺寸下可读。用户阅读页可以组合图、规则对照和复现结果，并链接原始模型及日志；不要把完整机器日志堆进正文。

## 回到真实实现核验

模型描述当前代码时，将每条相关反例逐步重放到真实接口、测试或现场复现中。没有重现先检查模型、抽象边界与调用前提，不能仅凭模型宣布生产缺陷。对应真实代码的模型通过，也只支持已建模范围；实际平台、界面和外部交易仍按原验收要求验证。

首次接通或改变模型检查机制时，可用故意破坏一个关键保护的独立模型作负向对照，确认目标规则会失败、反例能读懂。对照清楚标成注入错误，不写成项目已存在的 bug。正常模型检查、负向对照与真实代码重放分别记录。

交付保留：规则来源、模型与实现的对应、假设和省略项、实际工具版本及适配、检查完成度、图与反例、代码复现结果和可重跑命令。将发现用于受影响的需求、设计或测试；修复范围超出当前授权时先交回决定。
