# 测试方法

本参考说明怎样为已确认的行为选择测试证据。它补充验收设计中的反例选择与分层验证；普通改动沿用已有测试门槛，不要求所有任务先写测试或新增文档。

## 先确定独立于实现的测试依据

先从已确认的用户结果、接口合同、不变量和故障案例写出输入、可观察结果及拒绝条件。测试预期来自这些依据，不从当前实现的输出反推“正确答案”。实现细节只在它本身属于公开合同或必要边界时才进入断言。

选择一个能够推翻完成声明的错误，并确认测试在该错误出现时会失败。若测试只是调用同一个实现、重复它的内部判断，或只验证调用次数而未验证结果，就补上独立的结果依据。预期尚未确定时，先用临时检查、手工观察或实验澄清行为，决定稳定后再纳入回归测试。

例如，重试接口规定同一请求不得重复扣款。测试根据接口合同检查一次扣款和稳定的最终余额；不能把当前实现“重试时先写缓存”的内部步骤当作正确性依据。

## 选择真实依赖、fake 或 stub

替身（fake 或 stub）用于隔离慢、昂贵、不稳定或难以控制的边界。它们能让测试快速重复，也可能漏掉真实协议、序列化、事务或部署配置问题。决定替身是否合适时，先问故障可能位于业务逻辑还是依赖连接，再检查测试要证明什么：

1. 若目标是业务规则，给替身明确且简单的行为，并验证调用后的可观察结果。
2. 若目标涉及数据库语义、消息格式、认证、驱动行为、并发或外部协议，用真实依赖或其受控实例验证该边界。
3. 若真实依赖昂贵或不可用，记录替身覆盖的合同，并保留一个更高层的连接检查来捕获替身与真实系统的差异。
4. 不因真实依赖启动困难就让替身假装证明了真实集成；也不因集成测试存在而重复模拟每个内部调用。

例如，余额计算单元测试可使用内存 fake 钱包；事务是否原子、唯一键是否防止重复扣款，则需要针对实际数据库的集成检查。

## 让同一契约检查真实实现与替身

当多个实现都声称遵守同一接口合同，建立一组只依赖公开接口的契约检查。用同一组检查分别运行生产适配器、内存 fake 或替代实现，确保它们对调用方表现一致。契约检查覆盖输入限制、结果含义、错误类型、幂等和状态变化等会影响调用方的行为。

不要为每个实现复制一份断言后任其漂移。共享检查可由实现工厂或测试套件参数化提供对象。真实实现的环境准备可以不同，但判断规则保持相同。若某个实现有意不支持某种能力，应由接口合同明确表达，而不是悄悄跳过对应检查。

例如，钱包合同检查对同一幂等键重复提交只产生一次扣款，并在余额不足时拒绝。该检查分别运行于生产数据库适配器和内存 fake，避免 fake 对重复请求比真实服务更宽松。

## 用状态序列检查状态行为

只测单次调用容易遗漏顺序相关错误。对有状态组件，描述可执行的操作序列，并在每步后检查不变量和可观察状态。序列应包含正常操作、重复操作、无效操作、恢复或重启等会改变后续行为的步骤。

当状态规则复杂但可用更简单的逻辑表达时，写一个小型参考模型（reference model），按相同操作更新模型与实际系统，再逐步比较结果。参考模型应独立、直接，避免复制生产算法。先用短而可复现的序列定位问题；随机生成操作只有在记录种子、缩减失败序列或能够重放时才有诊断价值。

例如，购物车模型只保存商品数量。对“加入、移除、清空、重复移除”的每步操作，比较实际购物车的数量，并检查数量非负、清空后为空。该模型不复刻生产系统的缓存实现。

## 按集成边界分层

分层的目的在于让故障证据指向发生错误的位置，而不是追求固定比例或测试数量：

- 单元检查快速验证纯计算、解析、转换和局部规则。
- 组件集成检查验证模块接线、参数传播、持久化和状态视图一致性。
- 边界检查经过实际数据库、HTTP、CLI、消息队列或平台接口，验证协议和拒绝行为。
- 端到端检查从日常入口完成代表性用户操作，确认组件组合后得到预期结果。

优先让多数确定性逻辑在局部快速反馈；保留覆盖关键连接和真实路径的检查。若错误能在较低层直接、快速、稳定地触发，就在那里检查；较高层补充低层无法证明的实际连接、协议和完整操作结果。不同层各自覆盖独有的失败方式，避免同一断言机械重复。

例如，创建订单的单元检查覆盖价格计算，数据库集成检查覆盖库存扣减与订单写入的一致性，端到端检查从结账入口验证用户最终看到确认编号。
