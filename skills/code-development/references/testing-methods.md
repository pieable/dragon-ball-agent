# 测试方法

本参考说明怎样为已确认的行为选择测试证据。它补充验收设计中的反例选择与分层验证；普通改动沿用已有测试门槛，不要求所有任务先写测试或新增文档。从需求写测试、测试环境和测试模型判断的具体做法见 [用测试引导实现](test-driven-work.md)。

## 先确定独立于实现的测试依据

先从已确认的用户结果、接口合同、不变量和故障案例写出输入、可观察结果及拒绝条件。测试预期来自这些依据，不从当前实现的输出反推“正确答案”。实现细节只在它本身属于公开合同或必要边界时才进入断言。

选择一个能够推翻完成声明的错误，并确认测试在该错误出现时会失败。若测试只是调用同一个实现、重复它的内部判断，或只验证调用次数而未验证结果，就补上独立的结果依据。预期尚未确定时，先用临时检查、手工观察或实验澄清行为，决定稳定后再纳入回归测试。

例如，重试接口规定同一请求不得重复扣款。测试根据接口合同检查一次扣款和稳定的最终余额；不能把当前实现“重试时先写缓存”的内部步骤当作正确性依据。

## 选择真实依赖、fake 或 stub

替身（fake 或 stub）用于隔离慢、昂贵、不稳定或难以控制的边界。它们能让测试快速重复，也可能漏掉真实协议、序列化、事务或部署配置问题。决定替身是否合适时，先问故障可能位于业务逻辑还是依赖连接，再检查测试要证明什么：

1. 若目标是业务规则，给替身明确且简单的行为，并验证调用后的可观察结果。
2. 若目标涉及数据库语义、消息格式、认证、驱动行为、并发或外部协议，用真实依赖或其受控实例验证该边界。
3. 若真实依赖昂贵或不可用，记录替身覆盖的合同，并保留一个更高层的连接检查来捕获替身与真实系统的差异。
4. 不因真实依赖启动困难就让替身假装证明了真实集成；也不因集成测试存在而重复模拟每个内部调用。

例如，余额计算单元测试可使用内存 fake 钱包；事务是否原子、唯一键是否防止重复扣款，则需要针对实际数据库的集成检查。

## 让同一契约检查真实实现与替身

当多个实现都声称遵守同一接口合同，建立一组只依赖公开接口的契约检查。用同一组检查分别运行生产适配器、内存 fake 或替代实现，确保它们对调用方表现一致。契约检查覆盖输入限制、结果含义、错误类型、幂等和状态变化等会影响调用方的行为。

不要为每个实现复制一份断言后任其漂移。共享检查可由实现工厂或测试套件参数化提供对象。真实实现的环境准备可以不同，但判断规则保持相同。若某个实现有意不支持某种能力，应由接口合同明确表达，而不是悄悄跳过对应检查。

例如，钱包合同检查对同一幂等键重复提交只产生一次扣款，并在余额不足时拒绝。该检查分别运行于生产数据库适配器和内存 fake，避免 fake 对重复请求比真实服务更宽松。

## 用状态序列检查状态行为

只测单次调用容易遗漏顺序相关错误。对有状态组件，描述可执行的操作序列，并在每步后检查不变量和可观察状态。序列应包含正常操作、重复操作、无效操作、恢复或重启等会改变后续行为的步骤。

当状态规则复杂但可用更简单的逻辑表达时，写一个小型参考模型（reference model），按相同操作更新模型与实际系统，再逐步比较结果。参考模型应独立、直接，避免复制生产算法。先用短而可复现的序列定位问题；随机生成操作只有在记录种子、缩减失败序列或能够重放时才有诊断价值。

例如，购物车模型只保存商品数量。对“加入、移除、清空、重复移除”的每步操作，比较实际购物车的数量，并检查数量非负、清空后为空。该模型不复刻生产系统的缓存实现。

## 按集成边界分层

分层的目的在于让故障证据指向发生错误的位置，而不是追求固定比例或测试数量：

- 单元检查快速验证纯计算、解析、转换和局部规则。
- 组件集成检查验证模块接线、参数传播、持久化和状态视图一致性。
- 边界检查经过实际数据库、HTTP、CLI、消息队列或平台接口，验证协议和拒绝行为。
- 端到端检查从日常入口完成代表性用户操作，确认组件组合后得到预期结果。

优先让多数确定性逻辑在局部快速反馈；保留覆盖关键连接和真实路径的检查。若错误能在较低层直接、快速、稳定地触发，就在那里检查；较高层补充低层无法证明的实际连接、协议和完整操作结果。不同层各自覆盖独有的失败方式，避免同一断言机械重复。

例如，创建订单的单元检查覆盖价格计算，数据库集成检查覆盖库存扣减与订单写入的一致性，端到端检查从结账入口验证用户最终看到确认编号。

## 现有测试可能漏掉的实际差异

| 涉及的机制 | 具体材料与查法 | 取得什么结果 |
|---|---|---|
| 新状态通过、旧状态失败 | 读取历史 schema、旧文件/消息、已安装版本与迁移路径，比较测试是否只从空库开始 | 将旧数据经正常升级入口交给新实现，再从重启和混合版本状态运行。验证时间/数值单位、身份、默认值、约束与实际读回结果 |
| 替身比真实边界宽松 | 比较 fake 与生产适配器的编码、错误码、分页、事务、唯一约束、取消及配置 | 用相同契约样本穿过真实边界或受控实例，确认真实消费者和替身的差异没有被“都返回成功”掩盖 |
| 错误被捕获成成功 | 检查空数组、部分结果、吞异常、skip/xfail、测试收集和异步任务等待 | 让目标依赖实际失败，观察退出码、成功标记、输出及副作用。断言应区分完整成功、合法空结果、部分完成与失败 |
| 时序依赖只靠 sleep | 找两个操作争用的读取/提交/取消窗口和失败事件，而非仅增加等待 | 用 barrier、可控时钟、阻塞 transport 或显式完成信号形成关键顺序，失败后能重放具体序列 |
| 测试顺序和共享状态 | 比较单跑/全套、串行/并行、顺序和种子，查全局变量、缓存、环境、工作目录、固定端口、临时文件/数据库及后台线程 | 定位哪项前置测试或并行参与者改变了状态，修复 fixture 与 teardown。等待线程/任务退出，核对框架测试原语的线程安全边界 [T1] |
| 浮点、时间和环境断言 | 读取精度与时间合同、locale/时区、CPU负载和平台差异 | 选择合同允许的容差或可控时钟，保持能拦住实际错误的判据。放宽断言、延长超时与重跑到绿分别需要原因 [T1] |
| 重试掩盖 flaky | 从原始 CI 每次尝试、失败栈、worker/shard、收集数和测试版本对照首次失败与重跑 | 复现依赖条件并修正根因；报告首轮与重试结果，不将一次重跑成功作为问题已修复的依据 |
| 测试成本主要在连接和准备 | 读取 job/step 与测试 duration，区分依赖安装、fixture、真实网络、setup/teardown、快照组合和测试主体 | 优化主导成本并核对有效测试/断言与关键连接覆盖。合法隔离用替身时保留真实边界检查，不用删掉有效测试换取速度 [T2] |

出现具体疑点时，可在隔离副本回退目标修复或注入目标错误，确认相关检查因预期原因失败。已有最小复现足以验证时直接使用。复杂的状态与资源验证按相关参考选择输入，普通局部任务继续沿已有有效检查完成。

- [T1 pytest flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html)：系统状态、隔离、断言与线程清理。
- [T2 Google 工程评审 Tests](https://google.github.io/eng-practices/review/reviewer/looking-for.html#tests)：测试有效性与维护复杂度。

## 用变异测试检查测试有效性

关键规则反复漏错、覆盖率较高却缺少有效断言，或重要重构需要检验现有保护时，主动评估 mutation testing（变异测试）：在隔离副本中小幅改变条件、运算或返回值，观察现有测试能否发现行为错误。先确认原始测试通过，再从相关规则和受影响代码开始，依据发现与成本决定是否扩大范围。

优先选择适合项目语言、测试框架与运行环境的现有工具，例如 JS/TS 的 [Stryker](https://stryker-mutator.io/docs/)、Python 的 [mutmut](https://mutmut.readthedocs.io/en/latest/)，也可考察 [ub-mode 配套 mutator](https://github.com/unclebob/mutator)。使用前核实当前兼容性、测试选择、隔离机制和结果分类；例如 mutmut 当前文档要求支持 fork，Windows 需 WSL。工具名是查找入口，不要求安装全部工具或自建变异框架。

逐项解释重要存活变异：是缺少场景、断言无效、测试未选中，还是改变后行为等价。依据业务合同补检查或纠正实现；死代码需确认无消费者及保留用途再删除。编译失败、环境错误或超时与行为断言发现错误分别报告，检查所用工具是否将它们混计；不能凭高分推断业务正确，也不为消灭等价变异添加无意义测试。该方法补充原有真实边界和用户路径验证。
