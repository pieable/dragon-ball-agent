# 用测试引导实现

测试将已明确的需求落实为可重复检查的行为，真实使用验证补足自动测试未覆盖的情境。这份参考说明怎样把需求写成测试、怎样搭测试环境、怎样防止实现者绕过测试，以及怎样测试由模型做判断的功能。测试依据、替身和分层的原理见 [测试方法](testing-methods.md)，验收合同见 [验收设计](acceptance-design.md)。

## 从需求写出测试用例

1. 把每条需求写成具体例子，每个例子有三部分：起始状态、用户或系统做了什么、应该看到什么结果。用表格列出，先不写代码：

   | 起始状态 | 操作 | 期望结果 |
   |---|---|---|
   | 今日重点有 A、B 两项，A 仍在进行 | 跨过凌晨 4 点，程序重新选择重点 | A 仍在今日重点里，B 按新的选择保留或移除 |
   | 用户在记录里写“X 不急” | 程序整理记录 | X 的紧急程度降低，其他任务不变 |

2. 每条需求至少写一个正常例子和一个会让错误实现失败的例子，例如边界值、重复操作、旧数据、并发或输入缺失。
3. 期望结果涉及用户的取舍或体验时，把表格给用户确认。用户确认的是表格里的例子，不需要读测试代码。
4. 期望结果写成具体的值或状态，例如“A 的状态是 waiting”，不写成“状态正确”。
5. 表格确认后，每一行变成一个测试。测试名直接说出这一行的行为，例如 `InProgressFocusSurvivesDayRollover`。

## 测试先行的顺序

适用于主 Skill 中已确定采用测试先行的行为。界面、探索性任务和真实外部系统按其实际验证方式处理。

1. 写测试并运行，确认它们失败，而且失败原因是功能还没有实现，不是编译错误、路径错误或测试本身写错了。
2. 把测试单独提交。提交说明写清这些测试规定了什么行为。
3. 写实现，直到这些测试通过。实现过程中不修改这批测试。
4. 实现中发现测试本身不对（需求理解错了、接口不可行），停止实现，说明哪个测试、为什么不对、建议怎样改，交给掌握需求的负责人或用户决定。改测试单独提交，提交说明写明原因。
5. 通过后，运行约定必跑的检查及受影响的回归测试。项目要求完整套件时运行完整套件，并补足整体使用路径的验证。

把实现交给子代理时，负责人提供已确认的行为期望、约束和验收依据，测试编写可以委派。实现者可以补充局部测试，修改既定期望时交回掌握需求的负责人。独立核验从用户情境和真实接口检查结果，补查实现者与测试作者可能共有的假设。

## 测试环境

测试环境搭好以后，每次修改只需要一个命令就能得到可信的结果：

- **用成熟框架。** .NET 用 xUnit、NUnit 或 MSTest，Python 用 pytest，JavaScript 用 Vitest 或 Jest。不手写测试运行器。
- **一个命令跑全部。** 例如 `dotnet test`、`pytest`。只跑部分测试用框架自带的筛选，例如 `dotnet test --filter "FullyQualifiedName~Focus"`。
- **按被测模块组织。** 测试项目的目录结构对应源码；测试文件按被测模块命名，例如 `DailyFocusTests.cs`。不按任务编号、阶段或修复事件命名。
- **反馈及时。** 按项目规模和检查用途安排测试耗时。慢的测试（真实模型、真实网络、界面自动化）单独分组，可以分开运行，约定必跑的检查继续执行。
- **构造测试数据有专门的工具。** 用 builder 或工厂方法创建测试对象，例如 `TaskBuilder.Active().WithFocus("A").Build()`，每个测试只写和自己有关的字段。
- **可控的时间和随机数。** 被测代码通过参数或接口拿到当前时间，测试传入固定时间；随机数固定种子。
- **独立的临时目录。** 每个测试自己创建，结束时删除，测试之间不共享文件或全局状态。
- **失败信息看得懂。** 断言失败时能看出期望值和实际值。比较复杂对象时，输出差异部分。

## 写有效的断言

- 断言具体结果：返回值、保存后的状态、用户可见的文字。只断言“不为空”“没有抛异常”“方法被调用了一次”通常拦不住错误。
- 通过公开接口测试。不要为了测试用反射调用私有方法；需要测试的内部逻辑提成可以直接调用的类或函数。
- 一个测试验证一个行为。一个测试里断言很多不相关的东西，失败时很难判断是哪里坏了。
- 测试代码里不重复实现被测算法。期望值写成明确的常量或手算的结果。

## 防止实现者绕过测试

实现者（包括模型自己）在压力下可能让测试通过，而功能并没有做对。交付前逐项检查：

| 信号 | 怎样检查 |
|---|---|
| 测试被删除、跳过、改弱，或期望值被改成当前输出 | 单独查看本次对测试文件的 diff，每处修改都要有已确认的原因 |
| 实现里出现针对测试输入的特殊判断 | 在实现 diff 里搜索测试用到的具体数值、字符串和文件名 |
| 测试只验证了替身 | 检查断言针对的是被测代码的输出，还是替身记录下的调用 |
| 异常被吞掉，测试因此通过 | 搜索新增的 `catch`，以及返回默认值的分支 |
| 测试根本不会失败 | 故意改坏一处实现（例如把条件取反），运行对应测试，确认它失败后恢复 |

重要功能可以保留几条实现者看不到的验收例子，由主 agent 持有，在实现完成后再运行。

## 测试由模型做判断的功能

程序调用模型做理解或判断时（例如由模型判断任务进度），分三层测试。

### 确定性部分：普通单元测试

提示词组装、输出格式校验、解析、把模型结果应用到状态，这些都是确定性代码。测试时用固定的模型输出 JSON 代替真实调用，覆盖以下情况：

- 正常输出；
- 字段缺失、类型错误或超出限制（例如行动超过 28 个字）；
- 引用了不存在的任务；
- 模型返回空结果。

每次提交都运行这一层。

### 录制回放

保存真实模型的输入和输出，作为固定的测试数据。程序逻辑修改后，用录制的输出离线回放，确认程序对同样的模型输出仍然处理正确，不需要每次都调用模型。

录制数据放在测试数据目录，文件名说明场景，例如 `replay/quoted-history-not-progress.json`。

### 语义评测集

模型判断本身是否正确，用评测集衡量：

1. 从真实使用中收集案例，尤其是出过错的案例。每个案例保存输入，并写明期望的判断，例如“这段是引用旧对话，不算用户进展”“任务 A 应该保持 waiting”。期望判断由用户确认。
2. 修改提示词、更换模型或调整输出格式时，用真实模型跑完整个评测集，记录通过数和失败的案例。修改前后各跑一次，用同一份评测集比较。
3. 模型输出有随机性。重要案例重复运行几次，按通过比例判断，不凭一次结果下结论。
4. 发现新的误判时，先把这个案例加进评测集并确认它失败，再修改提示词或程序。
5. 评测集单独运行，不放进每次提交都跑的测试，因为它慢、要花费额度，而且结果不完全稳定。交付提示词或模型相关的修改前必须运行。

评测集和它的运行脚本放在仓库里的固定位置，例如 `tests/eval/`，并在项目 `AGENTS.md` 里写明运行命令。每次运行的原始输出不进仓库。

## 桌面界面

- 把界面逻辑（显示什么文字、按钮什么时候可用、点击后状态怎样变化）放进可以直接测试的类，例如 ViewModel，用普通单元测试覆盖。
- 少数关键操作路径用界面自动化测试，例如 Windows 上的 FlaUI。只覆盖启动、主要操作和关闭这类关键流程。
- 视觉效果和使用感受靠实际打开程序查看，并把截图或现象交给用户判断。
