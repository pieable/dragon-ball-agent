# 验收设计

验收设计用于在实现前确定什么结果才算完成，以及什么观察能够证明或推翻这个判断。非平凡功能、跨组件或外部边界、核心状态不变量、难以复现的缺陷，以及已有检查通过但用户结果仍失败时使用。局部且结果唯一的修改只采用必要部分。

## 当前任务规格

任务跨越多个阶段、参与者或需求调整时，维护一个可发现、可修正的当前任务规格。它是当前结果、已确认决定、未知与假设、边界、验收、阶段接口和采用路线的共同来源，可以存在于当前计划、已有产品文档或项目规格中，不要求创建固定目录或套用统一模板。

用户校准或新证据改变规格时，标出受影响的计划、实现合同、测试和运行证据，只更新受影响部分。逐项检查变化对仍有效的旧规则及跨功能关系的影响；未受影响的工作和仍然有效的证据继续保留。交付候选应能说明它依据的是哪一版当前规格，避免旧要求、旧测试或旧运行结果与新设计混用。

项目预计长期维护，并且会跨多个任务或由多名参与者持续推进，而且建立规格入口确实能减少信息散失时，优先使用项目已有的产品或设计资料；没有合适入口时，可以建立一个简洁的项目级规格目录并由 AGENTS.md 索引。目录只保存当前规格、关键设计、任务关系和验收证据等后续仍需使用的内容，不复制会话过程，也不要求所有项目采用同一名称和层级。短期、单阶段或上下文足以承载的任务不为形式创建目录。

多个待确认决定相互依赖、分别询问会使后续方案或答案反复失效时，集中列出会改变目标、结构、权限、验收或明显投入的问题，并说明各自影响。能够通过调查解决的事实先调查，普通实现细节自行处理；问题相互独立或可随反馈逐步形成时继续渐进确认，不积攒成固定问卷。

## 开发前整体检查和证据选择

每个新的开发工作时段开始时，在首次修改生产代码前做一次轻量整体检查。持续项目在当天首次继续、会话或上下文切换后恢复时也执行。它独立于当前出现的缺陷和待办，不以失败、轮数、耗时或投入作为前提。检查可以写在当前计划、现有规格或对用户的阶段说明中，不要求创建新文件；同一工作时段没有结构变化时不重复执行。

先回答当前实现是否建立在足够理解上：

1. 用户现在要获得的完整结果是什么，哪些整理、判断或维护责任不应留给用户？
2. 当前日常入口从启动、读取来源、判断、写入状态到展示或执行，实际依次发生什么？
3. 每项长期状态、权威来源和决定由谁维护，程序、模型和用户分别负责什么？
4. 当前准备处理的事项位于这条路径的哪里，它会直接推进主路径，还是只维持历史实现？
5. 哪项尚未确认的事实或假设最可能改变下一步，什么观察能够支持或推翻它？

根据第五项选择证据。目标、完整体验、用户不愿承担的责任或价值取舍不清楚时，回到产品过程并取得用户的真实经历或决定。外部成熟做法、标准、候选或平台当前行为会改变方案时，先研究相应一手材料和反例。当前仓库、配置、宿主、依赖、性能或集成行为不清楚时，读取真实对象或运行能够区分路线的最小实验。不同证据存在依赖时按需要组合，但每一步都要说明它预计改变哪个决定，不能用生产实现替代调查。

取得证据后，更新受影响的当前规格、运行逻辑、架构判断和验收，说明哪些原决定继续有效，再判断是否已经可以实现。完整路径已经清楚、修改原因明确且没有结构影响时，用一句简短结论确认后直接处理。无法说清路径或证据尚不足以决定主结构时，不沿历史待办继续编码。

产品结果、责任归属、状态来源或执行主路径一旦变化，立即重做受影响部分。尤其在新增持久状态、后台进程、调度器、模型职责、重试、兜底、兼容或第二条路径之前，先说明为什么现有结构不能承担该责任，以及新增机制最终由谁调用、取代什么、如何验证。需求已经改变时，先更新会误导实现的当前规格和验收；新旧架构并存时，明确最终主路径和旧路径的退出方式。

整体检查暂时不受历史代码和投入约束，写出满足当前要求的最简运行逻辑，再与现状比较。只有确认下一项改动直接缩小两者差距后才继续编码。发现需要改变主要产品行为、架构或明显投入时，停止受影响实现，由用户决定；路线仍成立时保留可复用成果并继续最小下一步。准备进入下一个主要阶段或声明整体完成前，再确认实际实现仍符合这条主路径。

## 按风险展开生命周期

普通开发沿最短闭环完成结果、实现和相应验证。数据迁移、权限或安全边界、难以回滚的状态变化、核心架构替换、大范围跨模块改造或正式发布等失败代价较高的工作，按实际风险展开：

1. 确认当前规格和验收合同。
2. 形成并检查设计及主要取舍。
3. 拆分实现责任和阶段合同。
4. 实现并取得分层验证证据。
5. 按风险需要进行独立评审并处理发现。
6. 从真实入口完成最终候选验收，再按授权发布。

只有风险需要时才展开相应阶段。没有设计分歧时不为形式生成设计文档，局部修复不拆成多阶段。需要独立评审时可以直接调用只读评审代理；发布仍按已有授权执行。

## 验收合同

为会改变完成判断的要求记录以下内容。可以写在现有任务、规格、设计或测试中，不要求另建文档。

| 项目 | 需要回答的问题 |
| --- | --- |
| 结果声明 | 用户或系统最终能够观察到什么结果？ |
| 生产路径 | 代表性输入从日常入口到结果经过哪些提供方、调用方、状态和外部边界？ |
| 不变量 | 哪些状态、权限、身份、预算或拒绝行为必须始终成立？ |
| 反例 | 什么输入、绕过路径、故障或旧状态能够推翻完成声明？ |
| 自动门槛 | 哪些命令或检查必须执行成功，它们各自证明哪一层？ |
| 真实证据 | 哪些宿主、界面、模型、外部服务或完整流程必须实际运行？ |
| 所有权与新鲜度 | 谁能改变门槛，哪些后续修改会使已有证据失效？ |

结果声明使用可观察行为，不使用“代码已经支持”“模块已接入”或“测试通过”代替产品或系统结果。生产路径只追踪声明成立所需的部分；当同一要求有多个可执行入口时，包含会绕过限制或改变权威状态的入口。

## 从反例选择证据

先问什么错误会让完成声明不成立，再在该错误发生的层级设置检查：

- 局部计算、解析或转换错误由单元检查捕获。
- 模块存在但没有接线、参数未传播或状态视图不一致，由集成检查捕获。
- 客户端限制可被服务端、CLI、RPC 或其他调用方绕过，由真实边界和拒绝路径检查捕获。
- 不可变绑定、唯一所有者、组合预算、幂等和权限隔离等要求，作为不变量检查其正常转换与禁止转换。
- 模型实际收到的提示、工具 schema 或上下文需要在最终组装点做 snapshot，必要时沿真实模型调用核验。
- 用户操作、宿主加载、外部服务和可见界面需要经过日常入口的代表性操作。

检查应能在目标错误存在时失败。无法说明测试怎样失败时，先修正验收设计。可以用手工观察、日志、快照或受控实验代替不合理的自动测试，但要记录观察对象、判据和限制。

## 基线与实现

缺陷修复先复现原问题。新增确定性合同在可行时先运行一条尚未满足的检查，确认失败来自缺失行为，而不是环境、语法或测试自身错误。探索性工作可以先取得基线或最小实验，再决定稳定合同。

实现者可以增加更细的测试，不能为了获得绿灯删除、跳过或降低既定反例与门槛。真实要求、平台接口或新证据表明门槛错误时，由掌握验收合同的负责人修改，并记录受影响的要求和证据。

阶段进入实现或交给 subagent 后，当前阶段合同保持稳定。需要调整时，执行者停止受影响工作并提交冲突或新证据，由掌握整体任务规格的负责人更新合同；未受影响的阶段继续。整体任务规格的可修正性不能成为执行者自行扩大范围、改变产品结果或降低验收门槛的理由。

## 逐项关闭

要求较多或跨越多个边界时，用现有任务记录一张最小追踪表：

| 结果或不变量 | 实现位置 | 反例/检查 | 当前证据 | 状态 |
| --- | --- | --- | --- | --- |

状态只按实际证据写为已满足、失败、未执行或受阻。交付前确认：

1. 每项重要结果和不变量都能找到实现与证据。
2. 约定检查没有未执行、报错、待定或被静默跳过。
3. 证据来自最终候选；后续修改使证据失效时已经补验。
4. 自动检查覆盖不到的真实入口和外部边界已经实测，或者明确标为未验证。

完成条件是验收合同被有效证据关闭，不是测试数量、覆盖率数字或输出中的零失败。

最后从规格反查候选：是否有要求遗漏、只完成一部分、产生相反行为，或增加未经确认且会改变结果、风险或维护负担的内容。这项收敛检查用于发现实现与规格的偏离，不把普通技术细节误判为擅自增加产品范围。
