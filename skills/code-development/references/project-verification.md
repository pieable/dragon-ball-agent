# 项目验证入口

用于持续维护、会由不同 agent 接续的项目，且现有工具或说明不足以重复验证真实用户功能时。已有可用入口就直接复用和补齐，本参考不要求另建一套测试框架。

## 查明现有运行方式

从项目文件和实际运行查明用户接触的入口、启动到可用状态的命令、配置与数据前提，以及可用的操作工具。优先使用已有测试、浏览器驱动、CLI、API 或宿主控制能力。确定可取得的界面、终端、响应、日志和持久化结果证据。

核实多个实例能否隔离端口、数据目录和会话。验证使用可隔离的实例及测试数据，已有用户会话和外部操作继续遵守当前授权。缺少环境或权限时记录具体缺口，不用改变功能要求来绕过。

## 接通可重复的验证路径

将下列实际命令、操作或工具入口写入项目现有验证说明，并链接必要的脚本。没有现成说明时，放入项目约定的开发资料或项目级 Skill，由 AGENTS 或开发入口索引。路径和命令以已核实的项目内容为准。

1. **启动。** 运行真实构建和启动命令，准备必要迁移与测试数据，说明怎样确认已可使用。检查服务进程存在和实际功能可用之间的差别。
2. **核对实例。** 用只读检查确认版本、配置、端口或进程归属以及必要认证。出现异常时先确认正在操作正确实例。
3. **操作。** 通过用户实际入口执行功能，复用稳定选择器、命令或公开接口。验证生产入口时不使用直接设置内部状态的方式代替用户操作。
4. **取得证据。** 同时记录操作与可观察结果，并检查对应文件、数据库或其他副作用。证据关联到本次候选及场景，保存位置可查。
5. **清理。** 停止本次创建的实例并回收测试状态，只处理已确认归属的对象。保留验证证据，并在清理后检查证据仍可读取。

脚本需要明确的调用方式、前置条件和失败输出，并能够在失败后重新执行或明确恢复步骤。测试或 dry-run 名称不直接证明没有副作用，涉及外部影响时核实它实际执行和跳过了什么。

## 维护功能与验证路径的对应关系

在项目已有测试索引或验证说明中，记录功能的用户入口、必要前提、操作步骤和可观察的成功结果，链接对应自动检查或手工操作。先覆盖当前任务涉及的关键功能，明确尚未覆盖的范围，随相关功能变更更新。

同一结果有多个入口时，标明共享检查证明的部分，以及各入口仍需要核验的连接。功能不可达时记录缺少的前提和已尝试的路径，不缩短操作流程来制造成功。功能移除或行为改变后，按当前要求更新或删除失效说明和检查。

## 实际跑通再交付

新增或修改验证入口后，照说明完整执行启动、实例核对、代表性功能操作、取证及清理。验证成功的范围以实际跑过的场景为准。新增脚本和操作步骤需要实际验证，未执行部分保留明确状态。

产品交付的覆盖仍由验收合同决定，跑通一个代表场景只证明该验证路径可用。验证入口发生漂移时，区分说明错误、驱动工具问题和真实产品缺陷，分别修正有权限修改的对象并保留证据。
