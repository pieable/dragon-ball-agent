# 变更、Git 与交付流程

用于持续项目、多人或多代理协作，以及跨实现、审查、集成和交付阶段的开发。实现负责人组织完整变更，执行者负责其范围内的结果，审查者独立核对候选，主 agent 负责与用户形成决定及最终整合。优先使用已有 issue、任务、设计资料、提交与 PR 作为材料入口，按下一位接收者需要补足内容。

## 从要求接到设计与实现

先明确要改变的可观察行为、必须保持的不变量、验收依据和本次交付终点。区分探索原型、可合入候选和正式使用，确认代码最终从哪个入口被使用。需求和验收的具体方法沿用 [验收设计](acceptance-design.md)。

会改变重要接口、状态归属、兼容策略或部署顺序的决定，在大量实现前让有关调用方、维护者或独立视角检查成立条件。普通局部技术选择由执行者处理。设计检查形成当前采用的决定、理由、接口与关键反例，作为实现和审查共同输入；新证据改变决定时更新受影响材料。

划分可独立实现和核验的变更，保持每项变更的实现、接线、测试及必要说明完整。跨责任接口和验收依据应足以支持下游工作，已决定部分直接推进。设计与实现之间出现根本冲突时，把事实交回掌握该决定的负责人，先修正共同依据。

## Git 基线、分支与提交

持续维护的仓库默认按下面的习惯使用 Git。创建本地分支和本地提交不需要逐次请示用户；推送、创建 PR、合并到主分支和发布按项目约定或已有授权执行。项目有其他成文约定或用户限定了做法时，按其要求。

### 动手前看清现状

1. 运行 `git status`、`git branch --show-current` 和 `git log --oneline -5`，看清当前分支、已有改动和未跟踪文件。
2. 读取项目的分支、提交和 PR 约定（`AGENTS.md`、`CONTRIBUTING.md`、已有提交说明的格式）。
3. 查明哪些已有改动属于本任务。不属于本任务的改动保持原样：不还原、不暂存、不混进本次提交。无法分开时保留原状，在交付说明里写出本次差异及影响。
4. 依赖远端最新状态时，在已有授权内 `git fetch`，避免在过时的基线上判断集成结果。

### 开分支

- 当前在主分支（`main`、`master` 或项目指定的分支）上时，先 `git switch -c <分支名>` 再改。分支名沿用项目已有命名；没有时用简短的英文主题，例如 `fix/focus-carry-over`。
- 一项独立工作一个分支。已经在本任务的分支上时继续使用。
- 切换分支会带上工作区里未提交的改动，分支名变了不代表内容已经隔离。另建工作树（`git worktree add`）不会复制未提交的改动。转移内容时只转移确认属于本任务的部分。
- 处理合并冲突前，确认冲突两边各自属于哪项工作；解决后重新运行受影响的检查。

### 经常提交

每完成一个能用一句话说清的步骤，并且相关检查通过，就提交一次。例如：修好一个缺陷并通过对应测试；完成一处行为不变的重构；接通一条功能的完整路径；更新一份文档。不要把一整天的改动攒成一个提交。

以下时刻之前，工作区里不留本任务未提交的改动：切换到别的任务、开始一个可能失败的试验、长时间暂停、交付。

行为修改和重构、格式化分开提交，审查者才能看清哪一个提交改变了行为。

### 用 Git 代替手工备份

- 要保留某个版本，就提交它或开一个分支，不复制文件或目录。不建 `*.bak`、`before/`、`baseline/`、`candidate-source/` 这类副本。
- 需要对照新旧代码时用 `git diff <提交>`、`git show <提交>:<路径>`；需要同时运行两个版本时用 `git worktree add`。
- 试验失败时用 `git restore`、`git switch` 或丢弃试验分支回到原状。

### 提交前检查

1. 按文件暂存：`git add <文件>`。工作区里有不属于本任务的改动时，不用 `git add -A` 或 `git commit -a`。
2. 运行 `git diff --staged`，确认没有混进无关改动、密钥、日志、构建输出或临时试验文件。
3. 运行项目的格式化、编译和相关测试，确认通过后再提交。
4. 提交说明第一行用一句话写改变了什么行为，例如“关闭任务窗口时一起退出后台更新”，不写“更新文件”“修改代码”。原因或取舍不明显时，空一行再补充。沿用项目已有的语言和格式。

### 合并与交付

一项工作验证完成后，按项目约定合并回主分支。没有约定时，交付说明写清分支名、最后一个提交号、是否已推送和合并，并问用户是否合并。分支长期不合并会和主分支越走越远，交付时要提到这一点。

暂不提交时，交付说明写出候选包含哪些未提交的文件，不只用分支名或“最新版”指代候选，也不另存完整副本或计算文件哈希。

## PR 与 CI

有可用共享远端的持续项目，默认以 PR 和 CI 组织集成，项目有明确的其他约定或用户指定本地终点时按其要求。尚未建立流程时，在已有授权内创建当前变更的 PR，补足本次集成需要的最小 CI 入口，执行并核对结果。已有对应 PR 时继续使用，避免为同一变更重复创建。推送、创建或更新 PR 时核实目标仓库、base、head 与实际 diff。仍在实现或关键验证未完成时准确标记状态。PR 说明应让未读聊天的审查者理解问题、改变后的行为、主要取舍、测试结果、剩余风险及需要时的恢复方法。新建或用户要求继续处理的 PR 按宿主工具要求附加到当前任务。

读取适用的 CI 工作流、运行条件、检查矩阵和仓库合并规则，确定哪些检查是必须通过的。查运行链接、对应 SHA 或测试合并提交、实际执行范围及结论，区分分支检查与基线组合检查。旧提交的通过结果不自动覆盖新提交；没有触发、待执行、被取消、缺失和跳过的必要检查要查明原因。检查被平台标为成功也要核对是否实际执行了所需验证。

使用 GitHub 时，PR 的三点 diff 是从共同祖先到 head 的变更，不单独证明与最新 base 的组合已经验证。`pull_request` 工作流常检查测试合并提交，记录时区分 head SHA 和该测试提交。workflow 因路径过滤未运行可能让必要检查保持 pending，而 job 因条件跳过可能被记为成功。使用合并队列时核对 `merge_group` 触发与组合提交的必要检查，不能只沿用 PR 自身的结果。其他托管平台按其实际语义核对同类关系。

失败时区分本次回归、已有失败、环境问题和不稳定测试，保留命令及日志，修复本次问题并重跑受影响检查。不能通过删除检查、降低规则或反复重试掩盖失败取得绿灯。已有失败与本次无关时写出依据及影响，仍按项目合并规则处理。CI 缓存、测试发现与产物来源的机制检查见 [构建与发布](build-and-release.md)。

缺少远端、所需权限或可用执行环境时，先使用现有本地测试、构建与正常使用路径形成可审查候选，明确集成尚缺什么、怎样补足及由谁继续。只有项目或用户明确把终点限定为本地结果时，在该范围内完成交付；否则将集成缺口保留为未完成工作。已有远端而缺少 CI 配置时，按前述默认路径补齐本次需要的检查。涉及新的外部服务、权限或费用时先完成可审查方案，再由用户决定。

## 候选与证据交接

送审材料应让审查者独立取得下列事实，可集中在现有 PR、任务或阶段记录中：

| 内容 | 需要能核对的事实 |
|---|---|
| 要求和决定 | 当前问题、预期行为、不变量、已接受取舍及资料入口 |
| 基线和候选 | 基线提交和候选提交，或候选包含的未提交文件；新文件和排除的既有改动 |
| 实际修改 | 实现、消费者、接口或数据变化，相关说明，仍需保留的行为 |
| 验证 | 命令、工作目录、必要环境与版本、结果和日志，证明的行为、未运行范围及原因 |
| 集成和交付 | PR 与 CI 状态、目标基线、构建或安装入口、当前停留阶段和后续责任 |

证据对应确切候选和有效要求。工作区会继续变化时，先提交候选，或放到单独分支或工作树，让审查者读取固定版本。这些内容写进 PR 说明或交付消息，不在仓库里另建核验记录文件。评审过程中改变相关文件，及时告知审查者变化及影响；并行工作避免让审查者读取一个不断变化且无法复原的混合版本。验证日志不复制凭据或不必要的用户数据。

## 审查发现与复审

实现负责人把发现交给能核对原始证据的执行者，按触发条件、因果关系和实际影响判断。成立的问题按共同根因检查本次影响范围内的相关实例，修复机制并增加或复用能捕获目标错误的检查。误报、已有保护或有意设计的行为，通过源码、实际运行或已接受要求说明，由审查方或掌握合同的负责人核对。

在原问题处或已有任务中保留问题位置、严重程度、证据、处理结果、修复候选及复验依据。处理结果可以是已修复并验证、证据反驳、由有权负责人接受的范围变更或仍未解决。未经处理的阻塞问题继续阻止相应交付，普通非阻塞意见按实际价值处理。

修复后交回新的候选差异和受影响验证，由审查者核对问题是否关闭及是否引入相关回归。未受影响的结论与证据沿用。候选或基线变化使原结论失效时补审相应关系，不按固定轮数重复全量审查。出现重复争论、连续修补改变主结构或审查不能收敛时，整理共同根因和分歧证据，重新检查要求或方案。

## 集成、交付与反馈

合并前确认候选和 CI、审查结论、所需人工批准对应，所有阻塞发现已经处理，项目规则已经满足。代理的审查结论按项目规定使用，不能替代规则要求的人工批准。PR 中拟修改的审查或验收规则在被有权负责人接受前，不用来放宽该 PR 的通过标准。补充提交、冲突解决或基线变化后，按影响补验并核对批准是否仍有效。

复用项目的合并队列或集成检查，验证候选与目标分支及相关并行改动组合后的结果。没有这种机制时，在安全、已授权的本地环境检查实际组合，清楚记录尚缺的远端保障。只有任务范围和已有授权包含合并时才执行，按项目约定保留可追溯的提交与 PR 关系。

交付安装包、插件、可执行文件或部署时，核对产物来自哪组源码、构建配置及检查结果，确认实际安装或服务加载的是该产物。合并后检查相应集成结果，发布后沿约定正常入口核验关键行为；测试环境的成功不自动证明日常或生产入口已更新。依任务风险说明恢复动作、触发条件和负责人，状态迁移涉及旧版本时核对回退是否仍能正确读取数据。

范围包含运行后观察时，使用现有日志、错误率、关键业务结果或资源指标判断变更，按授权处理回归及恢复，不另行创建未经请求的长期监控。把已确认缺陷转成能复现的回归案例，把稳定机械规则放进项目检查，把本项目约束留在项目资料；有跨任务价值的方法再进入通用 Skill。记录实际漏检环节及证据，下次变更工具、模型或方法时复用有关案例检查实际效果。

交回时区分实现完成、验证通过、评审通过、待合并、已合并、已构建、已安装和已部署。仅列当前交付相关状态，说明剩余动作由谁执行、缺什么条件，以及对用户当前使用的影响。任务只要求补丁或候选时，准确完成该终点。

## 方法来源

- [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)：分支、提交、PR、审查与合并的关系，实际步骤沿用项目平台和约定。
- [Git switch](https://git-scm.com/docs/git-switch) 与 [Git worktree](https://git-scm.com/docs/git-worktree)：未提交内容与工作树隔离的边界。
- [PR diff](https://docs.github.com/en/pull-requests/reference/branches#three-dot-and-two-dot-git-diff-comparisons)、[必要状态检查](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) 与 [合并队列](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)：候选、基线、CI结果、触发条件及组合提交的关系。
- [Claude Code 团队审查流程](https://claude.dev/blog/solving-code-review-at-anthropic/)：开发前自验、独立审查、CI、按风险批准、集成发布及事故反馈。本文采用这些责任连接，不把其内部人数、轮数或发布渠道转成通用固定门槛。
- [Code Review](https://code.claude.com/docs/en/code-review)：公开服务发现、核验与报告的边界，运行验证和合并控制需由相应环节承担。

以上流程是结合当前两份 Skill 与用户已确认职责形成的工程指导，项目事实、现行平台语义及操作权限按实际对象核对。
