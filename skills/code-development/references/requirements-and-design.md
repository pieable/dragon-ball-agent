# 需求分解与设计

在用户目标已经基本明确，但仍需决定组件职责、接口或跨组件行为时使用。目标与核心体验尚未确定时，先按主 Skill 的产品过程处理。本文件帮助形成可实现的设计，验收关闭方法仍由 `acceptance-design.md` 承载。

## 从用户结果分解到软件行为

1. 用代表性场景说明谁在什么条件下做什么，以及完成后能够观察什么。区分用户明确要求、外部限制和当前技术假设。
2. 沿场景识别所需输入、处理、输出及失败后的行为。每项派生要求说明它支持哪个上层结果；发现无法满足或互相冲突时回看上层要求。
3. 把会影响设计的质量目标改成具体场景。例如“可靠导入”细化为“写入中断并重启后，已完成内容仍可读取，未完成内容不会被当作成功发布”。数值门槛来自真实用途或测量，待定值保留为未知。
4. 将最可能推翻结构的假设转成源码核对、原型或小实验。保留决定、理由和成立条件，放入当前规格或已有设计资料。

结果应足以解释每个主要组件为什么需要存在，以及缺少它会使哪个用户结果失败。简单改动可以在当前任务说明中完成这些判断。

## 设计职责、接口和运行时交互

围绕业务责任与权威状态划分组件。分别看静态职责和运行时协作：谁接收请求，谁决定是否合法，谁执行副作用，谁拥有持久状态，谁把结果呈现给用户。一个数据结构被多个模块读取，不意味着这些模块都可以维护它。

对会决定正确性的接口说明：输入和身份范围、前置条件、成功结果与状态变化、失败表示、调用者后续动作。宿主已有合同以当前版本为准。接口假设未核实前先隔离未知，避免让多个模块复制同一猜测。

业务规则由共同使用的应用能力承载。UI、CLI、宿主回调和测试通过各自适配代码调用它。适配代码负责格式、协议和宿主生命周期转换。这样可以单独检查业务规则，也能核验各入口是否真正接入。已有直接调用足够时沿用它，仅为存在的边界建立接口。

对正常场景画出或写出调用顺序，再沿同一路径检查关键失败场景。存储、错误表示、身份、日志等影响多个组件的决定统一说明，避免每个组件自行选择互不相容的语义。具体状态和恢复设计使用 `state-and-reliability.md`。

## 比较设计方案

只有真实存在取舍时才比较候选。用同一组重要场景衡量方案是否满足要求、依赖哪些假设，以及实现和后续修改的代价。记录选择理由与会触发重判的条件。

例如同步处理容易保证调用结束时工作已完成，但长任务可能阻塞界面；后台处理改善响应，却引入任务身份、取消和迟到结果的问题。先确定用户需要的响应和完成语义，再选择结构。普通技术细节由实现者判断，影响产品目标、主要形态或明显投入的选择按主 Skill 交回决定。

实现时用一条最小完整路径检查职责和接口是否成立。新证据改变设计时，同时更新受影响的调用方与依据。评审既检查代码符合设计，也检查设计是否仍解释得了实际运行。

## 例子：桌面和 CLI 共用的资料导入

目标是两个入口都能导入单份资料，资料校验规则一致，失败不会发布不完整内容。

- 将格式解析、业务校验、保存与发布区分为责任。两种入口调用同一个导入能力，界面负责选择文件和呈现结果。
- 导入接口返回明确成功结果或失败原因。业务拒绝若通过返回值表达，两个入口都检查该结果，再决定是否显示成功。
- 校验约束在共同能力中执行，避免 CLI 绕过界面限制。文件系统与桌面宿主细节由实际需要的适配代码处理。
- 先让一份小资料经过真实入口完成导入和读取。再检查非法资料、写入中断及重复执行，按这些场景决定提交和恢复机制。

最终设计材料包括这条路径、责任与接口、关键取舍及未解决假设。它可以只是现有规格中的一小节。

## 方法来源

以下是方法依据，正文为针对代码开发的综合指导。需要更完整方法时阅读原文相关部分。

- [NASA：软件需求记录与分解](https://swehb.nasa.gov/spaces/7150/pages/16449789/SWE-049%2B-%2BDocument%2BSoftware%2BRequirements)。采用需求来源、理由、假设和逐层分解方法，正式流程按项目风险裁剪。
- [arc42 方法](https://arc42.org/method/)。职责、运行时视图、跨组件概念与实现反馈。
- [Cockburn：Ports & Adapters，2005](https://alistair.cockburn.us/hexagonal-architecture)。应用规则与外部适配的边界。
- [SEI：ATAM，2000](https://www.sei.cmu.edu/library/atam-method-for-architecture-evaluation/)。存在重要质量属性冲突时深入分析架构取舍。
