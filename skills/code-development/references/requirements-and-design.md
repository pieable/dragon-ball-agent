# 需求分解与设计

在用户目标已经基本明确，但仍需决定组件职责、接口或跨组件行为时使用。目标与核心体验尚未确定时，先按主 Skill 的产品过程处理。本文件帮助形成可实现的设计，验收关闭方法仍由 `acceptance-design.md` 承载。

## 从用户结果分解到软件行为

1. 用代表性场景说明谁在什么条件下做什么，以及完成后能够观察什么。区分用户明确要求、外部限制和当前技术假设。
2. 沿场景识别所需输入、处理、输出及失败后的行为。每项派生要求说明它支持哪个上层结果；发现无法满足或互相冲突时回看上层要求。
3. 把会影响设计的质量目标改成具体场景。例如“可靠导入”细化为“写入中断并重启后，已完成内容仍可读取，未完成内容不会被当作成功发布”。数值门槛来自真实用途或测量，待定值保留为未知。
4. 将最可能推翻结构的假设转成源码核对、原型或小实验。保留决定、理由和成立条件，放入当前规格或已有设计资料。

结果应足以解释每个主要组件为什么需要存在，以及缺少它会使哪个用户结果失败。简单改动可以在当前任务说明中完成这些判断。

## 设计职责、接口和运行时交互

新增或重塑接口时，先写代表性调用方怎样完成操作，包括正常调用、会改变设计的失败或中断情形以及调用后的可观察结果，再据此推导类型、函数签名和模块边界。用实际调用检验接口是否足够，调用方不应靠猜测内部步骤才能正确使用它。普通局部修改可以直接对照已有调用方，无需另写设计稿。

有状态或分支密集的行为，先列出有效状态、允许的转换、不能出现的组合以及主要读取方式，再选择能表达这些关系的数据结构。例如，用明确状态及转换表达任务生命周期，用有类型的输入和结果表达不同情况，用一个注册来源派生各入口需要的列表。逐项检查主要操作怎样读取和更新该结构，再填入实现。现有局部逻辑已清楚时保持直接实现，新增结构应实际减少重复规则、非法状态或调用方负担。

围绕业务责任与权威状态划分组件。分别看静态职责和运行时协作：谁接收请求，谁决定是否合法，谁执行副作用，谁拥有持久状态，谁把结果呈现给用户。一个数据结构被多个模块读取，不意味着这些模块都可以维护它。

对会决定正确性的接口说明：输入和身份范围、前置条件、成功结果与状态变化、失败表示、调用者后续动作。宿主已有合同以当前版本为准。接口假设未核实前先隔离未知，避免让多个模块复制同一猜测。

涉及字段/枚举、默认值、分页或旧数据时，用[接口、数据与版本演进](contracts-and-data-evolution.md)取得当前读写双方、存量样本和共存组合，再决定 presence、单位、兼容方向与迁移次序。涉及授权或不受信输入时，用[权限与信任边界](trust-boundaries.md)核对主体、资源、属性、缓存隔离以及最终打开/连接/执行的位置。

业务规则由共同使用的应用能力承载。UI、CLI、宿主回调和测试通过各自适配代码调用它。适配代码负责格式、协议和宿主生命周期转换。这样可以单独检查业务规则，也能核验各入口是否真正接入。已有直接调用足够时沿用它，仅为存在的边界建立接口。

对正常场景画出或写出调用顺序，再沿同一路径检查关键失败场景。存储、错误表示、身份、日志等影响多个组件的决定统一说明，避免每个组件自行选择互不相容的语义。具体状态和恢复设计使用 `state-and-reliability.md`。

按后续修改者可能只看到局部文件的情形检查受影响结构：

- 同一状态由谁修改，其他模块是否通过该责任方请求更新；多个并发参与者确需共享时，明确共同不变量及协调方式。
- 模块内部是否能被外部随意导入。用项目已有的导出边界、类型或静态检查保护内部决定，使调用者走公开接口。
- 多处是否手工维护同一列表或规则。优先从一个权威来源派生，确需独立保存时用一致性检查发现偏差。
- 调用者是否必须协调多个内部阶段才能完成一个业务操作。让接口承担它应拥有的协调，保留有实际策略、适配或独立责任的层。

会反复出错且能够确定性表达的约束，落实到类型、生成步骤、静态检查或可运行测试中；需要情境判断的部分继续说明理由和适用条件。检查围绕当前改动，不借此全面重构已有系统。

## 控制结构随需求演变的复杂度

同一业务决定应有明确的权威来源：改变它时，能找到负责实现的地方和受影响的消费者。相似代码是否合并，看它们是否表达同一规则、是否应随同一个原因改变。只是语法相似而用途、权限或演变方向不同的代码可以分开；抽象需要减少需要同步修改的地方及调用方知识负担。

外部数据在进入相应信任边界时解析和验证，内部传递明确的领域值与结果，尽量将规则计算与 I/O 副作用分开。授权、跨进程输入和并发提交等边界仍按各自条件检查，不能用入口曾经校验过来代替当前权限或状态判断。能通过类型和数据结构排除的非法组合直接排除，保留动态业务约束所需的运行检查。

新需求导致特殊分支、跨模块协调或重复状态持续增加时，问“如果从开始就有这个需求，怎样的职责与数据结构更合理”，对照当前结构找到需要改变的责任。优先消除不必要的状态、复制和中间步骤，再增加机制。沿真实调用方分步迁移，按 [调试与修改](debugging-and-change.md) 保护行为；主要架构或投入变化按主 Skill 与用户形成决定。

## 从实际结构发现问题

复杂度、覆盖率和重复检测用于选择值得调查的区域。结合改动频率、故障、业务责任与调用关系判断处理价值。可考察 [crapper](https://github.com/unclebob/crapper) 的复杂度与覆盖组合，以及 [dryer](https://github.com/unclebob/dryer) 的结构相似候选；优先沿用项目已有的适配工具。工具阈值用于筛选，不能仅为过线拆碎函数或合并不同业务规则；具体缺陷与约定门槛才决定是否阻塞交付。

用户需要理解系统、比较架构或判断影响时，从当前代码、配置及必要运行观测形成视图，显示关键职责、状态归属、依赖或运行序列，允许追到具体来源。按问题选择视图，避免只画文件树或把所有连线堆在一页；静态扫描无法确认的动态关系保留未知。实际结构与拟议方案清楚区分，采用方案后检查代码与图是否一致。

可参考 [uml-viewer](https://github.com/unclebob/uml-viewer) 的逐层查看、质量信息叠加和方案比较方式。选择现有依赖分析、图示或交互工具前核实语言、运行环境、来源提取与维护成本，不将特定工具设为必装依赖，也不为一次说明自建可视化平台。

## 比较设计方案

只有真实存在取舍时才比较候选。用同一组重要场景衡量方案是否满足要求、依赖哪些假设，以及实现和后续修改的代价。记录选择理由与会触发重判的条件。

例如同步处理容易保证调用结束时工作已完成，但长任务可能阻塞界面；后台处理改善响应，却引入任务身份、取消和迟到结果的问题。先确定用户需要的响应和完成语义，再选择结构。普通技术细节由实现者判断，影响产品目标、主要形态或明显投入的选择按主 Skill 交回决定。

实现时用一条最小完整路径检查职责和接口是否成立。新证据改变设计时，同时更新受影响的调用方与依据。评审既检查代码符合设计，也检查设计是否仍解释得了实际运行。

## 例子：桌面和 CLI 共用的资料导入

目标是两个入口都能导入单份资料，资料校验规则一致，失败不会发布不完整内容。

- 将格式解析、业务校验、保存与发布区分为责任。两种入口调用同一个导入能力，界面负责选择文件和呈现结果。
- 导入接口返回明确成功结果或失败原因。业务拒绝若通过返回值表达，两个入口都检查该结果，再决定是否显示成功。
- 校验约束在共同能力中执行，避免 CLI 绕过界面限制。文件系统与桌面宿主细节由实际需要的适配代码处理。
- 先让一份小资料经过真实入口完成导入和读取。再检查非法资料、写入中断及重复执行，按这些场景决定提交和恢复机制。

最终设计材料包括这条路径、责任与接口、关键取舍及未解决假设。它可以只是现有规格中的一小节。

## 方法来源

以下是方法依据，正文为针对代码开发的综合指导。需要更完整方法时阅读原文相关部分。

- [ub-mode](https://github.com/unclebob/ub-mode/blob/master/SKILL.md)：吸收规则归属、数据形态、重新审视设计和减少复杂度的判断；工具评分用于调查，范围、权限与交付沿用本地要求。

- [NASA：软件需求记录与分解](https://swehb.nasa.gov/spaces/7150/pages/16449789/SWE-049%2B-%2BDocument%2BSoftware%2BRequirements)。采用需求来源、理由、假设和逐层分解方法，正式流程按项目风险裁剪。
- [arc42 方法](https://arc42.org/method/)。职责、运行时视图、跨组件概念与实现反馈。
- [Cockburn：Ports & Adapters，2005](https://alistair.cockburn.us/hexagonal-architecture)。应用规则与外部适配的边界。
- [SEI：ATAM，2000](https://www.sei.cmu.edu/library/atam-method-for-architecture-evaluation/)。存在重要质量属性冲突时深入分析架构取舍。
- [pstack：设计执行要求](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/references/runner-prompt.md)与[设计检查](https://github.com/cursor/plugins/blob/main/pstack/skills/architect/references/design-red-flags.md)。采用调用方用法优先和结构约束检查，候选数量、模型配置与人机决定方式沿用本项目要求。
