# 调试与安全修改

本参考用于核心结果失败、故障原因不明或需要改变既有代码时。它补充实现与实验流程中的定位、归因和回归保护；按风险选用步骤，不要求所有任务采用同一流程。

## 先定位第一个偏差

对可重放的确定性路径，把预期结果写成可观察条件，并记录输入、运行版本、配置、依赖和实际结果。沿真实路径从入口向后检查输入、调用、状态转换和输出，找出第一个不再符合预期的步骤。后续异常可能只是这个偏差的结果，先定位源头再修补。并发、性能或概率行为按 [实验与结果归因](experiments.md) 设计观测与判据，不把单次轨迹当成首个偏差的充分证据。

比较正确案例与失败案例的最小差异，例如输入、状态、配置、版本或时序。减少变量时保留能稳定触发故障的必要条件。修正环境或复现条件后重跑；如果结果无法归因于当前候选，不能据此判断代码正确或错误。

例如，导入后页面少一条记录。沿路径检查文件解析数量、过滤条件、写入结果和列表读取，先发现解析结果已经少一条，再检查边界行格式，而不是先改页面渲染。

## 用假设和实验区分原因

针对首个偏差列出少量可区分的原因假设。每个假设都配一个预测：若它为真，哪项观测应该变化；若为假，观测会是什么。优先做能以低成本排除多个假设的最小实验，并在执行前确定支持、排除或仍无法区分的判据。

一次只改变会影响判断的条件，尽量复用同一输入和相同环境。记录实际运行版本、配置、观测值及与最终系统的差异。结果若未支持假设，更新假设，不通过堆叠补丁把它包装成已证实原因。并发或概率问题使用受控工作负载和足够观测窗口；单次成功不能证明间歇故障已消失。

难重现失败的关键证据可能丢失，而现有诊断不足以区分原因时，在证据丢失前确定下一次判断需要的最小材料、采集位置和后续使用者。按场景保留必要的输入、运行版本或状态、原始返回与具体冲突，并说明怎样用于对照或回放。根据调查需要约定留存数量、体积或期限，使边界覆盖最终记录与中间产物；采集失败的处理沿用现有失败合同。确认原因后将仍有价值的最小样本纳入回归依据，其他材料按已约定条件回收。

例如，导入漏行可能源于换行解析、去重或数据库冲突。用只含一条末尾空行的最小文件分别观察解析条数和写入条数，可以区分解析与数据库原因。

## 记录旧行为，再区分它是否正确

接手缺少测试或说明的旧代码时，可先写 characterization test（行为刻画测试），记录当前可观察行为，帮助安全地改变实现。这种测试回答“现在发生什么”，不能单独回答“用户要求什么”。

将观察到的行为与当前用户要求、权威接口合同、既有不变量和真实调用方对照。把行为标为已确认合同、实现细节、历史偶然结果或尚未确定。只有有依据的当前合同应约束新实现；历史行为若已知错误，先写目标行为检查并说明旧行为为什么要改变，不能把旧结果固化成正确预期。

若合同或影响无法查明，保留未知并交由掌握要求的负责人判断。不要通过改变测试使目标看起来成立，也不要假定“代码长期这样运行”就代表用户认可。

例如，旧导入器把重复行保留两次。行为刻画测试可以记录现状；产品规则若明确每个外部 ID 唯一，则回归检查应验证只保留一次，并把旧结果作为有意修正的行为。

## 以小步重构保持安全

重构是改善内部结构而保持既定外部行为。先用调用方可观察的结果描述需要保持的行为，并确认现有检查确实覆盖这些行为。对尚无保护的关键路径，先补最小的行为检查或可重放样例。已确认的缺陷修复则以正确目标合同作为依据，不要求保留错误行为。

把结构变化拆成短小、可单独检查的步骤。每步只移动或整理一个明确责任，运行对应检查并查看差异；保持可工作的中间状态，失败时回到最近一次可解释的步骤定位。可以在结构整理与行为修正之间交替推进；每一步都说明是在保持既定行为的重构，还是依据已确认合同改变行为，并运行对应检查，使两种意图和证据可区分。

若变化涉及公开接口、状态语义、权限或主要架构，就超出纯重构的保持条件，按对应合同评估并由其负责人确认。安全小步不意味着为形式制造提交、文档或测试；它要求每一步的行为影响清楚且能检查。

例如，先把订单校验提取为独立函数并确认相同订单结果，再单独修正“数量为零仍通过”的缺陷。前一步保持原合同，后一步依据新确认的拒绝规则改变行为。
