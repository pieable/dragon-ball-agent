# 应急开发与事后整治

本参考用于需要尽快恢复使用或限时补齐必需能力的开发。主文件的应急模式决定优先级；以下方法按现场需要选择，不要求救火前读完或补齐整套事故制度。

## 选择能最快取得结果的办法

先从真实失败、急需结果和当前运行状态判断哪个动作最有把握缩短不可用时间。已有开关、正常版本或局部修正能恢复时直接用，不为了“修代码”先建设新机制。局部补丁、临时脚本、直接实现或人工衔接也可作为明确的应急结果，能力损失和适用条件须可辨认。

回退尤其要区分代码、配置与持久状态。若新版已写入旧版不能读的数据，或发生迁移、对外提交等副作用，单独恢复旧代码可能更坏。只查会改变当前选择的状态与兼容事实，选择可行的回退、兼容性补丁或局部前向修复。恢复入口和撤销方法应对应现场实际版本，不抄一个未核验的通用命令。

暂时硬编码或复制逻辑是否值得，取决于它能否更快取得当前结果。不要为了迎合“应急”故意把简单修复写乱，也不要为了未来通用性延误现在可用。若现场继续运行会持续损坏用户数据，先停止受影响的写入可能比维持进程更有用。

## 最短验证与协作

用一个代表当前必需结果的输入走实际入口，观察最终输出及与改动直接相关的关键状态。复用已有快速检查；没有合适自动化入口时直接作真实使用验证。完整回归、结构评审和长期测试建设按主文件后置或旁路进行，不把被缩减的检查删掉，也不将未验证部分标成通过。

恢复负责人掌握当前有效版本、正在执行的动作和下一个判断点。同一运行状态由明确的执行者维护，其他人可独立取证、验证或记事。动作结果不清时先观察实际状态，尤其避免重复提交、重启或部署。现场协调应随团队大小缩放，不要求个人项目设置企业式指挥、沟通和规划职位。

## 记录要能帮助下一次行动

复用项目现有工作记录或issue，把当前有效状态放在容易找到的位置。记录可以粗糙，但接班者应能回答：

- 现在从哪个入口运行，加载了哪个版本、配置和临时开关，急需结果是否已恢复。
- 尝试了什么、为何尝试、观察到什么，哪些已撤销，哪些仍在生效。
- 临时补丁或绕行位于哪里，依赖和代价是什么，怎样回退或停止使用。
- 尚欠哪些根因调查、验证和结构修复，由谁在什么窗口接续，什么结果算处理完成。

直接引用现成命令、diff、日志和部署输出。短句或一行时间线即可，不要求逐项填表或重复整理已自动记录的信息。在动作后立即追加关键变化；必须先保留的短暂证据和恢复点在动作前取得。交接确认下一位已经掌握当前有效状态，不能只发一长串历史输出。

## 恢复与整治分开完成

以实际使用结果和故障相关的运行周期判断恢复，不强设统一观察分钟数。恢复后停止扩大临时措施，保留必要观察。程序停止本轮运行、活动结束或进入可维护窗口时，接续下面的工作：

1. 根据现场记录核实原因和实际改动，找出正式来源与现场状态的差异。
2. 将遗留项分成应撤除的措施、需正规化的补丁、尚未修复的原因与未完成的验证，按复发风险和维护成本安排。
3. 在适当位置完成结构修复、关键反例回归和必要评审，重新从正常入口验证，防止下一次启动或发布覆盖有效热修。
4. 更新临时项的去向和证据，说明哪些已解决、哪些作为正式方案保留及理由，哪些仍未完成。

用户说“下线后”通常可指本轮使用结束或合适停机窗口，不需要等到软件永久退役。线上继续运行期间，未完成整治留在已有项目入口，不能靠一个“TODO优化”结案。整治按实际风险和收益处理，不因曾是临时代码就全部重写，也不擅自创建新的调度任务。

## 方法来源与适用条件

2026-11-09核查以下一手资料。大型组织的角色、SLA、审批层级和发布设施只在其适用环境使用，未作为个人AI开发的通用前置。把事故缓解方法用于限时补能力，是结合用户目标所作的方法综合。

- [Google SRE：Effective Troubleshooting — Triage](https://sre.google/sre-book/effective-troubleshooting/)：先止血、恢复尽可能好的运行状态，再完成根因调查，保留必要证据。
- [Google SRE：Managing Incidents](https://sre.google/sre-book/managing-incidents/)：现场修改责任、可用的实时记录与明确交接，支持事后查证。
- [Azure：Emergency SDP protocols](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments#emergency-sdp-protocols)：紧急时压缩或调整部分质量与测试门，将后置检查尽快旁路补跑，沿用真实授权。
- [AWS：Ensuring rollback safety during deployments](https://builder.aws.com/content/3F04j2yRAAMBuPSPs50xwXZqg01/ensuring-rollback-safety-during-deployments)：旧代码与新状态可能不兼容，回退需要检查数据和协议条件。
- [AWS：Stage 5 — Respond and learn](https://docs.aws.amazon.com/prescriptive-guidance/latest/startup-resiliency-baseline/stage-5.html)：小团队沿用已有工具，以轻量时间线和具体行动积累经验。
- [Google SRE Workbook：Postmortem Culture](https://sre.google/workbook/postmortem-culture/)：整治行动应有明确对象、负责人和可检验结果。
- [Martin Fowler：Technical Debt Quadrant](https://martinfowler.com/bliki/TechnicalDebtQuadrant.html)：有意识承担短期设计债，并按实际成本判断是否偿还，不能把杂乱天然当作更快。
