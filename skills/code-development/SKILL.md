# 代码开发

把用户要求落实为可以实际使用、并有相应证据的代码结果。工作按取得的反馈推进，研究、设计评审和专项测试由会改变当前结果的未知与风险决定。

## 从实际使用路径开始

从用户要获得的结果和可观察验收路径开始，确认修改范围、必须保持的行为和当前事实。沿实际入口、调用关系、状态与依赖，查到足以解释当前行为和决定下一项改动即可。

把当前要求转成可观察的目标行为和与用途相称的工程验收依据，覆盖会影响结果的接口、状态、可靠性及维护约束。普通技术细节由实现过程补足，产品用途和核心结果沿用已确认要求。

核实用户实际启动或加载的版本及其配置，区分日常入口与隔离候选。任务只要求候选时按候选交付，否则把日常使用路径的更新与验证纳入结果，按已有授权执行。

依赖现有软件平台或组件时，从当前版本的源码或官方资料核实会决定实现的行为，需要确认加载结果时沿真实入口检查。能说明代码怎样进入现有系统、结果如何观察，而且剩余未知不会改变做法时，进入实现。

需要先决定重要接口或架构时，形成足以比较目标行为、主要结构、关键取舍与验收的简短设计，在大规模实现前检查方向。尚有会推翻方向的未知时，用定向调查或最小真实实验解决。局部改动在理解问题后直接修改。安全与边界检查由合同、现有代码或具体操作触发。

成品形态、核心价值或完成标准仍有多种合理解释，而且已有要求不足以决定时，向用户说明具体差异与影响。普通实现选择在已有边界内连续完成。

用户反馈或实现与使用证据使产品用途、完整体验、核心价值、范围或成功标准需要重新判断时，使用 `product-development` 处理受影响的产品决定，再据更新后的要求继续实现。已约定行为未实现且要求仍清楚的局部缺陷直接修复。

需求变化后，先更新已有资料中会误导后续实现的要求和说明，再继续受影响的工作。供后续接手者使用的入口应能直接找到当前有效要求，已经被取代的说明应更新或明确标为历史。是否新增资料按交付部分的条件判断。

## 实现并取得反馈

先取得能验证当前关键判断的最小结果，让代表性输入沿实际入口、核心处理、必要状态和真实依赖产生输出。产品方向尚未确定时，用代表性成品取得用户对核心价值的反馈。随后按行为和集成边界补全要求。切片可以小，但应回答当前最重要的问题，不能用绕开核心问题的样例证明方向成立。

每次变更包含同一行为所需的生产代码、相关验证和必要说明。增加接口同时接通真实调用方。完成关键变更就运行对应路径，普通失败在当前工作中修正，避免全部写完后才首次集成。仍依赖后续结果的细节取得证据后再决定。

每轮实现明确本轮要改变的行为及结果判断依据。取得结果后，判断它是否推进约定的实际使用结果，再决定下一轮行动。构建、测试和工具状态按其实际覆盖范围作为证据。

核心结果失败时，先定位首个阻碍，做能区分普通缺陷和路线问题的最小修正或实验。同一目标下的连续修正结合此前计划和结果判断投入，不能仅按当前一次改动的大小估计范围。局部改动逐渐涉及更多模块、依赖或替代实现时，更新对剩余工作和路线可行性的判断。过程指标通过而用户结果持续失败，或为维持当前方法不断增加补偿和例外、却仍无法推进核心结果时，停止扩大实现。根据结果、剩余成本、风险、可复用部分和切换代价决定继续、缩小或换路。普通缺陷修复持续推进目标时继续处理，既有投入不构成继续理由。需要改变已约定的要求、主要形态或明显投入时，向用户说明依据和影响。发现产品目标、完整体验或成功标准需要改变时，将实现证据带回产品定义过程形成决定。

并发、性能、随机结果、不可逆状态或受限外部服务的验证需要设计观测方式时，读取 [实验与结果归因](references/experiments.md)。普通确定性改动直接使用与故障相称的检查。

## 实现范围

实现复杂度以当前已证实需求为准。优先使用项目和平台已有的能力，也从解决相似问题的成熟方案中借鉴做法，包括采用不同技术的方案。核实其成立条件，选择适合当前项目的部分，补足完成结果所需的实现。现成方案不必整套采用。

一次性操作直接写在使用处，几行相似代码通常比提前创建 helper、utility 或抽象层更合适。不为假设中的未来需求增加配置和兜底。

依据一致的用户要求和项目权威资料实现，避免增加没有需求或证据支持的替代路径。把权威主路径失败、缺失或不确定时改走另一来源并继续产生结果的实现视为兜底。只有当前要求或已经观察到的系统边界失败需要恢复，并且触发条件、结果语义和验证方式明确时，才增加或保留这类路径。

依赖内部代码和框架已经提供的保证，不重复实现同一机制。

新证据与已约定的要求冲突时，向用户说明具体矛盾，由用户决定是否改变要求。当前要求中的信任边界、安全、数据保护、兼容性和可访问性继续保留。

修改只覆盖完成当前结果所需的代码。修复缺陷不顺手清理周边代码，简单功能保持简单，未修改的代码不补文档字符串、类型注解或解释性注释。逻辑确实不直观时写必要注释。

能直接修改代码时，直接完成改动并删除被当前要求取代的路径。确认不再使用的代码直接删除，不留下重新导出、变量改名或 `// removed` 一类兼容痕迹。

## 验证与评审

用能证明目标行为、也能抓住目标错误的证据决定完成。优先复用相关检查，按实际错误的层次选择局部测试、集成检查或真实使用流程。修改后运行受影响的检查，失败时修正。测试应在实现出现目标错误时失败，不能仅重复当前代码的假设。测试预期与真实接口或要求冲突时，先纠正依据。

核心流程首次可运行时，就从约定的正常入口完成一条代表性操作，确认测试入口与实际使用行为一致。涉及可见界面、视觉反馈或完整操作路径时，从首次使用者的视角实际操作，按发现修正受影响部分。验证前核实所需工具和环境可用，缺失时寻找可用路径，无法补足时说明具体缺口。用户明确指定亲自验证或其他验证方式时按其要求。

交付前确认最终采用的证据对应交付候选，后续修改使证据失效时补验受影响部分。完成声明涉及真实模型、宿主、外部服务或完整用户流程时，确认已有该路径的验收证据，缺失时沿该路径补验。代码检查和截图都只证明实际覆盖的范围。

局部、结果唯一且证据充分的改动直接复核。非机械的行为、接口、状态或结构变化，以及范围大、难回滚或证据薄弱的候选，使用 `code-review`，按其中要求确定评审对象、检查候选并处理发现的问题。

自查发现的问题直接修正，证据不足时补足决定结论的输入。自查只作为实现者复核，不称为独立评审。需要独立视角时，可以向用户提议启用 `code-reviewer` 子代理，获得授权后再使用。

证据已经支持全部完成标准，而且没有会改变结论的未知时，结束实现和验证。新增检查应针对具体疑点，不因还能增加覆盖率、日志或测试器能力而继续。确需统计重复的观测按已确定的计划完成。

## 交付

确认交付的是约定入口下能够构建或加载的产物，相关检查通过，失败可诊断，风险需要时可恢复。分阶段发布按有限范围取得运行反馈再扩大，不自行扩大外部影响。

未来正确修改依赖无法从代码和测试恢复的信息时，更新项目已有权威资料，记录仍有效的约束、决定及依据。已否决的路线保留原因与重新判断条件，便于后续据实取舍。缺少入口时用简洁 AGENTS.md 索引资料。影响使用、构建或发布方式时同步说明。普通局部改动不新增文档，资料不把候选写成已生效结果。

交付说明实际可用的结果、关键变更、验证和剩余限制。真实路径受阻时说明停在哪里及其影响，不能以局部通过代替整个任务完成。
