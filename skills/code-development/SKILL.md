# 代码开发

把用户要求落实为可以实际使用、并有相应证据的代码结果。工作按取得的反馈推进，研究、设计评审和专项测试由会改变当前结果的未知与风险决定。

本 Skill 同时供主 agent 和代码 subagent 使用。正文中需要向用户说明、提问或由用户决定的事项，由主 agent 与用户沟通。subagent 将具体事实、差异、影响和所需决定交回直接上级。产品目标、范围或成功标准需要重新判断时，subagent 先交回上级，由主 agent 组织产品判断。

## 从实际使用路径开始

从用户要获得的结果和可观察验收路径开始，确认修改范围、必须保持的行为和当前事实。沿实际入口、调用关系、状态与依赖，查到足以解释当前行为和决定下一项改动即可。

把当前要求转成可观察的目标行为和与用途相称的工程验收依据，覆盖会影响结果的接口、状态、可靠性及维护约束。普通技术细节由实现过程补足，产品用途和核心结果沿用已确认要求。

进入实现时沿用产品过程中与用户确认的使用情景、实例和边界。只有团队自行写出的规格或用户尚未看懂的方案时，不能据此认定重要体验已经确定；会改变当前切片目标或主要形态的歧义交回 `product-development` 核对。普通细节在已确认范围内自主完成，关键事实调查和帮助理解的原型可以先行。

需要用户判断的机制、方案或实现取舍难以直接理解时，使用 `teach-and-explain`，先说明它怎样改变实际操作、结果、成本或后续选择。核心路径首次可用、重要体验发生变化以及交付时，围绕原情景展示实际结果，区分技术行为已验证与个人体验仍待用户反馈。实现者和测试代理的认同不能代替用户的偏好判断。

核实用户实际启动或加载的版本及其配置，区分日常入口与隔离候选。任务只要求候选时按候选交付，否则把日常使用路径的更新与验证纳入结果，按已有授权执行。

依赖现有软件平台或组件时，从当前版本的源码或官方资料核实会决定实现的行为，需要确认加载结果时沿真实入口检查。能说明代码怎样进入现有系统、结果如何观察，而且剩余未知不会改变做法时，进入实现。

需要先决定重要接口或架构时，形成足以比较目标行为、主要结构、关键取舍与验收的简短设计，在大规模实现前检查方向。多个用户决定相互依赖、分别询问会使后续答案反复失效时，把会改变路线的关键问题及其影响集中交给用户；其他未知随着证据逐步解决。尚有会推翻方向的未知时，用定向调查或最小真实实验解决。局部改动在理解问题后直接修改。安全与边界检查由合同、现有代码或具体操作触发。

非平凡功能、跨模块或外部边界的变更、核心状态不变量、高风险变更，以及已有检查通过但用户结果仍失败的任务，在实现前读取 [验收设计](references/acceptance-design.md)。用其中的当前任务规格和验收合同把结果、生产路径、反例和证据对应起来，并按风险决定是否展开完整生命周期。局部且结果唯一的修改直接采用必要部分，不为填写模板增加无用文档。

成品形态、核心价值或完成标准仍有多种合理解释，而且已有要求不足以决定时，向用户说明具体差异与影响。普通实现选择在已有边界内连续完成。

用户反馈或实现与使用证据使产品用途、完整体验、核心价值、范围或成功标准需要重新判断时，使用 `product-development` 处理受影响的产品决定，再据更新后的要求继续实现。已约定行为未实现且要求仍清楚的局部缺陷直接修复。

需求或证据变化后，先更新受影响的当前要求、已有说明、架构判断和验收依据，再继续相关工作。保留仍有效的内容，让接手者能从现有入口找到当前要求，已被取代的说明更新或标为历史。是否新增资料按交付部分的条件判断。

## 开发中的人机协作

需要用户共同判断功能或方案时，先调查并筛选会改变使用结果的选择，用代表性输入、操作情景、对照样例或可运行片段呈现差异。把相关技术机制连接到实际行为、代价和后续影响，帮助用户运用领域经验与使用感受形成判断。材料做到足以解决当前未知即可，普通实现、调试和工程检查由 agent 连续完成。

用户指出结果不合预期或感觉不对时，将原情景、预期结果与当前行为放在一起核对，借助具体操作和对照找出差异。由 agent 继续调查差异来自需求理解、方案假设还是实现行为，再按前述产品判断与局部修复规则处理。把反馈的适用条件和形成的决定带回受影响的规格、实现与验收。

面向用户展示当前可用结果、实际使用过程和会影响选择的机制与差异，提供方便查看或操作的入口。面向执行者保留接口、状态、实现位置、验证证据和剩余问题，使其可以准确接续。两类材料对应同一版本和决定，代码及工程记录按需可查。根据用户参与是否帮助澄清问题、辨别质量和减少返工，调整展示内容与交流时机。

## 进入代码前选择证据和路线

开始新的开发工作时段或恢复持续项目时，在首次修改生产代码前执行 [验收设计](references/acceptance-design.md) 中的“开发前整体检查和证据选择”。先确认当前用户结果、日常入口到结果的完整运行路径、状态和决定的责任归属，以及当前待办在主路径中的位置。多轮决定已经散落、现有理解不能可靠指导下一步时，先使用 `workflow-state-distiller` 恢复当前状态；只看当前现象不足以判断原因、目标或成熟参照时，使用 `xy-axis-thinking`。状态和路径仍清楚时直接沿用，不重复生成说明。

把仍会改变实现方向的未知交给适合的证据来源。客户现实、产品价值、完整体验、范围和成功标准不清楚时使用 `product-development`，通过用户的具体经历或重要取舍形成决定。需要外部成熟方案、标准、同类产品、当前平台资料或反例时使用 `deep-research` 或相应的定向研究。当前代码、配置、宿主、性能、集成或可实现性尚未查明时，先读取实际对象或运行最小本地实验。只有目标行为、主要路径和验收依据已经足以决定修改时才编写生产代码；代码可以实现已确定的决定，不能代替产品判断、外部取证或可行性实验。

高频运行、输入持续增长、引入较重依赖或已有资源问题时，先查清实际消费者需要什么、每次处理多少、多久执行一次，以及主要成本发生在哪里。比较满足同一结果的处理范围、计算次数和依赖范围；需要测量时使用实际规模和可比较的运行阶段，区分内存、显存、发布体积与开发临时占用。把会改变方案的成本依据、约束和关键未知并入当前决定与执行交接，按风险选择必要的检查，不为每项任务增加资源监测或固定指标。

产品结果、责任归属、权威状态来源或执行主路径发生变化时，立即重新选择所需证据，尤其是在新增持久状态、后台进程、调度器、模型职责、重试、兜底、兼容或第二条执行路径之前。按上述要求更新相关资料后，再继续实现。检查要把现状与不受历史补丁约束的最简运行逻辑比较，明确保留、取代、退出和暂缓的路径。原因明确且不改变完整运行逻辑的局部缺陷，简短确认后直接修复；需要改变产品行为、主要架构或明显投入时，先把依据和影响交给用户决定。

## 按任务选择工程方法

进入设计、实现或验证时，按当前需要作出的工程判断读取相应参考。方法用于补足判断与操作步骤，产出并入当前规格、实现或测试；已有依据充分的简单改动直接处理。

- 用户目标需要分解到组件职责、接口或跨组件行为时，读取 [需求分解与设计](references/requirements-and-design.md)。
- 新增或重塑用户界面、接收独立设计结果时，读取 [界面设计交接](../frontend-design/references/design-handoff.md)，把受影响的状态、交互、响应式和内容边界并入当前实现与验收依据；普通局部修改只核对受影响部分。
- 新增或修改持久状态、后台任务、重试、并发写入或恢复路径时，读取 [状态、失败与恢复设计](references/state-and-reliability.md) 中相关部分。
- 需要选择测试依据、依赖替身、契约检查或状态序列覆盖时，读取 [测试方法](references/testing-methods.md)。
- 原因不明的故障、缺少行为保护的旧代码修改或有结构影响的重构，读取 [调试与安全修改](references/debugging-and-change.md)。
- 持续维护的项目缺少可重复执行的真实功能验证入口，或已有操作说明随功能变化失效时，读取 [项目验证入口](references/project-verification.md)。复用项目现有测试与驱动工具，将启动、实例核对、用户操作、结果证据和清理接成实际可运行的路径。

先使用与当前未知有关的方法，再随发现补充。关键判断应落实为接口、状态转换、代码结构或可运行检查，不能停留在方法说明中。

## 实现并取得反馈

在编写非平凡生产代码以前，先建立与风险相称的验收合同并取得修改前基线。合同写清用户或系统可观察的结果、结果实际经过的入口和边界、必须保持或拒绝的不变量、能够推翻完成声明的反例、自动门槛与必要的真实运行证据。缺陷修复、核心合同或容易回归的确定性行为，在可行时先增加能够因目标问题而失败的验收测试，并确认它依据预期原因失败，再修改实现。用户可见界面、真实外部系统、探索性实验或缺少合理自动化入口的改动，先明确等价的手工、集成或观测路径，不为了形式上的先写测试而制造无法证明结果的检查。文档、文案和结果唯一的微小配置修改按风险直接复核，无需强制新建测试。

通过门槛由整体实现负责人或主 agent 掌握。整体任务规格可以随用户决定和新证据修正；阶段进入实现或交给 subagent 后，其结果、范围和门槛在负责人明确更新前保持稳定。把生产代码交给 subagent 时，在委派中写明对应的结果声明、必须通过的测试、重现步骤和完成条件。subagent 可以为自己的实现补充局部测试，但不能删除、跳过、放宽或改写既定门槛来获得通过。如果测试与真实需求、平台接口或新证据冲突，停止针对该门槛的实现，返回冲突证据，由负责验收的 agent 决定是否修改。

先取得能验证当前关键判断的最小结果，让代表性输入沿实际入口、核心处理、必要状态和真实依赖产生输出。产品方向尚未确定时，用代表性成品取得用户对核心价值的反馈。随后按行为和集成边界补全要求。切片可以小，但应回答当前最重要的问题，不能用绕开核心问题的样例证明方向成立。

每次变更包含同一行为所需的生产代码、相关验证和必要说明。增加接口同时接通真实调用方。完成关键变更就运行对应路径，普通失败在当前工作中修正，避免全部写完后才首次集成。仍依赖后续结果的细节取得证据后再决定。

一项结果跨越多个组件时，逐项追踪要求经过的提供方、调用方、状态转换和最终观察点。客户端限制不能代替服务端边界，局部预算不能代替组合后的最终限制，保存成功不能代替实际消费者已读取。实现和验证应覆盖这些连接，不以各模块分别通过推断整体已经成立。

每轮实现明确本轮要改变的行为及结果判断依据。取得结果后，判断它是否推进约定的实际使用结果，再决定下一轮行动。构建、测试和工具状态按其实际覆盖范围作为证据。

核心结果失败时，先定位首个阻碍，做能区分普通缺陷和路线问题的最小修正或实验。同一目标下的连续修正结合此前计划和结果判断投入，不能仅按当前一次改动的大小估计范围。局部改动逐渐涉及更多模块、依赖或替代实现时，更新对剩余工作和路线可行性的判断。过程指标通过而用户结果持续失败，或为维持当前方法不断增加补偿和例外、却仍无法推进核心结果时，停止扩大实现。根据结果、剩余成本、风险、可复用部分和切换代价决定继续、缩小或换路。普通缺陷修复持续推进目标时继续处理，既有投入不构成继续理由。需要改变已约定的要求、主要形态或明显投入时，向用户说明依据和影响。发现产品目标、完整体验或成功标准需要改变时，将实现证据带回产品定义过程形成决定。

并发、性能、随机结果、不可逆状态或受限外部服务的验证需要设计观测方式时，读取 [实验与结果归因](references/experiments.md)。普通确定性改动直接使用与故障相称的检查。

## 实现范围

实现复杂度以当前已证实需求为准。优先使用项目和平台已有的能力，也从解决相似问题的成熟方案中借鉴做法，包括采用不同技术的方案。核实其成立条件，选择适合当前项目的部分，补足完成结果所需的实现。现成方案不必整套采用。

一次性操作直接写在使用处，几行相似代码通常比提前创建 helper、utility 或抽象层更合适。不为假设中的未来需求增加配置和兜底。

新增或收紧运行限制前，查明它依据的用户要求、业务规则或实际平台与资源约束，明确限制作用于哪一层、何时触发以及触发后怎样处理。执行时限、处理数量、输入大小等限制会改变任务能否完成或结果是否完整，不能仅凭习惯、示例或方便测试而设置默认值；把限制做成可配置项也不能代替依据。已有库、框架和模板的默认限制同样核对是否适用于当前用途，开发测试的时限与产品任务的总执行时限分别处理。

把有效限制及触发后的行为纳入当前规格与验收，验证需要超过该限制的正常使用情景是否仍能满足要求，以及触发时取消、失败或部分结果是否按约定处理并清楚反馈。按任务风险选择实际运行或能够验证相同行为的受控检查，不能只用未触发限制的小样例证明完成，也不能把因限制而中断或截断的结果报告为完整成功。缺少依据的新增限制不进入交付；确有约束但会改变已约定结果时，将依据、影响和可行处理方式交给用户决定。

依据一致的用户要求和项目权威资料实现，避免增加没有需求或证据支持的替代路径。把权威主路径失败、缺失或不确定时改走另一来源并继续产生结果的实现视为兜底。只有当前要求或已经观察到的系统边界失败需要恢复，并且触发条件、结果语义和验证方式明确时，才增加或保留这类路径。

依赖内部代码和框架已经提供的保证，不重复实现同一机制。

新证据与已约定的要求冲突时，向用户说明具体矛盾，由用户决定是否改变要求。当前要求中的信任边界、安全、数据保护、兼容性和可访问性继续保留。

修改只覆盖完成当前结果所需的代码。修复缺陷不顺手清理周边代码，简单功能保持简单，未修改的代码不补文档字符串、类型注解或解释性注释。逻辑确实不直观时写必要注释。

能直接修改代码时，直接完成改动并删除被当前要求取代的路径。确认不再使用的代码直接删除，不留下重新导出、变量改名或 `// removed` 一类兼容痕迹。

## 清理旧版本与开发遗留材料

会重复生成较大数据副本、构建或实验产物时，在创建前确定必要数量、可复用条件、归属和回收责任，并将其落实到实际生成入口。根据平台已有能力处理正常结束和中断后下一次执行的残留，保留仍在使用的产物及来源不明的用户内容；不把手工删除一次当作后续重复运行已经受控。

交付前检查本次开发产生、涉及或已被当前结果取代的旧版本、候选、临时备份和实验材料。按当前使用、必要回滚和独立参考价值决定保留范围，不因曾经有用或已经存在就一直累积。仍承担实际用途的版本保留，说明用途和适合清理的条件。

备份按本次变更的恢复需要决定，不默认每次修改或安装都复制完整版本。优先利用已有可靠的恢复来源；确需新增备份时只保存必要部分，明确保留范围和清理条件，避免多份相同或已失效的完整备份持续占用空间。

有用但不值得保留完整版本的材料，先提取未来可复用的思路、关键实现和成立条件。优先记录到已有设计决策或开发笔记，保留必要的代码片段、取舍原因、已知限制和来源，使后续开发不依赖原版本也能理解和采用。只保存有独立价值的部分，不复制整套旧代码或开发经过。

已经失去用途，或有用部分已经提取并核对完整的旧材料，在授权范围内实际清理，同时移除失效的入口和引用。清理前核实准确路径、归属、依赖及回滚需要，保留仍在使用的版本、必要恢复材料和来源不明的用户内容。清理范围围绕本次工作；更广的历史清理按用户明确要求执行。交付时简要说明实质清理结果，以及保留版本或提取思路的位置。

## 验证与评审

### 检查测试是否仍然有效

选择本次验证和新增测试前，专门检查受影响的已有测试。逐项确认它对应的需求或风险是否仍然存在、能否捕获实际错误，以及是否已由其他测试充分覆盖。范围以本次改动和已发现的问题为准，不为局部修改全面清理无关测试。

需求已经取消、路径已经删除或预期已经失效的测试，依据当前要求删除或更新。重复且没有独立覆盖价值的测试合并，保留能说明故障原因、便于定位问题的检查。只复述实现、依赖无关内部细节或已无法捕获目标错误的测试，改为验证可观察行为；没有有效验证目的时删除。先复用或调整现有测试，确有覆盖缺口时再新增。

清理时写明失效或重复的依据，并确认仍有效的关键行为有相应验证。测试失败或维护麻烦本身不是删除理由。涉及已约定验收要求的变化，交由掌握该要求的负责人判断，不能用清理测试绕过未修复的缺陷。交付前复查本次新增和修改的测试，简要说明有实质变化的删除、合并和保留依据。

### 执行验证与评审

用能证明目标行为、也能抓住目标错误的证据决定完成。优先复用相关检查，按实际错误的层次选择局部测试、集成检查或真实使用流程。修改后运行受影响的检查，失败时修正。测试应在实现出现目标错误时失败，不能仅重复当前代码的假设。测试预期与真实接口或要求冲突时，先纠正依据。

改动能否安全成立取决于尚未核实的关键事实时，写明该事实，并沿实际依赖检查符号搜索未覆盖的存储格式、协议、生命周期或下游消费者。按 [调试与安全修改](references/debugging-and-change.md) 构造能推翻它的检查，取得与声明相称的证据后再判断完成。

新增长期保留的测试前，确认预期来自已确认的行为或接口合同，说明它要拦住的具体错误，以及错误重现时测试为何失败。预期仍需通过探索或用户情境确定时，先使用临时检查或真实使用验证，取得决定后再判断是否纳入回归测试。

按声明可能失败的位置选择证据层级：局部计算用单元检查，组件连接用集成检查，HTTP、CLI、数据库、消息、模型提示或浏览器等边界用经过该边界的检查，状态所有权和禁止行为用不变量与拒绝路径，完整用户结果用正常入口。较低层检查不能替代完成声明所依赖的较高层证据；同一证据可以覆盖多项要求时不重复运行。

需要从多个现有测试中筛选本次运行范围时，先识别已约定的必跑门槛。测试数量多或改动影响关系不清时，可把变更、验收合同和测试入口交给 `worker`，由它自行选择并运行相关测试，交回实际运行的命令与结果、未运行的测试范围及理由。`worker` 不跳过既定门槛。遇到要求与门槛冲突、重要影响无法判断或执行环境受阻时，及时交回直接上级。直接上级不逐项审批测试选择，在整合结果和评审时核对遗漏及证据新鲜度。

交付前同时检查事先约定的验收门槛和实现期间新增的局部测试。验收门槛未通过、被跳过或在未处理真实需求冲突的情况下被改弱时，候选不能交付。全部自动测试通过仍只证明这些测试所覆盖的行为，真实入口、宿主、可见界面或外部服务属于完成声明时，还要取得对应的运行证据。

核心流程首次可运行时，就从约定的正常入口完成一条代表性操作，确认测试入口与实际使用行为一致。涉及可见界面、视觉反馈或完整操作路径时，从首次使用者的视角实际操作，按发现修正受影响部分。验证前核实所需工具和环境可用，缺失时寻找可用路径，无法补足时说明具体缺口。用户明确指定亲自验证或其他验证方式时按其要求。

交付前确认最终采用的证据对应交付候选，后续修改使证据失效时补验受影响部分。完成声明涉及真实模型、宿主、外部服务或完整用户流程时，确认已有该路径的验收证据，缺失时沿该路径补验。代码检查和截图都只证明实际覆盖的范围。

交付前逐项关闭验收合同：每个重要结果和不变量都有对应实现位置及有效证据，约定门槛没有未执行、报错、待定或被弱化的项目。检查输出中的零失败不等于所有检查都已执行成功。无法关闭的项目保留为未完成或未验证，并说明它对交付声明的影响。

局部、结果唯一且证据充分的改动直接复核。非机械的行为、接口、状态或结构变化，以及范围大、难回滚或证据薄弱的候选，使用 `code-review`，按其中要求确定评审对象、检查候选并处理发现的问题。

自查发现的问题直接修正，证据不足时补足决定结论的输入。自查只作为实现者复核，不称为独立评审。需要独立视角时，可以直接调用 `reviewer` 子代理进行只读评审。

证据已经支持全部完成标准，而且没有会改变结论的未知时，结束实现和验证。新增检查应针对具体疑点，不因还能增加覆盖率、日志或测试器能力而继续。确需统计重复的观测按已确定的计划完成。

## 交付

确认交付的是约定入口下能够构建或加载的产物，相关检查通过，失败可诊断，风险需要时可恢复。分阶段发布按有限范围取得运行反馈再扩大，不自行扩大外部影响。

未来正确修改依赖无法从代码和测试恢复的信息时，更新项目已有权威资料，记录仍有效的约束、决定及依据。已否决的路线保留原因与重新判断条件，便于后续据实取舍。缺少入口时用简洁 AGENTS.md 索引资料。影响使用、构建或发布方式时同步说明。普通局部改动不新增文档，资料不把候选写成已生效结果。

交付说明实际可用的结果、关键变更、验证和剩余限制。真实路径受阻时说明停在哪里及其影响，不能以局部通过代替整个任务完成。
