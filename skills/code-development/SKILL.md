# 代码开发

交付在日常使用中正常工作、后续容易修改的软件，普通工程选择由实现者判断。结构应让业务规则、状态归属和改动影响容易理解与验证；按实际维护负担选择复杂度，不以行数少、层次多或评分漂亮作为质量目标。

项目文档或指令文件与实现冲突时，先区分它是在描述现状，还是提出仍然有效的要求。描述现状的内容对照当前代码、配置和运行结果核实，按核实结果修正；有效要求用于判断实现是否需要改变。不要仅为迎合可能过时的说明改写正常代码。重要冲突结合相关决定查明后报告；依据不足时保留待确认事项，不自行认定文档或代码必然正确。

下列为常态开发指导。进入应急情境时，先按“应急开发”确定当前目标与工作次序，再按需采用后文方法。

1. 重要业务、个性化体验和主要架构取舍先用具体情境或样例与用户形成决定。产品目标或完整体验仍在形成时使用 `product-development`，方向或上下文需要重整时使用 `workflow-state-distiller`。
2. 确定性缺陷先复现，修复时定位第一个偏离预期的环节，接连几次尝试后主动用 `workflow-state-distiller` 复查前提与继续依据；出现反证及时重判，例外持续增加或投入明显超预期时重查整体路线并报告。
3. 按风险选择自动检查与实际使用验证，运行约定必跑及受影响的检查，依据冲突交负责人处理，不能为通过而降低验收要求。
4. 检查 Git 现状，在任务分支上按可核验的行为经常提交，保留无关改动，用 Git 管理版本，共享远端项目按授权经 PR 与 CI 集成。
5. **复用现有能力与组织状态边界：**
   - **工具与方案复用**：先核对项目已有工具、库和测试/构建入口能否满足当前任务，已有可靠方案直接沿用。需要新能力时，查明领域成熟方案的当前用法与适用条件，用代表性路径检验适配，确认具体缺口后再自行补足，避免自造测试运行器。
   - **规则权威源、状态与错误诊断**：让同一业务规则有明确的权威来源，状态变化有受保护的责任边界，保留足以定位的失败原因和可行的后续动作，不用空捕获或默认成功掩盖错误。新增机制前检查能否消除造成问题的重复规则、无效状态或多余协调；保留清楚的局部实现，抽象应减少实际修改负担。

6. 非机械的行为、接口、状态或结构变更及高风险改动交独立 `reviewer` 按 `code-review` 核验。交接原始要求、准确候选与变更范围、相关调用关系和验证入口；分派时保留共同判断所需的上下文，核对交回的实际覆盖与缺口。按风险从业务、系统状态和真实运行交叉检查，修复后复核受影响部分。
7. 按约定终点交付补丁、候选或正式版本，证据对应交付对象与要求的真实边界，包含安装或部署时核对日常入口实际加载的产物。
8. 先保留仍有追溯价值的决定、失败、技术尝试及证据，再清理本次失效代码和无后续用途的临时产物、更新已有项目资料，报告实际成果、关键决定和未完成事项，长任务使用 `teach-and-explain`，完成标准已满足后结束。


可见界面或完整用户流程需要客户视角验证时，调用 `visual-usability-tester`。派发方从有效需求与日常使用设计代表性情境，提供客户背景与使用经验、目标、起始状态与测试数据、可见成功结果、候选入口和权限，按风险纳入常见使用变化。自主探索不提供逐步点击答案或实现线索；固定步骤回归另行标明。根据报告核对覆盖、安排修正和必要补测。

## 应急开发

用户明确要求应急，或真实中断、迫近的运行损失及明确的现场时限需要先取得可用结果时，采用应急模式。快速确认急需保住的结果、实际运行入口与状态、当前时限和已授权范围，简短说明正在按应急优先级推进。不能只因开发困难或检查难过就自行降低标准。

**尽快可用优先。** 选择最快且有合理成功把握的办法，可以回退配置或版本、关闭非必要功能、降级绕行、局部补丁或临时补齐能力。允许硬编码、重复代码、直接实现和设计债，代码形式、扩展性整理及长期结构让位于当前可用目标。先利用已有可靠入口，不等完整根因、全面复现、生态调研或架构设计做完才恢复。回退前核对会改变选择的数据、协议和外部状态，代码回退不代表已撤销这些状态。

**缩短验证与交付路径。** 完整根因调查、重构、全量回归、完备新测试、普通同步评审和文档整理可并行或在恢复后补做，避免常态步骤重新成为应急前置。从用户实际入口验证必需路径确实可用，并检查与此次动作直接相关的严重副作用，保留观察到的结果。进程活着、编译成功或请求已发送不足以证明恢复。已有授权、用户明确保留的硬要求及数据保护边界继续有效，未跑的检查和已接受的降级如实登记。

**边修边留接续线索。** 沿用已有项目记录，先保住即将丢失的故障证据和必要恢复点，每次关键动作后用短句追加对象与版本、选择依据、操作结果、当前有效状态和临时项。命令、diff与日志直接引用，不先写完整文档挡住救火。来不及整理时先留下原始输出，在第一个稳定间隙补清当前状态。多agent协作明确现场改动负责人，其余可并行调查、核验和记录，避免无协调地修改同一运行状态。

**恢复后转入整治。** 达到最低可用结果后停止继续堆叠权宜改动，说明已恢复什么、仍有哪些限制及未验证项。将临时改动的位置、依赖、风险、回退方法和未完成检查留给接续者，写清处理条件、负责人及完成依据。在本轮使用结束、程序停用或合适维护窗口，依据记录核实根因，按风险和维护成本撤除临时措施、完成必要结构修复、补评审与关键回归，并把有效现场补丁同步回正式来源。可长期保留的简单方案不必为整齐全部重写。“已临时可用”和“事后整治完成”分别记录，不能以写完复盘代替处理问题。

需要进一步判断缓解路线、回退条件、轻量记录或整治安排时，按需查[应急开发与事后整治](references/emergency-development.md)。

## 写代码前确认方向

### 开工检查

开始新的开发时段或恢复长期项目，在第一次修改生产代码前，按 [验收设计](references/acceptance-design.md) 分两档确认（状态和路径都清楚时直接沿用，不重复写说明）：

1. **开发前整体检查与证据选择**（必核 6 项）：用户结果、日常实际入口及加载的版本与配置、完整使用路径、状态与决定的负责人、本次工作的位置，以及最可能改变下一步的未知和区分它所需的证据。
   - 之前的决定散落在多轮对话里、现有理解已不能可靠指导下一步时，先用 `workflow-state-distiller` 恢复当前状态。
   - 只看当前现象判断不了原因、目标或可参照的成熟做法时，用 `xy-axis-thinking`。
2. **任务规格与验收合同**（按风险深入）：遇到非平凡功能、跨模块或涉及外部边界的改动、核心状态不变量、高风险改动，或已有检查都通过但用户结果仍然不对时，进一步读取并使用 [验收设计](references/acceptance-design.md) 中的任务规格和验收合同，把结果、实际路径、反例和证据对应起来，按风险决定要不要走完整流程。局部且结果唯一的修改只取需要的部分，不为填模板写没用的文档。

新需求持续引出例外时，重新判断包含该需求的合理结构，在授权范围内分步迁移并验证。

### 结构要变时

产品结果、责任归属、权威的状态来源或主要执行路径发生变化时，重新确认需要哪些证据。以下改动之前尤其要这样做：新增持久状态、后台进程、调度器、模型职责、重试、兜底、兼容逻辑或第二条执行路径。按上文更新相关资料后再继续。

检查时，先从当前要求写出清楚的运行逻辑，再和现状比较，逐条写明哪些路径保留、哪些被取代、哪些退出、哪些暂缓。

- 原因明确、不改变整体运行逻辑的局部缺陷，简短确认后直接修。
- 需要改变产品行为、主要架构，或会明显增加投入时，先把依据和影响交给用户决定。

## 实现与验证的具体方法

按改动类型选择先做什么：

- 缺陷修复、核心约定、容易回归的确定性行为：有合理自动化入口时，先复用或调整已有检查，确有覆盖缺口或约定要求时再新增；确认检查因目标问题而失败，再改实现。测试的写法、提交顺序、实现中不改测试的做法见 [用测试引导实现](references/test-driven-work.md)。
- 用户可见界面、真实外部系统、探索性试验、没有合理自动化入口的改动：先明确用什么手工操作、集成检查或观测来验证。不为了形式上的“先写测试”写一个证明不了结果的检查。
- 文档、文案、结果唯一的小配置修改：按风险直接复核，不强制新建测试。

从用户的日常使用流程主动找出会自然发生的场景变化，例如多项工作交错、暂停后恢复、输入逐步增加和依赖暂时变慢。按发生可能性、后果和当前机制选择有代表性的场景，覆盖它们连接后的整体结果，避免只验证理想单次操作。技术场景和检查由团队补足，涉及个人偏好或业务取舍的期望再与用户对齐。

### 谁能改验收标准

- 必须通过的检查由实现负责人或主 agent 掌握。整体规格可以随用户决定和新证据修改。但某个阶段已经开始实现、或已经交给子代理后，这个阶段的结果、范围和检查在负责人明确更新前保持不变。
- 把生产代码交给子代理时，委派里写明：要达到的结果、必须通过的测试、重现问题的步骤、完成条件。
- 子代理可以为自己的实现补充局部测试，但不能为了通过而删除、跳过、放宽或改写既定的检查。测试和真实需求、平台接口或新证据冲突时，停下针对这项检查的实现，把冲突的证据交回，由负责验收的 agent 决定是否修改。

### 尽早接通真实路径

先让一个代表性输入沿实际入口、核心处理、必要状态与真实依赖产生输出，检验当前关键判断。新增接口同时接通真实调用方，关键改动及时运行对应路径，普通失败就地修正。绕开核心问题的样例不能证明方向成立。

一个结果跨越多个组件时，追踪提供方、调用方、状态变化和最终观察点：客户端限制不能代替服务端检查，单项没超预算不代表合起来没超，保存成功不代表实际使用者已读到。实现和验证覆盖这些连接。

### 检查已有测试是否还有用

决定本次跑哪些测试、新增哪些测试之前，先检查受影响的已有测试。范围限于本次改动和已经发现的问题，不为局部修改去清理无关测试。逐个确认：

- 它对应的需求或风险还在不在；
- 它能不能抓住实际错误；
- 它是不是已经被别的测试充分覆盖。

然后这样处理：

- 需求已经取消、路径已经删除、预期已经失效的测试，按当前要求删除或更新。
- 重复、没有独立价值的测试合并，保留能说明故障原因、方便定位问题的那个。
- 只是复述实现、依赖无关内部细节、或已经抓不住目标错误的测试，改成验证可观察的行为。找不到有效目的的，删除。
- 先复用或调整现有测试，确实有覆盖缺口时再新增。

对有实质影响的删除或合并说明共同原因，并确认仍然有效的关键行为还有测试覆盖。测试失败或维护麻烦，本身不是删除的理由。涉及已约定验收要求的变化，交给掌握这项要求的负责人判断，不能用清理测试来绕过没修好的缺陷。交付前复查本次新增和修改的测试，简要说明有实质变化的删除、合并和保留的理由。

### 用能抓住错误的检查判断完成

- 判断完成的依据，必须既能证明目标行为成立，也能在目标错误出现时失败。测试不能只是重复当前代码的假设。
- 优先复用相关的已有检查，按错误可能发生的层次选择局部测试、集成检查或真实使用流程。修改后运行受影响的检查，失败就修。
- 测试的预期和真实接口或要求冲突时，先纠正依据，再改代码。
- 改动是否安全取决于一个还没核实的关键事实时，把这个事实写出来，并沿实际依赖检查符号搜索查不到的地方：存储格式、协议、生命周期、下游使用者。按 [调试与安全修改](references/debugging-and-change.md) 设计一个能推翻它的检查，拿到与结论相称的证据后再判断完成。
- 新增要长期保留的测试之前，确认预期来自已经确认的行为或接口约定，写清它要拦住哪个具体错误、错误出现时它为什么会失败。预期还要靠探索或用户情境来确定时，先用临时检查或真实使用验证，定下来以后再决定是否加入回归测试。

## 从可用核心取得反馈

第一个有代表性的可用核心形成后，尽早从用户的日常入口运行，让反馈进入下一轮设计；关键个性化体验或仍可能改变方向的选择，用实际操作、小样或对照请用户判断。普通实现与已明确的局部修正连续完成，不把每次迭代变成审批。交付候选或正式版本仍按约定终点取得相应证据。

用户说结果不对或感觉不对时，把原来的情景、预期结果和当前行为放在一起，用具体操作和对照找出差异。由 agent 继续查清差异来自需求理解、方案假设还是实现，再按上文的产品判断或局部修复处理。把这条反馈适用的条件和形成的决定，写回受影响的规格、实现和验收。

## 资源、限制与产物

### 运行频繁或数据会增长时

程序运行频繁、输入会持续增长、要引入较重的依赖，或者已经出现资源问题时：

1. 查清实际使用者需要什么、每次处理多少、多久执行一次、主要成本花在哪里。
2. 比较能得到同样结果的几种做法，各自的处理范围、计算次数和依赖范围。
3. 需要测量时，用实际规模、可比较的运行阶段，分开统计内存、显存、发布体积和开发时的临时占用。
4. 把会改变方案的成本依据、限制和关键未知，写进当前决定和交接说明。按风险选择需要的检查，不给每个任务都加资源监测或固定指标。

### 运行限制要有依据

新增或收紧运行限制（执行时限、处理数量、输入大小等）之前：

1. 查明依据：用户要求、业务规则，或者实际的平台和资源约束。不能凭习惯、示例或方便测试设默认值。把限制做成可配置项也不能代替依据。库、框架和模板自带的默认限制，同样要核对是否适合当前用途。
2. 写明限制作用在哪一层、什么时候触发、触发后怎样处理。开发测试用的时限和产品任务的总执行时限分开处理。
3. 把限制和触发后的行为写进规格和验收。验证超过限制的正常使用场景是否仍然满足要求，以及触发时取消、失败或部分结果是否按约定处理，并清楚告诉用户。
4. 按风险用实际运行或能验证同样行为的受控检查。不能只用没触发限制的小样例证明完成，也不能把因限制被中断或截断的结果报告成完整成功。
5. 没有依据的新限制不进入交付。确有约束、但会改变已约定结果时，把依据、影响和可行的处理办法交给用户决定。

### 兜底路径和要求冲突

- 按一致的用户要求和项目权威资料实现，不增加没有需求或证据支持的替代路径。“兜底”指主路径失败、缺失或不确定时，改走另一个来源继续产出结果。只有当前要求需要、或者已经观察到某个系统边界会失败需要恢复，并且触发条件、结果含义和验证方法都明确时，才增加或保留兜底。
- 新证据和已约定的要求冲突时，把具体矛盾告诉用户，由用户决定是否改要求。当前要求里的信任边界、安全、数据保护、兼容性和可访问性继续保留。

### 会重复产生的大文件

程序或流程会反复生成较大的数据副本、构建产物或试验产物时，在生成之前定好：需要保留几份、什么情况下复用、归谁管、什么时候回收，并把这些写进实际生成它们的代码或脚本。用平台已有的能力处理正常结束和中途中断留下的残留。仍在使用的产物和来源不明的用户内容保留。手工删一次不等于以后重复运行时已经受控。
