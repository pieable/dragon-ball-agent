# 提示词与规则编写评测案例

这些案例用于维护或重写 `write-instructions-zh`，按改动影响选择，普通提示词任务不加载。检查判断、行动及其信息来源，不能以字数或目录整齐程度评分。保留原始案例作为比较依据；用户授权改变工作设计时，明确说明相应验收变化及理由，不为掩盖遗漏修改答案。

## 通过标准

- 能从用户的选择、纠正和当前系统恢复愿景，而不是只执行最近一句。
- 删除或迁移后，仍有效的重要判断、取舍、权限和完成条件有明确承载；获准移除的辅助说明理由。
- 按责任、直接证据、决策权和稳定信息链分配判断；层级负责协调，不压过直接证据。
- 根据当前文字问题检查防御性否定、过度枚举、过度抽象和长句堆叠；不因模型系列固定增加一套永久流程。共同关系直接表达，需要分别判断或执行的项目保留。
- 生效文本只包含当前指导；演变原因和已废弃路线留在历史材料。
- 复审目标使用时稳定获得的 Base、角色提示词、Skill、合同和配置，不用当前修改会话补足未来缺口。
- 区分文件写入、静态有效、宿主加载和真实行为验证。
- 标题、段落、无序列表、有序列表和嵌套列表表达真实语义关系，不把示例层级当作固定模板。
- 历史中标为当前的规则须结合后续用户决定和实际条件核对，不能仅凭更短或更整齐判断删减成立，也不能将全部历史规则永久冻结。

## 案例一：从多轮纠正恢复整体愿景

用户先要求精简子代理规则，随后指出删掉了上下文隔离、工人局部判断、阶段负责人继续派工和主任务直派中等任务的能力。

期望：先恢复这些选择共同服务的工作结构，再重写连贯的当前规则；不能把四句反馈逐条追加成修改日志式禁令。

## 案例二：判断权随责任分布

一个 `explorer` 需要从大量原始资料中筛出会改变上级结论的证据，但不能决定用户的整体路线。

期望：允许它判断相关性、证据强弱和合同覆盖，同时把用户意图、跨阶段取舍和最终结论留给拥有完整上下文的责任人。下级用证据报告矛盾但不自行夺取整体任务，上级必须处理证据而不能凭印象否定；不能把证据强度和裁决权写成简单高低排序，也不能擅自增加用户没有确认的争议轮数、上报次数或固定流程。

## 案例三：正向机制与必要边界

候选提示词已经说明“执行者按合同完成固定责任并上交证据”；历史上仍多次出现执行者越权改变授权范围。

期望：保留正向合同机制，并加入只针对权限扩大的明确边界。不能机械删除所有否定句，也不能把每次普通执行差异写成禁令。

## 案例四：权威迁移而非重复复制

一条角色专属行为原来同时写在 root Base 和角色提示词中；当前宿主确认该角色总会加载自己的提示词，但 root 不需要据此调度。

期望：把具体行为保留在角色提示词，root Base 只保留调度所需的接口；确认所有目标阅读者都能获得新来源后再删除重复。不能仅因文字相似就合并，也不能为保险永久复制两份。

## 案例五：Skill 的语义与结构共同修改

用户要求修改一个 Skill 的职责，同时新增按需参考资料和前向测试。

期望：使用本 Skill 恢复愿景、判断权和语义边界，使用 `skill-creator` 处理触发、资源组织、元数据和静态校验，并复审最终加载组合。不能让任一 Skill 代替另一方的职责。

## 案例六：生效规则与演变记录分离

历史上某条严格禁令是为修复已经不存在的平台缺陷而加入；新的正向机制已覆盖仍有效的风险。

期望：当前提示词只保留仍会改变行为的机制，旧禁令及其来源进入版本或演变记录。不能为了展示审慎而把过时事故继续写进生效文本。

## 案例七：稳定信息链中的空洞

root 加载了批处理 Skill，但 worker 的配置关闭 Skill 自动注入；root 的委派合同只写“按批处理 Skill 工作”。

期望：识别真实加载链中的空洞，在 Base、角色或合同接口的适当层补上传递机制，而不是把完整 Skill 复制到每个角色，也不能假定 root 已加载就等于下属已获得。

## 案例八：字面覆盖但真实行为没有触发

一条 Base 已经写着“路线证据不足时不扩大投入”，但一次真实高代价任务仍在未经代表性验证的路线中持续实现和评审，最后没有形成可用结果。

期望：不能只因文字相近就判断“规则已经覆盖，不改提示词”。应检查这条规则在稳定指令链中的位置、注意力竞争、相邻规则冲突、责任接口和真实传递，再决定重组、提高作用、修改其他来源或确认问题不在提示词；用户对跨任务代价和结果的说明是强证据，模型提出的技术原因仍须核实。

## 案例九：规则与直接对话例子并存

一个长期角色提示词同时包含明确责任边界和多轮真实对话例子；例子用于校准关系、语气和反应方式，无法被几条抽象形容词等价替代。

期望：保留仍会改变体验的少量差异化例子，并以明确规则处理责任和边界；不能因为例子不增加显式事实就全部删除，也不能把例子中的醒目措辞提炼成普遍口号。规则与例子冲突时，以明确规则和边界为准。

## 案例十：结构方向不是固定模板

用户要求提示词更加结构化，给出多级标题作为方向示例，随后说明标题应尽量表达单一概念，但内容太短时没有必要单独分块。

期望：根据稳定主题、内容独立性和阅读定位决定章节。标题使用自然语言直接说明本节讲什么，使第一次阅读者只看目录就能判断其中的对象、情境或责任；不为简短、等长或形式统一压成无法定位内容的宽泛分类词。段落表达连续关系，无序列表表达并列规则，有序列表只表达真实步骤、阶段、优先级或判断顺序，嵌套列表表达从属关系。调查时需要共同考虑的因素不是天然的执行顺序，不应只因可以编号就改成固定流程。不能照抄示例的层级深度，不能为了标题单一而制造只有几句话的小节，也不能把原本独立的规则用复合标题和分号重新压在一起。

## 案例十一：结构重写后的保真核对

一个成熟 Skill 已有规则储藏库和标注状态的保真并集。候选版本保留了原有标题方向并明显缩短正文，但压弱了直接证据与裁决责任、字面覆盖失效时的诊断、新建提示词的最小当前版本、例子保护、语义等价检查、Git 保护和分层验证。

期望：核对候选是否保留仍有效的重要行为，直接承载或存在可核验的承接关系。对用户已授权去掉的辅助说明依据，恢复意外遗漏的职责和条件。主题相近、宽泛名词和更整齐的目录不能证明等价，也无需机械复制旧结构和旧措辞。

## 案例十二：成熟提示词的局部修改

用户只指出成熟 Base 中一项委派责任存在问题。候选方案为了让全文更连贯，重新生成所有章节，并声称新版本整体表达了相同意思。

期望：默认保留没有问题证据的原文和措辞，只修改会形成目标行为所需的局部机制。只有确认累积补丁已经破坏整体关系时才重组，并在重组前后逐项映射原有规则承担的行为。不能把“不机械打补丁”解释成整体重写，也不能用模型自己的概括证明语义保真。

## 案例十三：模型迭代中的骨干和血肉

一个成熟 Base 同时包含跨模型仍应成立的工作方法，以及为了当前模型、宿主和工具形成正确行为而加入的具体说明、例子和固定协议。候选精简把前者压成抽象短句，又把见过的失败逐项写成清单。

期望：从目的、背景、行动、结果和边界中选择实际需要的内容，恢复需要跨版本保持的骨干，把当前模型才需要的内容作为血肉贴在骨干上。模型或宿主变化时先保持骨干，再复审血肉。以跨版本行为是否一致判断修改，而不以新文本是否更短、更连贯判断。开放现实使用能够迁移的原则，模型需要按项查找、执行或核对时再枚举。

## 案例十四：减少条目没有消除枚举

候选版本把一组较长的场景或判断因素缩成两三个代表词，并据此认定已经完成反枚举审查。目标模型仍需逐项理解这些词，再自行推断它们共同控制什么判断。

期望：先找出这些项目共同影响的判断关系。一个关系能够覆盖整组内容时，直接写清这个关系怎样改变行动，整组项目消失。每项都会独立改变行动，或者模型必须分别处理时，才逐项保留。形式上的缩短不能证明枚举已经消除。

## 案例十五：提炼后只剩抽象词

候选版本为了消除枚举，把一段能够直接指导行动的说明改成“调查问题空间”“控制实际影响”或其他宽泛概括。第一次阅读的模型知道这些词大致正确，却无法从文字本身判断具体何时怎么做。

期望：共同原则既能覆盖未列情境，也要直接说明它怎样改变行动。概括词仍需读者自行补全含义时，恢复足以形成行动的具体说明。必要差异会分别改变行为时直接保留，不能为了文本更短而强行合并。

## 案例十六：把必要枚举误删成一句提醒

候选版本为了减少枚举，把委派合同必须填写的固定字段、会造成不可恢复损失的具体禁止动作，以及一份经过长期使用验证并有意覆盖全部有效选择的工程检查表，都改成了“写清合同”“注意安全”和“优先复用成熟方案”。

期望：保留完整性本身决定正确性的有界枚举。固定字段逐项缺失会造成交接断裂，高风险动作需要明确边界，成熟的有界检查表只有在证明其项目可以由同一个判断等价吸收后才能删减。高风险禁令同时说明其上位风险，防止模型只避开被点名的命令却执行等价破坏动作。开放现实中的非穷尽例子仍应提炼成共同判断，不能因为少数枚举必须保留，就把所有列表都视为合理。

## 案例十七：不能同时改写新稿和原来的检查答案

一个成熟提示词需要修改其中一项行为。维护者为了让全文更加简洁，重新生成了整份正文，同时修改当前规则说明和评测案例，使它们与新稿保持一致，然后据此判断新稿已经通过。

期望：保存原文、规则说明和案例，形成可独立比较的候选，核对授权范围、重要行为去向和新增来源。未获准改变的目标、职责和验收条件保持；获准精简时区分有依据的删除与意外遗漏，不以改写答案掩盖后者。涉及重要结果而理由不清的内容先追查，普通改动无需强制逐条编号或重复请求已有授权。候选核对完成后再同步维护材料，验收要求的改变单独说明依据。

## 案例十八：用户不必亲自找完整批次中的每一个问题

用户在一次大修改后发现某条规则被弱化，说明自己已经无法信任这一批改动，也没有能力逐份读完所有提示词，要求维护者自己检查其他地方是否有同类遗漏、擅自新增或改写。

期望：把这一批全部差异和相同改法波及的位置纳入恢复检查，利用当前规则说明、Git 历史、修改日志、旧版、会话和相关文档逐项核对。能够由材料明确还原的当前规则进入恢复候选，未经确认的新增进入撤回候选；理由只能推断或材料互相冲突时如实标明，只有会改变用户当前目标的歧义才交给用户决定。不能只修用户点名的一句，也不能要求用户继续逐条找出遗漏。

## 案例十九：当前正在生效不等于规则正确

一条规则仍写在当前提示词中，当前规则说明也为它写了理由。继续追查 Git、冻结快照和旧任务以后发现，用户后来已经明确否决这条路线，新的机制也取代了它，但当前正文在一次同步中没有删除。

期望：把正文和规则说明都作为待核对材料，依据后续用户决定、实际结果和机制变化更新状态。已否决或取代的规则进入删除候选；理由不清时调查它保护的结果，关键职责与高代价条件先保留，普通细则按当前需要判断。正在生效、写有理由或位于最新提交都不能单独证明规则正确。

## 案例二十：模型版本变化后的审查

一个较新的 GPT 模型接手维护提示词，认为原来针对 GPT-5.6 的检查与自己无关。它把开放情境缩成几个抽象词，把独立的交接要求合并成长句，并以配置同步成功作为审查完成的依据。

期望：核对这些实际表达缺陷是否削弱判断和交接，恢复具体条件与清楚的职责。模型变化后按当前表现判断专项辅助是否还需要，允许缩减或移除，不将原模型的固定检查永久施加给后继模型。配置同步只证明装配一致，不证明文字审查或真实行为已经通过。

## 案例二十一：稳定骨架与当前功能块

用户维护一份长期学习助手提示词，希望换模型以后继续沿用原有教学设计。当前模型经常提前提示解法，网页宿主又要求用户手动替换学习状态文件。随后模型版本和文件能力发生变化，用户的学习目标与教学设计保持不变。

期望：骨架直接说明帮助用户形成独立能力的教学责任、工作关系和完成标准。当前提问表现和文件更新方式分别由对应功能块补充。模型或宿主变化后，检查这两块的实际需要和承接机制，据此调整，骨架保持。功能块仍然必要时继续保留。文件数量和标题格式由实际使用决定，不擅自增加独立骨架文件或固定模板。

## 案例二十二：具体行动与禁止边界也可属于骨架

一份提示词规定完成前核对用户要求、未经授权不得扩大行动范围，并针对 GPT 的表达特点设置专项审查。维护者需要区分骨架和功能块。

期望：前两项作为基本工作需要的行动和边界可以属于骨架。GPT 专项审查针对特定模型细化通用审查，属于血肉。根据规则承担的基础或补充作用分类，保留仍然需要的功能块，不按文字是否具体、是否禁止或使用时间长短分类。

## 案例二十三：网页项目补充的触发和阅读对象

用户分别要求为 ChatGPT 网页端项目写小说创作指令、给普通网站写开发需求、修改 Codex 的 AGENTS.md。

期望：只有第一项因此加载网页项目补充。按小说项目的持续工作方式产出完整项目正文，不把补充原文交给用户作为项目指令，不强制加入教学演练。其余任务仍按各自适用指导处理。

## 案例二十四：文件存在与网页端实际可用性

编写者在本地读到资料与进度文件，用户希望网页项目下次能接着工作，但尚未提供文件更新能力的证据。

期望：说明需上传或连接的来源，按实际可用信息恢复进度，不将本地路径、当前 Codex 工具或完整历史可见性写成网页端能力。区分生成文件与替换项目来源，无法直接更新时提供完整替换内容及操作交接，不报告已保存。

## 案例二十五：不同项目的长度和互动方式

前一教学项目要求不超过 8000 字并提供独立诊断练习，后一项目用于共同研究产品需求，用户没有要求固定课程、隐藏答案或字数上限。

期望：保持通用骨架与环境适配方法，按后一项目用途选择功能块，不继承前一项目的教学流程和固定限额。前一项目实际计数并保留必要边界，不能靠长附录绕过长度要求。两份正文都允许按当次意图给出相称响应。

## 案例二十六：能力存在但跨 Skill 工作链没有接通

一个长期开发任务已经分别拥有状态恢复、因果参照、产品判断、外部研究、本地实验和代码验收 Skill。各 Skill 单独看都能完成自己的责任，但代码开发每次都沿最后一个待办继续，既不触发前置能力，也不把研究和实验结果更新回当前规格。维护者准备重写状态恢复和研究 Skill，让它们再次强调自己的用途。

期望：检查目标使用时的完整工作链，区分上游触发、能力正文、结果交接和下游消费。保留已经有效的状态恢复与研究 Skill，只在共同规则或调用方增加选择证据的触发，并在接收方明确怎样更新当前决定、规格和下一步。不能因能力没有被使用就重写能力正文，也不能把整个流程复制到每个 Skill。

## 案例二十七：结果未送达与收到后未使用

一个实验 Skill 已生成会改变产品定义的结论，但执行者只把结论留在自己的任务记录里，产品负责人没有收到。另一次实验的结论已明确交给产品负责人，产品规格和下一步行动仍沿用旧判断。

期望：前一种情况修正结果交付环节，让接收方得到结论及其影响。后一种情况修正接收方使用结果的规则，更新受影响的产品决定、规格和行动。两种情况都不因实验 Skill 已经正确产出结论而重写它的正文。

## 案例二十八：培训手册式指导不等于固定步骤模板

用户要求把“按情况调整方案”写得能够指导模型工作。已有材料说明信息不足时先查明关键事实，事实足够时比较方案。另有一句简单而明确的指令只要求保存已确认结果。

期望：前一项补足改变行动的条件、判断依据及必要解释或实例，后一项保持简单。无需让两项都包含背景、反例、预期结果和练习。普通操作不因示例而新增用户审批。已知错误才补足识别或恢复方法，不列举假想故障。

## 案例二十九：语句流畅不能掩盖歧义或改变原意

原文“甲把乙的文件交给丙后，由他确认结果”无法确定确认者。另一条规则要求两项动作同时完成，候选改写为了短句把它们变成先后步骤，并把必要条件留在例子中。

期望：利用可用材料核实确认者，关键歧义仍无法解决时向用户确认。保留同时关系，将必要条件写入对应规则。改写保持原要求、范围及确定程度，审查不以句子变短或另一个模型表示理解作为行为验证通过。

## 前向测试方法

实际运行采用 [真实任务中的行为验证](behavior-validation.md)，本文件的期望只交给检查者。

1. 在独立上下文中提供待测提示词体系和一个真实请求，不提供本文件中的期望文字。
2. 用正常的用户需求要求模型完成提示词编写或修改，并交付候选及必要依据。检查者从实际读取、产物和执行记录判断它是否保留用户愿景、责任、证据、稳定来源和验收要求，不额外提示待测模型逐项自报这些检查。
3. 检查删除、合并和迁移是否保持原有行为，新增边界是否对应具体失败机制。
4. 按拟推广的范围选择未参与改写的留出情境，以及单文件或多层组合任务；不把所有类型作为每次局部改动的必测清单。
5. 每轮只改变一组相关规则，保持模型、推理档位和测试请求不变，再比较行为差异。

## 案例三十：共同规则、描述与正文分开审查

全局 AGENTS 同时提供主 agent 专属规则和主子 agent 共用原则。主 agent 能看到角色描述和 Skill 目录，但某个子角色没有可用的 Skill 目录；另一个 Desktop 启动记录虽有关闭配置却仍显示目录。维护者准备为避免遗漏，把所有共同规则和完整 Skill 再复制到每个角色。

期望：检查实际输入及适用对象，复用已加载的共同规则，保留角色独有职责。角色描述写调用者选择所需的条件，角色正文写被调用者的方法。需要 Skill 的角色获得准确入口及读取要求；不把描述可见当成正文已读，不根据单个配置值断言所有宿主的加载情况。用户要求不用子代理时，由当前主 agent 亲自审查，验证使用已有记录或无模型诊断。

## 案例三十一：具体专业工作被抽象成质量要求

用户要求研究提示词让模型说明顶尖专家会补做哪些未被要求的工作、列出最原始的素材、明确具体方法和工具，并确定用户和模型之外的检验依据。候选把这些内容改成“采用专业方法，重视一手证据，确保结论可靠”，认为提炼出了更通用的原则。

期望：保留四项各自要求完成的工作，把回答用于研究题目与执行。原则说明为什么需要这些工作、如何作取舍。审查时按一个具体研究任务核对模型下一步是否仍需列出遗漏工作、原始材料、方法工具和外部检验。仅有质量形容词不能承接这些动作。该案例说明写法，不要求所有领域的提示词都套用研究四问或固定工具。

## 案例三十二：真实任务表现与提示泄漏

维护者比较旧提示词和新提示词。给新版本的任务特别提示“正在测试原始来源和外部验证”，又让两个版本使用不同模型，最后依据模型自报遵循规则和评审者知道版本身份后的偏好，认定新版本更好。

期望：固定自然任务输入和可比环境，移除额外的评测暗示，保留正常使用所需材料。模型若不是研究变量则保持一致。独立评审使用匿名标签，逐项核对实际打开的材料、执行的操作和交付结果，能运行检查的结果实际核验。多项条件同时变化时分别说明，证据不足以归因于提示词时保留未知。

## 案例三十三：写得清楚但尚未取得专业方法

用户要求创建一份陌生领域的专业分析 Skill。编写者可以写出“收集材料、比较方案、验证结果”，但说不清什么差异影响选择、哪些结论需要实验，以及结果如何改变下一步。

期望：识别方法依据不足，使用 deep-research 查成熟实践、原始案例及关键失败，恢复专家实际观察、取证和取舍的依据。将研究结果用于责任与工作设计，以实际案例或小样检查关键判断。只补齐动作对象、增加专业术语或贴上来源清单不足以完成任务。

## 案例三十四：深读改变了原来的问题

一份方法材料的前半段否定旧解释，中间提出暂时方案，后半段又修正该方案。编写者依据中段摘要准备把暂时方案写成最终操作规则。同一方法的新旧版本还使用相同工具，但评价标准不同。

期望：沿完整论证和实际使用核对问题、解释及修订条件，区别作者转述、异议、过渡和最终主张。研究结果改变原来理解时，修改工作设计并回查受影响的材料。记录工具读取范围只能帮助识别缺口，不能代替判断论证含义。运行指令保留适用条件和有用方法，形成过程留在研究记录。

## 案例三十五：同一动作在不同条件下意义不同

编写者从事故案例提炼“禁止增加空值检查”，想防止执行者在崩溃处遮住上游故障。另一个任务的空值属于合法输入，真正缺陷是没有按约定处理它。

期望：恢复原案例的成立条件，说明如何判断状态是否合法，再决定处理当前状态还是追查产生异常状态的位置。让案例服务于判断关系，不把具体机制写成无条件禁令。对候选作实际情境核对，确认它能区分这两种情况。

## 案例三十六：简单指令与已有可靠方法

用户只要求个人助手默认中文回答、金额保留原币种。另一个任务已有经过核实且适用的专业方法，只需调整执行者分工。

期望：前者直接写清偏好，后者复用已有方法并核对新的责任及结果交接。研究投入取决于当前认识的缺口，不能为满足新章节而无差别重查历史、制造实验或要求用户审批普通选择。

## 案例三十七：一句话需求被扩写成整套流程

用户说“开发 Skill 里没有 Git、PR 和 CI，补上”。候选除了分支、提交和 PR 流程，还加入了“用快照和文件哈希标识候选”“把核验记录保存为文件”等要求，并新建一份十几 KB 的参考文件。

期望：逐条标明哪些内容来自用户原话，哪些由编写者推出。快照、哈希和核验记录属于推出的新记录义务，单独列出请用户确认后再写入。一句话需求带来大量新增时，在改动说明里解释原因。

## 案例三十八：规则积累到需要清理

一个开发 Skill 的正文在一个月内从 16KB 增长到 30KB，每次增加都经过用户确认，但没有任何规则被删除。用户觉得模型执行时越来越抓不住重点。

期望：检查累积规则是否重复、冲突或已失去当前用途，并区分长期工作设计与模型辅助。按重要行为记录保留、合并、删除或按需使用的依据，不设固定删减比例。既有授权内连续完成，新出现的重要取舍再与用户决定；关键条件理由不清时先查明并保留。新稿更短、读起来顺畅不能单独证明删得正确。

## 案例三十九：有能力实现，却没有采用成熟方法与工具

编写者为 Python 项目设计测试 Skill，只要求执行者依据需求写测试。执行者发现项目尚未配置测试工具，便准备自行编写测试发现、运行与报告框架。另一个项目已经使用经核实适用的测试框架，只需补充业务测试。

期望：Skill 提醒执行者查找现有专业生态中的成熟方案，结合项目需要核对适配与实际用法；工具暂时未配置不代表需要自建。现成方案适用时复用，自行构建应有具体未满足需要。已有可靠方案的项目直接沿用，不机械重查工具市场。评估实际选择和产物，不把列出工具名字或重复“复用成熟方案”当成通过；案例中的 Python 测试情境不扩展为所有任务必须采用某个框架。

## 2026-11-03 增补：全局与 description 的职责

用户要求将全局 AGENTS 重写为合作目的、判断原则和必要约定。候选包含“项目开始使用某推进 Skill、复杂解释使用某教学 Skill”，这些 Skill 的 description 已包含相应用途。

期望：删除全局的具名触发路由，在各 Skill description 核对发现入口，保留全局关于接续、解释与用户参与的真实要求。专业方法由 Skill 承接，重要边界不因精简而丢失。若用户另明确删除 Shell 用法，不将其迁为新的强制资源。

失败：把调用表换成自然段继续留在全局；删除调用句时同时删除它承载的用户合作要求；将全局压成缺少判断含义的口号。

## 2026-11-05 增补：恢复核心而不撤销近期认识

用户认为核心提示词 Skill 被过度精简，要求恢复，同时强调最近关于专家方法、description 与工作记忆的新认识必须保留。

期望：核对精简前原文、实际差异与用户后续会话，恢复方法设计和审查的具体判断；保留后来有效的认识与授权边界。大幅重写须逐项标出原行为的准确去向并反查新增来源，不能只凭同主题标题判为保留。既不直接覆盖成历史旧版，也不将原来的具体行动再次压成几句原则；不能为了恢复核心，把已经放宽的固定阈值与模型专项仪式一并强制恢复。

## 案例四十二：版本记录不能由备份替代

用户要求修复全局 AGENTS 与若干 Skill。本机生效文件、独立 Skill 仓库和公开发布仓库并存，部分新改动未提交，另一个新 Skill 尚未纳入 Git。

期望：查明每个目标的版本源和工作区状态，沿相关提交核对原有行为，保留无关改动。无仓库的授权对象建立范围明确的本地仓库；修订经检查后提交并给出标识。明确历史缺口和未提交事项，不以备份及日志宣称版本管理已完成，也不因本地提交而自动发布公开仓库。Git 确实受阻时保全候选并说明阻塞。

## 案例四十三：专家常识与共同约定分别处理

恢复候选同时带回 Markdown 语法示范、测试在目标错误出现时应失败的方法，以及用户共同设计的路线图分叉条件和稳定编号。

期望：省去不增加判断的基础语法示范，保留实际取证方法及用户约定的完整语义；核对后续决定和现有承接，避免旧版整包回滚或把具体方法重新压成口号。description 概括整套方法与用途，不缩成触发词列表。判断依据是内容的实际作用，不能只看长短、难易或是否来自旧版。

## 案例四十四：共同认识集中，专业方法分别维护

用户确认 Skill 应是专家备忘小手册，要求以后从写提示词 Skill 找到共同的编写认识，并检查其他 Skill 是否同步。路线图已有独特的分叉、编号和连线约定。

期望：将共同认识融入本 Skill 的当前指导，后续编写者无需翻旧会话即可采用；核对受影响文件并修正实际冲突。路线图方法仍在所属 Skill 完整承载。不能只追加历史日志而不更新当前指导，不能把专业协议全部搬进本 Skill，也不能为表面统一在所有文件复制同一段话或重写未受影响内容。

## 案例四十五：项目知识与工作入口

一个持续维护的软件项目已有README、项目规格和路线图，agent反复找错正式源码、使用旧启动命令。另一个小说项目已有固定原稿、人设与术语依据。用户要求补足项目AGENTS的指导。

期望：分别保存新接手者应提前知道的项目知识、核实后的操作入口与具体约定，并连接已有详细资料；根目录写共同内容，局部独特约定按适用范围放置。不复制全部规格和进度，不把软件命令模板套给小说，也不在每个目录机械建文件。已有授权内完成并用Git保存。若任务仅为只读检查，报告缺口而不擅自创建文件。

## 案例四十六：减少重复工作与保留专门要点

同一份成熟提示词分别遇到：只改默认语言；修改主子 agent 的 Skill 阅读分工；整体重写；清理一条已有可靠机制承接的规则和一条用户约定的路线图编号规则。

期望：默认语言的局部修改核对变动与有关表达约定，其余用 diff 确认原文不变，不重查装配材料或重列全部规则。分工变化需读有关装配说明，核对受影响的职责和读取关系。整体重写仍逐项对应有效要求，检查条件、力度和例外，核对依据保持原件。清理时利用现有证据判断承接，只有仍影响去留的疑问才试验，不能用一次碰巧正确的输出删除用户的编号约定。维护说明只更新受影响项，保存完整要求、来源、条件、状态与承载；已有失败和约定的改变条件继续保留，不为每条规则编造删弱后果或改变门槛。
