# 提示词编写

## 部署材料

本 Skill 的公共主干与个人材料分开安装。涉及本地样例、档案或维护历史前，读取 [本地依赖](LOCAL-DEPENDENCIES.md)；缺失材料不等同于方法已执行。

## 目标

让提示词在真实使用中持续产生用户期望的行为，并在模型、宿主和工具变化后，仍能以较低的维护成本保持这种效果的一致性。写出的指导既保留长期校准形成的有效经验，也能迁移到未列出的情境。

## 共同认识的维护

本 Skill 集中保存双方已确认的提示词编写与维护认识。维护提示词、全局 AGENTS、角色和其他 Skill 时，先以这里的当前指导作判断。新认识确认后，融入对应正文，使后续编写者无需反复翻会话也能掌握有效方法。修改日志与原始记录保留来路，供有疑问时查证。

各专业的具体方法与共同约定保留在相应 Skill。共同的编写认识变化时，核对受影响的全局、角色与 Skill，将变化落实到各自相关内容，保留仍有效的专业细节。无需把同一套编写规则复制到每份文件。

## 专业能力与工作方法

让目标模型在实际任务中形成用户需要的判断与行动。将执行者视为知识丰富、但相关方法可能记忆模糊、工具使用可能停留在原始阶段的专家。专业知识与实际采用的工作方法、工具环境可能脱节，需要主动查找当今本领域优秀实践者采用的方法与工具，把模糊认识核实为可准确运用的能力。

Skill 的作用包括唤起未被主动采用的专业知识，提醒成熟工作方法，并帮助执行者查证、更新和准确应用。编写时关注模型是否想起合适的方法、是否了解现有工具、能否正确使用；不能因模型具备专家知识，就假定它会自然采用专家的工作方式。准备自建前，先了解现有专业生态，确认已有方案的具体缺口。保留用户要求、背景和边界，普通专业操作由执行者选择，详细指导按实际困难与任务条件补充。

Skill 按专家随身备忘小手册组织：省去基础概念教学、通用语法示范和重复讲解，保留会改变方法选择、准确操作、衔接与验收的关键提醒及必要细节。用户共同形成的具体工作约定须保留到可执行的程度，例如路线图的分叉条件、编号与连线语义；不能以专家已知为由删去。旧版用于核对行为是否误删，不以恢复旧篇幅或逐句搬回为目标，后续有效决定继续采用。

## 按需补充

为 ChatGPT 网页端项目创建、修改或审查项目指令时，读取 [网页端项目提示词编写补充](references/chatgpt-project-instructions.md)，与本 Skill 一起使用。该补充指导编写者适配项目的使用环境，不直接作为用户项目指令。普通网站开发或其他宿主的提示词任务不因此加载它。

为 Codex 编写或审查指令，涉及规则放置、角色分工、能力入口或加载方式时，读取 [Codex 提示词装配与分工](references/codex-prompt-assembly.md) 的相关部分。先区分目标 agent 已获得的正文、用于选择能力的描述和按需读取的材料，再决定规则放在哪里。主 agent 与子 agent 共用的规则按实际加载关系复用，角色正文补充职责差异。普通措辞修改沿用已确认且未变化的装配关系。

## 确定提示词需要说明什么

从以下五个方面还原用户希望模型怎样工作。根据实际需要选择其中的内容，形成提示词的骨架。

- **目的：** 希望通过这块提示词让模型做到什么。
- **背景：** 模型理解任务和作出判断需要知道什么。
- **行动：** 模型需要做什么。
- **结果：** 模型做完后要交付什么，怎样判断已经完成。
- **边界：** 需要保持什么，模型可以行动到什么范围，以及何时停止。

### 骨架与功能块

骨架是整份提示词最基础、最通用、可复用的工作设计，承载总体原则、目标和方向，以及基本工作所需的直接行动指导、禁止事项和边界。这些指导共同说明模型怎样工作、怎样判断和完成责任，并能用于未列出的情境。模型替换和版本迭代本身不改变骨架。用户需要的工作设计发生变化时，才据此调整骨架。

血肉由补充骨架的功能块（function chunk）组成，针对具体模型、环境或任务条件，进一步细化骨架中的规则。每块补充一项完整的判断或行为，可以使用具体说明、方法、例子或协议，其内容和粒度由实际需要决定。区分骨架和血肉时，看规则是共同的基础指导，还是针对特定对象和条件的补充。

例如，本 Skill 的通用审查属于骨架，针对模型实际表达问题的专项检查属于功能块。按当前表现判断它是否仍然需要；模型更新不自动证明它已经失效，也不要求永久沿用某个模型家族的固定流程。

编写时先形成连贯、可直接指导工作的骨架，再根据实际需要补充功能块。每块都应明确它服务于骨架的哪项责任、在什么条件下需要，以及怎样帮助模型实现这项责任。功能块放在对应责任之下或目标模型能稳定获得的位置，具体文件组织服从实际使用方式。

维护时保持骨架的工作设计，分别复审功能块的必要性和适用条件。模型或环境变化后，根据实际表现决定各块继续保留、调整、替换或移除。移除前确认它补充的行为已经由骨架、模型能力、其他功能块或可靠机制承接，或者相应需要已经消失。新增功能块同样应有实际需要，并服从骨架的目标、责任和边界。

## 结构

提示词按稳定主题组织。标题直接说明本节的对象、情境或责任，使第一次阅读者只看目录就能定位内容。

结构应当表达规则之间的统摄关系。先找出一组规则共同服务的责任或判断，把共同原则写在上位，再把需要分别处理的差异放在它下面。不要只把原有句子拆成更多标题、段落或列表。

一个标题优先表达一个完整概念。内容能够独立展开且足以成节时再拆分，较短内容留在更大的自然主题中。

同一个判断能够用一句自然的话说清时，直接写成一句。内容包含多个独立规则或真实的从属、并列、步骤关系时，再用相应结构展开。

标题表达实际从属关系，并列内容用无序列表；有真实步骤、优先级或判断顺序时使用有序列表。

多个独立规则分别写清，不用分号压成长句。章节可以长短不一，使用能够准确表达语义关系的最浅层级。根据实际内容选择需要的形式和层级。

## 编写流程

### 明确本次要改变的表现

先说清楚这次想让模型在哪种情况下改变什么表现。把现在已经做对、需要继续保留的部分也记下来，避免修一个问题时破坏其他效果。

对于已经成熟、规则较多或与其他提示词共同生效的提示词，在动笔前列出本次新增、修改、迁移和删除的规则。没有列入这些变化的当前规则和原文保持不变。用户要求精简、改写表达或重组时，这项改写本身就是本次的变化，被改写部分的原文可以改变，规则意思保持不变，按“写成当前指导”中的改写流程处理。工作中发现确实需要扩大范围时，先补充变化及原因，再修改新增范围。

把用户的一句话需求展开成多条规则时，逐条标明它来自用户原话，还是由编写者推出。推出的新流程、记录义务或限制改变工作设计、权限或用户负担时，说明必要性和后果，与用户形成决定。已有明确授权的内容直接落实。新增内容明显超出原需求时，核对是否把局部需要扩成了整套流程。

用户已经发现某次或同一批修改擅自弱化、删除或增加规则，并要求继续排查时，不再要求用户逐条找出问题。本次范围包括检查这一批的全部差异，以及相同改法可能影响的其他位置。能够从当前规则、Git 和历史材料明确还原的内容直接列入恢复候选。证据冲突或者会改变用户当前目标时，再请用户决定。

用户持续经历自己的任务与结果，模型的认识受当前可用上下文影响。用户跨任务的体验、纠正和实际代价是恢复问题的重要依据；对文件状态、运行记录及失败原因的解释仍需核验。概括与多轮改写可能丢失关键区别和成立条件，应能沿记录回到原始依据，不能用流畅摘要代替核对。

先确认这次的问题能不能靠修改提示词解决。提示词里已经有相关规则，模型却仍然没有形成预期行为时，再判断是规则本身没有说清楚，还是问题根本不在提示词。问题不在提示词时，修改真正出问题的地方。

### 恢复现有提示词的来路

这一阶段是为了知道现有规则为什么存在，避免精简时删掉过去解决过的问题。

修改已经使用一段时间的提示词，先核对覆盖目标文件的 Git 仓库、工作区状态和相关提交，再结合当前文本、修改日志和保真并集（从历代规则中筛出的、仍然有效的规则汇总，见下文“保存修改记录”）恢复规则来路。沿本次涉及的行为查看历史差异；目的、删改原因或已否决路线仍不清楚时，继续查旧版、备份和原始会话。没有提交覆盖的改动明确列为历史缺口。

对于成熟而且关联较多的提示词，维护一份不参与运行的当前规则说明，沿用已有文件，没有时按本次影响建立有关条目。保存每项独立行为的完整要求、精确来源、适用条件、当前状态和承载位置。已有的特殊理由、失败案例和明确约定的改变条件继续保留；不要求逐条预设删弱后的后果或未来允许改变的条件。按本次影响更新有关条目，不重写未变化的记录。建立或补足说明时，沿相关 Git 历史、修改日志、保真并集、旧版、备份和会话追溯；局部修改不以补全其他条目的历史为前提。能够核实的内容写成事实，只能由材料共同支持的结论标明是推断。暂时无法还原理由的现有规则继续保留并标为待确认，不能自行补造原因，也不能因为来路尚未整理清楚就删除。

当前正文、当前规则说明和保真并集都是需要核对的材料，不因正在生效或被标成“当前”就自动正确。根据历史证据分别确认规则仍然有效、只在特定条件下适用、已经迁移、已经被取代、被用户否决、实验失败、暂停、尚未验证或仍然未知。当前规则与后来的用户决定、真实结果或可靠机制冲突时，把它列入修正或删除候选。不能用“现在就在正文里”证明它应该继续保留。

新建提示词没有这些历史，直接从真实用途和代表性例子开始，先写够当前使用的版本，不为假想的未来增加结构。

从当前对话和旧任务中提取未来仍然需要生效的规则和背景，把它们写进目标模型会稳定读取的位置。会话原文和只用于这次判断的例子留在修改材料中。

### 研究并设计工作方法

创建或实质修改承担专业工作的 Skill、Agent 或提示词时，先判断已有认识是否足以设计这项工作。能够写出对象、动作和结果之后，还应能说明关键处观察什么、依据什么选择，以及结果怎样改变下一步。已有可靠方法和案例时复用。只调整表达或明确的长期偏好时，按当前依据直接处理。

方法依据不足时，使用 [deep-research](../deep-research/SKILL.md) 研究成熟实践、原始案例及失败或修订记录。研究题目围绕当前要设计的工作，要求查明专家实际解决什么困难、从哪些材料入手、在关键节点怎样取证和取舍、哪些结果会促使其修正问题或做法。把所得解释及其成立条件带回工作设计，研究发现改变目标或主要路线时与用户形成决定。

选择能体现关键判断的实际任务，沿材料取得、判断、行动和反馈走通相应工作。对已有依据不足以决定的方法，用调查或小样补足。将选定方法安排为执行者的责任，明确所需输入、可用工具、选择依据以及结果如何被接收和使用。保留决定行动的理由，让执行者能够处理案例未列出的条件。某种具体做法只在已查明的条件下成立时，将条件与动作一起写入。

设计时区分能够由结构或工具稳定承担的检查与仍需模型判断的工作，按下一节安排承载位置。例如，读取范围检查可以发现缺失材料，结论是否符合完整论证则需要研究者解释和核对。复用已有机制，检验它是否能发现实际错误，再确定提示词还需指导哪些判断。

把方法的来源、选择理由和试用结果留在修改材料中，生效提示词保留执行者需要的指导。编写者应能用具体案例说明，这套方法怎样帮助识别问题、取得证据、作出选择及根据结果调整。这些认识足以支持当前工作时再写成指令。

### 确定规则放在哪里

一条规则应该写在哪里，先看谁需要读到它，以及谁负责按它工作。

提示词活在目标模型实际收到的整个 agent 调用里，不能作为孤立文件审查。先看完整调用已经通过运行时指令、角色、工具和按需材料具备什么能力。现有机制已经可靠产生所需行为时，不再用提示词重复描述。机制只规定怎么执行而没有决定何时执行时，只保留模型需要判断的触发条件。

机制压缩不是把几条规则合成一句，也不只是把规则迁移到另一份提示词。先判断能否通过一次恰当的工具调用、角色委派或工作流动作直接产生这些规则共同要求的行为。能够时直接使用该机制并删除描述过程的规则。没有稳定的等价机制时保留原有判断，不为缩短文字改写。

- 共同工作方法写入共同读取的提示词。
- 角色自身的问题写入该角色的指令。
- 项目事实和工作方式留在项目层，会变化的配置事实靠近当前配置来源。

一个问题同时来自多个位置时，各处分别修改自己负责的部分，不把整套规则复制到每个文件。

一项工作由多个 Skill、角色或提示词接力完成时，沿实际使用路径检查：上游是否在需要时调用相应能力，能力能否完成自己的部分，产出的结果是否送达接收方，接收方是否据此更新当前决定。需要调用的能力没有被调用时，修改调用方或共同规则中的触发条件。结果已经产出却没有送达时，修改负责交付结果的一端。结果已经送达却没有按其结论更新后续状态、规格或行动时，修改接收方如何使用结果的规则。只有能力本身的判断或动作不足时才修改该能力。各处只修改自己负责的环节，保留已经有效的规则。

全局 AGENTS 主要承载合作目的、关键概念、判断原则、稳定的责任关系及重要约定；用概括而有辨别力的表达组织理解，必要细则保留准确条件。Skill 承载专业方法、经验与按需细节。篇幅由判断所需的信息决定，不以口号化或固定字数代替保真。



全局 AGENTS 不列举“遇到什么就使用哪个 Skill”的具名调用指令；描述不足应修改所属 Skill，不在全局重复补路由。Skill 内确有依赖的资源引用与方法衔接按实际需要保留。

### 项目 AGENTS 的编写

将项目 AGENTS 写成进入该项目的 agent 的工作说明。选择项目特有、后续工作会反复需要，或遗漏后容易误判的信息，使新来的 agent 能理解项目、找到正确材料并开展工作。内容可以是关键背景、资料与成果入口、运行和验证办法、共同约定以及经过核实的项目经验，不必每项任务都会用到。

先查看已有 AGENTS、项目入口、配置和实际工作记录，确认哪些信息已经可靠提供、哪些仍需提前提醒。按当前项目选材，例如软件项目的正式源码、启动与验证入口，或创作项目的人设、术语及原稿依据。保留会改变行动的具体条件和做法，核实路径、命令及适用环境，不把示例或临时尝试写成项目约定。

需要跨会话持续推进或已有共同指导需要时，在项目根目录创建 AGENTS.md，已有文件就在原处维护。根目录承载项目共同知识，某个子目录确有独特约定时再在该目录补充指导，并核对目标 agent 能获得相应内容。沿用项目现有结构，创建与更新仍限于已授权的项目工作，纯问答和只读检查保持只读。

把需要提前知道的信息直接写清。详细设计、历史过程和当前进度保留在对应文档，AGENTS 说明资料用途及何时查阅，避免复制后出现多个不一致版本。全局已提供的共同规则沿用，项目层补充具体情境与差异。

项目变化或实际反馈揭示知识缺口时，更新相关指导，核实旧路径、命令和约定是否仍成立。从一个新接手者要完成的具体任务检查文件：能否找到正确入口、采用适用办法、遵守项目约定并判断结果。按实际作用保留内容，不追求固定栏目、字数或提前填满模板。

### Skill 的整体概括与正文

把 Description 写成整套方法的简短整体概括，让模型在读取正文前，对它怎样看问题、关注哪些关键关系、能帮助形成什么判断或结果有一个可辨认的印象。这可以借用专家凭经验识别情境、联想到已有方法的比喻来设计。用准确而有辨识度的概括唤起相关方法，保留足以让模型在具体任务中联想到它的情境线索；不必穷举触发条件，也不把完整步骤搬进描述。



从正文提炼这套方法独特的思路与用途，避免只写“提高质量、深入思考”等通用愿望。正文展开判断依据、做法和边界，引用资料承接按需深入的细节。只看到描述时，模型应能辨认它能提供什么帮助、与相邻能力怎样配合，并知道何时值得读正文；读完正文后应能实际采用该方法。按这两个层次分别检查，情境识别的比喻只用于指导写法，效果仍由实际选用与执行检验。

### 写成当前指导

提示词以模型能够执行的行动指导为主体。先把希望模型实际完成的工作写出来，说明要处理什么对象或材料、做什么，以及需要得到的结果。原则和规律用于解释这些行动的目的、适用条件和取舍，帮助模型在情况变化时调整做法。已有要求给出了有用的具体行动时，保留这些行动，按需补充判断依据。

例如，研究提示词可以要求“列出该领域顶尖专家还会做哪些用户未要求的工作”“指出他们会从哪些原始素材入手”“写明具体方法和工具及其用途”“确定由什么外部证据检验结果”。这些要求分别让模型完成实际工作。改成“采用专业方法，重视一手证据，确保结论可靠”会丢失原有动作。提炼共同原则时，核对这些工作是否仍被明确要求执行。

编写时，把阅读提示词的模型当作一个有不错理解能力的人：

- 使用清楚、直接的语言，让第一次阅读的模型能够理解这项工作的目的、需要采取的行动，以及判断结果的依据。根据实际需要补足说明，不要求每条规则都重复写一遍目的、步骤和结果。
  - 改写前先确认原文要表达的意思。原句存在多种解释时，根据上下文和已有材料查明。仍会影响行动或权限的关键歧义，向用户确认后再改写。保持原有要求、适用范围和确定程度。
  - 把动作和对象写清楚，直接说明谁在什么情况下做什么。例如，写“比较候选与当前版本，检查原有权限边界是否保留”，比“进行一致性检查”更容易执行。涉及多个角色时，写明各自负责的动作。只有执行者已经明确时才省略。
  - 按行动之间的关系组织句子。一句话围绕一项主要指令展开，先后执行的动作按顺序写，需要同时完成的动作放在一起并说明关系。与动作直接相关的结果要求紧跟该动作。句子是否需要拆开，取决于能否准确理解，不机械规定中文字数。
  - 把行动前必须知道的条件放在相关动作之前。条件影响不同选择时，说明它怎样改变行动。已有规则已经说清的条件可以直接引用。目的有助于选择行动时先说明目的，帮助理解动作的原因放在相关动作附近。安排信息时，以模型何时需要它为依据。
  - 让要求、解释和例子各自承担清楚的作用。要执行的动作、必须满足的条件和结果要求写在对应规则中，并放在容易找到的位置。解释说明为什么这样做，帮助模型在情况变化时继续作出合适判断。例子展示规则怎样应用。执行所必需的要求不能只藏在例子或附注里。
  - 用具体情形讲清判断。难以理解或容易误用的规则，可以接一个简短情形，说明面对什么问题、依据什么作出选择，以及怎样处理。例子只补足规则尚未说清的部分。简单指令直接写清即可，不为每条规则统一添加背景、反例和讲解。
  - 对已有证据表明容易出错的环节，说明怎样识别偏差，以及可用的检查或恢复办法。说明的多少以帮助执行者继续正确工作为准。
  - 保持名称和指代一致。同一个对象使用同一个名称，确需使用简称时先说明对应关系。“它”“这个”“当前版本”等说法可能指向多个对象时，写出具体对象。专业术语能准确表达且目标模型能够理解时可以保留，不用更抽象的词替换已经清楚的表达。
- 只写模型在实际使用时无法从其他地方可靠知道，或者值得长期提醒的内容。例如用户确认的长期偏好、目标模型不会从其他地方看到的项目规则，以及一旦忽略就会造成高代价的权限边界。
- 修改范围按“明确本次要改变的表现”处理，编写者不能自行把局部修改扩大成全文重写。发现原文本身过于抽象、冗长或结构混乱，需要超出已授权范围改写时，向用户提出建议，取得同意后再按下面的改写流程处理。
- 用户要求精简、改写表达或重组时，可以改写原文，按以下流程进行：
  1. 在独立候选中改写，不直接覆盖当前能用的版本。
  2. 把本次获准改写的原文逐条拆成规则并编号，为每条标出它在候选中的位置，并从候选中引一句原文作为证据。局部改写只映射该部分并检查关联规则；整体重写完整映射仍有效的要求。
  3. 按下文“通用审查”核对候选，包括原有行为去向、关联规则及新增来源。
  4. 主 agent 核对原文、对照与候选；已有明确授权的恢复或改写在核对后落实，新的重要语义取舍先与用户形成决定。
  两句话看起来相近时，也要确认它们实际管的是同一件事再合并。当前结构确实无法承载已经确认的变化时，同样按这个流程重组。
- 先判断一组项目是开放现实中的例子，还是完整性本身会决定正确性的有界规则。开放情境通常列不完，应提炼它们共同影响的判断，并写清这个判断怎样改变行动。每项会独立改变行动、固定合同或检查表必须逐项填全、遗漏具体高风险边界会造成重大损失，或者一份经过验证的成熟清单有意穷尽了有效选择时，保留明确枚举。高风险的具体禁令同时写明它防止的后果或上位机制，避免只列出一种写法却漏掉等价危险动作。不能仅因一组项目“很重要”就保留列表，也不能为了缩短文字把完整协议压成模糊概括。
- 优先写希望模型怎样做。正向指导仍然管不到明确边界，或者同一个问题在正向规则下反复出现时，再增加只针对这个问题的禁令。
- 普通、容易纠正的选择给模型发挥空间。错误代价越高，规则写得越明确。措辞力度跟证据和风险相称。没有写明的普通选择由模型在已有目的和边界内决定，也不会扩大权限。
- 难以只靠规则说清楚的语气、关系或感觉，可以附上少量真实例子。例子帮助模型理解规则怎样使用，适用范围仍由明确规则和边界决定。

### 通用审查

通用审查检查提示词本身有没有写对、写全和写在正确的位置。局部修改审查变化部分及受影响的关联规则，未修改部分用 Git diff 核实原文不变，无需重新逐项列出全部规则去向。修改影响全文的原则、结构或读取关系时，扩大到相应影响范围；整体重写完整核对仍有效的要求，已被用户指出失去信任或存在遗漏的批次，按“明确本次要改变的表现”所定范围全面检查这一批全部差异及相同改法波及位置。以下检查在这个范围内进行：

- 按实际使用情形阅读候选，检查模型能否明确判断执行者、行动条件、具体动作及必要的结果要求。检查顺序、同时发生的动作和条件分支有没有写清，名称和指代是否一致，以及执行所必需的信息是否只出现在解释、例子或附注中。缺少判断依据时补足依据，一句话承担过多关系时按这些关系重新组织。不要只凭句子短、标题齐全或措辞正式判断它容易执行。

- 对照修改前列出的变化逐项检查候选。变化部分的每项原有有效行为都由候选中的准确位置继续承载，或者属于已经确认的迁移、删除或取代；同时核对关联规则的条件、权限和职责是否仍一致。获准改写的部分核对“写成当前指导”中建立的逐条对照表。
- 反向检查候选中的每项新增行为和实际差异。它们必须来自已经确认的变化，或者是落实该变化不可缺少的文字。找不到来源的新增、删除和重写全部撤回。由编写者推出的新流程、新的记录或备份义务、新文件和新数字标准，必须已经单独列出并取得用户确认。
- 检查骨架是否完整表达可复用的工作设计，各功能块是否补充对应责任并保留其适用条件。模型或环境适配应落实在相关功能块中。涉及骨架的变化必须能够追溯到用户工作设计的变化。
- 新版本应当让第一次看到它的目标模型在真实任务中也能照着做，并从提示词本身获得所需说明。文字是否容易理解由人工复审，行为是否正确留到实际使用验证。另一个模型只读后表示能够理解，只能作为文字层面的参考。
- 检查是否使用了生造词或含义不稳定的概括词。目标领域已有、含义明确而且目标模型能够稳定理解的术语可以直接使用。其他词改用普通语言，必要时在首次出现时说明含义。
- 文件变短、目录更整齐或新文字读起来更连贯，都不能证明原来的效果还在。只有所有需要这条规则的模型都会稳定读到新位置时，才从旧位置删除。

- 对承担专业工作方法的指导，用实际案例检查关键观察、取证办法、取舍依据和反馈如何改变行动。方法依据不足时回到研究与设计，表达不足时补足指令。用会改变选择的条件变化检查适用范围，确认具体做法和案例没有被扩大成无条件要求。

### 表达问题的专项检查

通用审查之后，根据候选实际出现的问题使用以下检查；保留具体判断方法，不因模型家族固定另走一套永久流程。

- **防御性否定：** 逐句查看“不要”“不是”“不等于”等否定写法。正面说明已经足够时，直接写希望模型怎样做。仍然容易混淆的边界和高代价错误，保留明确而且范围窄的禁令。
- **过度枚举：** 看模型是否仍要逐项扫描开放式例子才能作出一个共同判断。按“写成当前指导”中开放例子与有界规则的区分，判断应提炼共同判断还是保留具体枚举。减少项目数量、把列表改成一整句，或把完整协议压成抽象词，都没有解决问题。
- **过度抽象：** 按一项实际任务读候选，指出模型接下来要处理什么材料、完成什么动作、交回什么结果。只能找到“专业、深入、合理”等要求而找不到相应工作时，把缺失的行动写回正文。对照改写前后的具体要求，检查原来要查明、列出、比较或验证的事项是否仍被明确要求完成。能够帮助理解和判断的原则、必要差异及例子继续保留。
- **分号长句：** 检查全文是否使用分号连接规则。同一个判断写成一句自然的话。内容承担不同责任时，按真实的统摄、从属、并列或步骤关系重新组织，不用分号代替结构。

### 验证实际效果

有可用环境时，让目标模型或实际宿主使用修改后的提示词。任务风险越高，验证越接近真实使用。

需要判断提示词修改是否改善实际行为时，读取 [真实任务中的行为验证](references/behavior-validation.md)。先确定可观察的成功行为，再让待测模型在正常任务输入下工作。比较版本时保持任务、模型和环境等条件可比，依据实际产物与执行记录判断变化。检查模型是否复述规则不能替代它是否完成了相应工作。

专业工作方法的验证还要检查实际结果：模型是否发现关键问题、取得能区分解释的证据、作出有依据的选择，并在结果不支持原判断时调整行动。按方法适用范围选择任务，检查条件变化后是否仍能作出恰当判断。由原始材料、实际操作和产物核对这些表现，避免只检查步骤是否出现。

暂时不能实际试用时，只完成文字审查，并明确告诉用户验证停在这里。文件已经写入、宿主已经加载和模型真的按预期工作，是三个不同的结果。

### 清理积累的规则

规则积累出现重复、冲突、失效或理解负担，模型与宿主变化影响原有方法，或者用户指出提示词太长、太抽象、效果变差时，复查相关规则。清理围绕实际问题，不设固定篇幅、增长比例或删减目标。

复查时逐条回答三个问题：

1. 这条规则针对的问题现在还会出现吗？查它在当前规则说明和修改日志里的来源。
2. 这条规则的作用是否已有可靠机制承接，或已被用户后来的决定改变？依据现有记录和实际证据判断；仍有会影响去留的疑问时，再选择针对性的比较试验。用户共同约定按其有效决定保留，一次去掉规则后的成功表现不足以证明可以删除。
3. 它和其他规则重复吗？

按回答记录保留、合并、按需使用或删除的依据。合并和删除核对原有行为去向，已有授权内连续完成，新的重要取舍与用户形成决定。理由暂时查不清时先追查它保护的结果；关键职责和高代价条件先保留，不把未知直接解释为无用。

### 保存修改记录

生效提示词只写当前应该遵守的指导。仍然帮助模型理解和取舍的原因留在正文，只用于解释某次修改的历史原因写进修改日志。

已有规则储藏库保存历代规则、来源和当前状态，保真并集汇集仍然有效的规则语义；沿用现成记录，维护深度服从本次影响，不为普通修改另建一套记录制度。

一次修改开始后，先把修改前的生效正文、当前规则说明和评测案例当作检查新稿的答案。新稿检查完成以前，不先改这些答案来配合新稿。确认新稿没有漏掉旧规则，也没有加入未同意的新规则后，再让新稿替换生效正文，并更新规则说明和评测案例。

创建或修改提示词、全局 AGENTS、角色和 Skill，必须使用 Git 管理版本。先确认实际生效文件与版本源的对应关系，沿用覆盖目标文件的现有仓库；没有仓库时，在授权对象的明确范围内建立本地仓库，不在已有仓库内嵌套建库，也不把整个用户目录纳入管理。

修改前检查工作区与暂存区，确认原状态可恢复，保留无关改动。修改后核对实际 diff，完成必要检查，将本次变化及配套依据提交为可追溯版本；提交说明写清改变的行为，交付时给出提交标识与未提交事项。历史漏提交如实记录，当前补交不能冒充当时已有的版本。

备份、哈希和修改日志补充 Git，不能代替提交。确因权限或环境无法使用 Git 时，先保全原件与候选，说明尚未完成版本记录及原因。生效副本、维护仓库和发布仓库分别核对；本地提交不自动授权推送远端或公开发布。

本 Skill 影响后续提示词体系的维护。维护或重写它时，当前主 agent 亲自完成语义判断和正文修改，按本次影响读取 `RULE_RATIONALE.md` 的有关条目、`references/eval-cases.md` 的对应案例及相关依赖，让用户能看到关键变化及依据。全面恢复或整体重写时完整核对相关原始依据和仍有效要求。其他 agent 可作只读取证、独立审查或机械核对，不代写核心正文。每次只改已确认变化所需内容；授权范围内连续完成，改变基础工作设计或存在重要未决取舍时再与用户形成决定。普通提示词任务不因此读取这两份维护材料。
