# 实现范围与复杂度

当候选增加抽象、配置、兜底或重构时，检查它们是否支持当前约定结果，以及引入的维护后果。

**实现范围和复杂度：** 检查改动是否复用了现有可靠机制，新增代码是否只填补当前结果所需的缺口。为未来需求增加的抽象、配置、兜底和与当前目标无关的重构，会扩大维护面而没有支撑本次结果时，作为问题报告。

沿实际消费者、调用关系和生命周期判断新增机制的必要性。已有可靠能力可以满足结果时，核对候选是否无依据新增竞争实现。整体结构变化仍按当前目标和已接受设计判断，局部简化也需要保持合同要求的保护、恢复与公共行为。

局部改动可能放大既有结构风险时，检查实际状态是否有多个写者、内部模块是否能被调用方直接导入、相关清单是否需要在多处手工同步，以及调用方是否必须了解内部阶段才能正确使用接口。只有能指出具体后果时才报告，例如状态或注册遗漏、顺序错误、兼容负担或不变量失守；这些结构特征本身不作为风格门槛。

每次兜底专项的固定责任、判定与报告要求继续按[Skill入口](../../SKILL.md#兜底路径专项审查)执行。
