# Code Review

审查的目标是判断本次变更能否安全交付，而不是逐行挑错或替作者设计产品。先恢复实际变更和它必须满足的合同，再用与风险相称的深度取得证据。

## 评审对象和权限

评审结论只覆盖当前候选变更和已经约定的要求，用于判断该候选能否合入或交付。它不代表整个用户任务已经完成，也不改变用户目标、产品路线或其他部分的设计。

开始前确认已有材料能够确定准确的基线和候选、变更应当产生的可观察结果、已接受的设计或约束、实际差异，以及已经取得的测试和运行证据。缺少会改变结论的内容时，补足材料或者给出“证据不足”，不猜测作者意图。

## 审查主干

1. **确定对象。** 核实比较的基线与候选版本、未提交改动和实际差异。目标变化后重新建立范围。只读足以理解设计的周边代码，不把一次审查扩展为全仓库审计。
2. **恢复合同。** 读取会决定结论的项目规则、接口、测试、文档、设计记录和调用方。区分已证实事实、作者主张与尚未验证的假设。
3. **判断需求、设计和集成是否成立。** 对照当前要求，检查候选是否漏掉必需行为、只完成一部分、产生相反结果，或增加没有要求且会改变结果、风险或维护负担的内容。确认设计和真实调用方能够共同实现目标行为，再深入局部细节。
4. **按实际后果选择检查。** 优先检查正确性、必需行为、数据保护、权限和生命周期，再考虑可维护性与风格。根据变更实际触及的机制深入相关风险，不机械跑固定清单。
5. **验证证据强度。** 核对证据是否对应当前候选，以及测试能否在目标错误出现时失败。预期应来自要求和真实接口，不能只复述实现或依赖作者自述。测试、构建和静态检查只能证明各自覆盖的层级。任务要求真实宿主、加载器、界面、外部服务或模型调用时，确认是否已有该路径的可观察证据。没有时标明未验证，不把代理指标说成完成。
6. **作出评审结论。** 根据实际问题和证据强度，按下文的结论标准与报告要求交回结果。

局部、机械且结果唯一的改动可以轻量执行上述流程。功能、接口、状态或系统结构变更必须完成足以判断整体方向的审查。

## 兜底路径专项审查

把权威主路径失败、缺失或不确定时改走另一来源并继续产生结果的实现视为兜底。每次评审按以下顺序检查候选新增、扩大或依赖的兜底：

1. 它处理的失败是否由合同要求或真实证据支持。
2. 项目、平台或框架是否已经提供同等机制。
3. 触发条件、结果语义、权威来源和验证方式是否明确。
4. 它是否会隐藏主路径失败、改变结果含义、重复副作用或与其他路径竞争。

缺少判断兜底必要性或正确性的材料时，先补足决定性证据，仍无法判断时给出“证据不足”，不据此通过交付。证据表明兜底没有必要或不满足上述条件时，列为阻塞问题，要求删除、收窄或修复相应机制。合同要求的安全、数据保护和恢复能力继续保留。

评审交回中单列这项结果。没有发现时明确说明。

## 评审结论

- **可合入：** 声明的评审范围内没有阻塞问题，而且证据足以支持该范围的正确性和交付声明。
- **要求修改：** 有事实和影响支撑的问题表明合同没有满足，或者当前候选不能安全合入或阶段交付。
- **证据不足：** 缺少准确评审对象、决定性合同、相关实现或与声明相称的验证证据。没有发现问题不等于证据充分。

先说明评审结论和实际评审范围，再单列兜底路径审查结果，随后按严重程度报告可操作问题。每项问题写明简短标题、准确文件和最小必要行范围、触发条件或证据、实际影响及需要纠正的机制。跨文件问题说明涉及的调用关系或共同机制。

只报告本次改动引入或暴露、作者可纠正且有事实和影响支撑的问题，把阻塞问题与非阻塞建议分开。纯风格偏好、没有实际影响的推测和无关旧问题不阻塞交付，代码的产生方式不改变标准。没有发现阻塞问题时，仍说明决定结论的证据、残余风险和未验证路径。

候选在评审后发生可能影响结论的变化时，重新确认基线和差异，并复审受影响的范围。不为无关变化重复整个审查。

## 常见风险的检查方向

- **异步、回调、子进程或释放：** 追踪创建、发布、取消、报错和清理。检查竞态、重复回调、所有权和销毁后的工作。
- **接口、配置或权限：** 同时追踪提供方与所有调用方。确认默认值和公开能力有当前消费者或明确合同支撑，并沿拒绝路径检查所有可执行入口。
- **状态、缓存或派生视图：** 确定权威来源、更新时点、所有通知与读取视图。防止旧值、借用值或失败状态被当作成功结果。
- **agent prompt、工具 schema 或 transcript：** 把模型可见文本和参数当作行为协议，核对模型实际收到的提示、schema、结果和诊断，并用 snapshot 或真实链路验证适用部分。
- **加载、注册、CLI 或外部集成：** 关注实际发布入口，而不是只测试手工组装的函数。检查导出、配置、注册和失败诊断。
- **边界与输出：** 对长度、字节数、批量、异常输入和包装层，检查限制是否覆盖最终发出或保存的完整结果。
- **项目可接续资料：** 未来正确修改依赖无法从代码和测试恢复的稳定信息时，检查项目权威资料是否能够被后续任务找到，并且与最终实现一致。缺失或失真会误导维护时作为问题报告。普通局部改动不要求为形式新增文档，任务流水也不充当项目资料。
- **文档和可见文字：** 核对配置、默认值、错误、事件和公共行为是否同步。逐项判断可见文字是否帮助使用者识别状态、作出判断或采取行动，避免把提示词、需求理由、验收解释、设计自述或实现辩护当作产品内容。产品语义需要由结构和行为保持时，不要求把合同原句显示出来。
- **实现范围和复杂度：** 检查改动是否复用了现有可靠机制，新增代码是否只填补当前结果所需的缺口。为未来需求增加的抽象、配置、兜底和与当前目标无关的重构，会扩大维护面而没有支撑本次结果时，作为问题报告。

不要求为每一类风险制造测试或意见。只在本次改动触及它且证据会改变合入结论时深入。

## 审查方式和边界

依据技术事实、项目规则和可复现证据判断，作者对正确性的自述不能代替验证。Astra 检查自己的修改时明确这是自查。

需要独立视角时，可以向用户提议启用 `code-reviewer` 子代理，获得授权后再使用。独立评审者按本 Skill 的标准检查，具体作用范围、只读权限和向上级交回结果的责任由其角色指令与任务合同限定。

用户只要求审查时保持只读，不提供补丁，也不重新决定用户目标或产品方向。已授权开发或修复任务中的自查发现问题时，在原范围内修正并重新验证。

已被可靠自动检查完全覆盖的纯机械问题不重复报告。评审发现可以用技术证据反驳，未经修复、证据反驳或用户明确改变要求的阻塞问题不得被静默忽略。
