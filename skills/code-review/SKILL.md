# 代码与文档评审

审查的目标是判断本次变更能否安全交付，而不是逐行挑错或替作者设计产品。先恢复实际变更和它必须满足的合同，再用与风险相称的深度取得证据。

## 评审对象和权限

评审结论只覆盖当前候选变更或指定文档及已经约定的要求，用于判断该候选能否合入或交付。它不代表整个用户任务已经完成，也不改变用户目标、产品路线或其他部分的设计。

代码候选评审开始前确认已有材料能够确定准确的基线和候选、变更应当产生的可观察结果、已接受的设计或约束、实际差异，以及已经取得的测试和运行证据。缺少会改变结论的内容时，补足材料或者给出“证据不足”，不猜测作者意图。单独核查已有文档时，明确文档对象、适用版本或核查时点，以及其重要主张的正确性依据，按相关内容补足实现、决定和验证材料。

## 审查主干

以下主干用于代码候选。纯文档任务按“文档正确性与进度同步”章节从用途、要求和原始依据开始核查，再按同一结论标准报告。代码、测试和运行记录按文档声明的需要取证。

1. **确定对象。** 核实比较的基线与候选版本、未提交改动和实际差异。目标变化后重新建立范围。只读足以理解设计的周边代码，不把一次审查扩展为全仓库审计。
2. **恢复合同。** 读取会决定结论的项目规则、接口、测试、文档、设计记录和调用方。恢复用户或系统可观察的结果、生产路径、必须保持或拒绝的不变量、已约定反例和通过门槛。区分已证实事实、作者主张与尚未验证的假设。
3. **判断需求、设计和集成是否成立。** 对照当前要求，检查候选是否遗漏必需行为、只完成一部分、产生相反结果，或增加未经确认且会改变结果、风险或维护负担的内容。先找出安全交付依赖的关键事实及权威实现位置，再追踪受影响行为从入口、调用方、状态与数据、外部边界到结果的关系，包括受影响但未出现在 diff 中的消费者、注册、发布和资料。对符号搜索难以覆盖的协议、存储格式、读取时序和库版本行为，沿实际实现核对。逐项追踪重要结果和不变量是否有实现位置及对应证据，确认设计和真实调用方能够共同实现目标行为，再深入局部细节。
4. **按实际后果选择检查。** 优先检查正确性、必需行为、数据保护、权限和生命周期，再考虑可维护性与风格。根据变更实际触及的机制深入相关风险，不机械跑固定清单。
5. **验证证据强度。** 核对证据是否对应当前候选，以及测试能否在目标错误出现时失败。预期应来自要求和真实接口，不能只复述实现或依赖作者自述。对拟报告的发现，主动核查可能推翻它的前置条件、调用方保证、框架处理、路径可达性和已接受的设计取舍；作者披露差异与合同负责人接受差异分别取证。保留有实际触发条件、因果路径和影响支撑的发现，按共同根因与所需纠正机制去重。对决定安全交付的关键事实，构造能推翻它的检查，核对实际代码或用户路径的相应证据，按下文要求处理缺口。测试、构建和静态检查只能证明各自覆盖的层级。任务要求真实宿主、加载器、界面、外部服务或模型调用时，确认是否已有该路径的可观察证据。没有时标明未验证，不把代理指标说成完成。
6. **核对相关文档。** 按下文的方法检查本次变更影响的文档是否正确、是否反映当前决定和实际进度，包括没有修改的相关资料。单独文档评审围绕指定对象及其依据执行同样的判断。
7. **作出评审结论。** 根据实际问题和证据强度，按下文的结论标准与报告要求交回结果。

局部、机械且结果唯一的改动可以轻量执行上述流程。功能、接口、状态或系统结构变更必须完成足以判断整体方向的审查。

## 验收追踪与门槛完整性

要求跨越多个组件、入口或外部边界时，检查每项重要结果和不变量从声明到实现再到证据是否闭合。证据在目标错误发生时应失败，并经过声明成立所依赖的边界。客户端限制不能证明服务端拒绝，内部函数测试不能证明 HTTP、CLI、模型或浏览器入口，分别满足局部限制不能证明组合后的最终预算或输出满足限制。

规格在实现期间变化时，确认受影响的计划、实现合同、测试和证据已经随之更新，未受影响部分没有被无故推翻。候选引用的要求与证据应属于同一当前规格和最终候选，不能混用已经被取代的要求或修改前证据。

检查反例和拒绝路径是否覆盖其他可执行入口、旧状态、重复请求和绕过方式。实现者新增局部测试不能替代既定门槛，也不能通过删除、跳过、放宽或改写门槛获得通过。门槛因真实要求、平台接口或新证据而改变时，确认改变由掌握验收合同的负责人作出，并重新判断受影响的证据。

交付候选的每项重要门槛应有明确状态。未执行、命令报错、结果待定和被跳过都不能算作通过；输出中的零失败也不能证明所有检查已成功执行。候选在取证后发生可能影响结论的变化时，要求补验受影响部分。

需要核对项目验证方式时，按 [项目验证入口](../code-development/references/project-verification.md) 检查已有操作入口、功能与检查的对应关系，以及本次合同涉及的路径。核对实例和版本、真实操作及副作用、清理后的证据留存。复用已有检查，缺少覆盖时在当前授权和只读边界内补取证据，无法补足的决定性缺口按“证据不足”处理。既有方式已足以证明结果时直接采用，完整应用实跑由结论所依赖的路径决定。

## 文档正确性与进度同步

代码评审同时检查本次变更影响的项目文档，包括未修改但仍在说明相关行为的资料。单独文档评审从指定对象及其引用的依据开始，按关键主张追查。用实际影响确定范围，避免扩展成全仓库文档审计。

纯文档审查可以完全不涉及软件或代码变更。明确文档用途、读者、要求和核查时点，核对关键事实、引用与来源、推理前提、已确认决定、相关资料的一致性和进度。核查引用是否支持所述对象、时间和结论，区分事实、判断和待确认内容。按重要主张查阅原始材料或实际成果，代码与工程验证只在技术声明需要时取证。文档无需同时描述下列每类内容，按实际用途选择检查。

先确定文档用途、适用版本和状态，再选择正确性依据：

- **需求与设计：** 对照已确认的目标、约束和决定，检查变更及其影响是否被准确保留。实现不满足已确认目标时，报告偏差，不能用现状实现把目标改成已满足。
- **行为与使用说明：** 对照当前代码、配置、接口和实际入口，核查关键步骤、前提、默认值、限制、示例和结果。沿变更影响查找相关说明与引用，避免只核对被编辑的页面。
- **当前进度与交付状态：** 对照实际成果和对应候选的验证记录，核查已完成、待办、阻塞及下一步是否仍准确。源码实现、测试通过、宿主验收和正式生效分别需要相应证据，未执行、报错、跳过或修改前的结果按其实际状态记录。
- **规划、历史与决策记录：** 按声明的时间、版本和状态判断。保留当时有效的决定与结果，核对已取代内容的状态和替代入口，检查当前资料是否仍把旧决定当作现行规则。

对影响使用、维护或交付判断的关键主张，读取决定性依据，并检查同一事项在相关权威资料和入口中的说法是否一致。文档之间互相引用、作者自述和更新时间只能帮助定位，不能替代事实证据。无法确定哪项需求或决定仍有效时，指出具体矛盾并交回掌握合同的负责人。

优先复用项目已有的生成参考、示例测试和文档检查。必要时在允许范围内验证关键操作或示例，并确认自动检查实际覆盖了什么、是否跳过。构建、样式和链接检查分别证明格式或可达性，示例测试只证明已执行的示例，均不能单独证明整体文档正确或项目已经交付。生成内容不一致时定位其来源及生成流程。

内容错误、遗漏或过时会导致错误操作、后续实现依据失真或交付状态误判时，按实际影响给出可操作问题。缺少决定性依据时先补查，仍无法判断的关键声明按“证据不足”处理，并说明缺什么、影响哪项结论。评审只指出需纠正的内容与依据，修订由有修改权限的负责人完成。普通局部改动不为形式新增文档，纯文字偏好不阻塞交付。

## 兜底路径专项审查

把权威主路径失败、缺失或不确定时改走另一来源并继续产生结果的实现视为兜底。每次评审按以下顺序检查候选新增、扩大或依赖的兜底：

1. 它处理的失败是否由合同要求或真实证据支持。
2. 项目、平台或框架是否已经提供同等机制。
3. 触发条件、结果语义、权威来源和验证方式是否明确。
4. 它是否会隐藏主路径失败、改变结果含义、重复副作用或与其他路径竞争。

缺少判断兜底必要性或正确性的材料时，先补足决定性证据，仍无法判断时给出“证据不足”，不据此通过交付。证据表明兜底没有必要或不满足上述条件时，列为阻塞问题，要求删除、收窄或修复相应机制。合同要求的安全、数据保护和恢复能力继续保留。

评审交回中单列这项结果。没有发现时明确说明。

## 评审结论

- **可合入：** 声明的评审范围内没有阻塞问题，而且证据足以支持该范围的正确性和交付声明。
- **要求修改：** 有事实和影响支撑的问题表明合同没有满足，或者当前候选不能安全合入或阶段交付。
- **证据不足：** 缺少准确评审对象、决定性合同、相关实现或与声明相称的验证证据。没有发现问题不等于证据充分。

纯文档审查通过时使用“可交付”，判断标准与“可合入”相同。证据要求由文档的重要主张决定。

先说明评审结论和实际评审范围，再单列兜底路径审查结果，简述文档检查范围、同步结果及缺少证据的关键声明，随后按严重程度报告可操作问题。没有相关文档需要检查时，说明依据。每项问题写明简短标题、准确文件和最小必要行范围、触发条件或证据、实际影响及需要纠正的机制。跨文件问题说明涉及的调用关系或共同机制。

只报告本次改动引入或暴露、作者可纠正且有事实和影响支撑的问题，把阻塞问题与非阻塞建议分开。纯风格偏好、没有实际影响的推测和无关旧问题不阻塞交付，代码的产生方式不改变标准。没有发现阻塞问题时，仍说明决定结论的证据、残余风险和未验证路径。

候选在评审后发生可能影响结论的变化时，重新确认基线和差异，并复审受影响的范围。不为无关变化重复整个审查。

## 风险资料的选择与读取

代码候选形成变更影响关系后，读取[风险索引](references/risk-index.md)，选择当前机制、后果或证据缺口涉及的专题，完整读取所选专题的方法。纯文档任务从文档用途和关键主张开始，只在相关内容需要时选择技术专题。入口正文与索引承担流程、共同门槛和资料选择，专题承担具体检查动作，案例详情按疑点展开。

先把专题方法落实到当前实现与证据。需要辨明适用条件、反例或取证办法时，再读取有关案例。新旧案例都可使用；机制与条件相近时，优先使用相关代码近期引入或修改且证据完整的案例。分别记录报告日期、相关代码的引入或修改日期、修复日期和证据状态；代码日期未知时保留未知，不用近期报告日期推定代码或模型的新旧。历史案例提供不同条件或更直接证据时继续使用；模型对自己知识的判断与本次关键事实取证分开。

索引帮助定位经验，审查范围由当前合同和改动后果决定。重要不变量无法判断、出现新的入口、消费者、状态或边界时，补读相关专题或沿权威实现调查索引尚未列出的机制。已掌握当前机制、适用条件和证据后，停止读取不再增加信息的重复案例。同一评审中已完整取得且仍有效的资料沿用，候选或条件变化后补查受影响部分。按判断需要扩展读取，不设固定专题数或案例数，不默认读取整个参考目录或研究资料库。

不要求为每一类风险制造测试或意见。只在本次改动触及它且证据会改变合入结论时深入。

## 审查方式和边界

依据技术事实、项目规则和可复现证据判断，作者对正确性的自述不能代替验证。实现者检查自己的修改时，明确这是自查。

需要独立视角时，可以直接调用 `reviewer` 子代理进行只读评审。独立评审者按本 Skill 的标准检查，具体作用范围、只读权限和向上级交回结果的责任由其角色指令与任务合同限定。

用户只要求审查时保持只读，不提供补丁，也不重新决定用户目标或产品方向。已授权开发或修复任务中的自查发现问题时，在原范围内修正并重新验证。

已被可靠自动检查完全覆盖的纯机械问题不重复报告。评审发现可以用技术证据反驳，未经修复、证据反驳或用户明确改变要求的阻塞问题不得被静默忽略。
