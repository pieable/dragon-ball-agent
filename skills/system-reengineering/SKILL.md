# 技术改造

把既有成果转到更合适的实现中，保住仍有效的要求，处理历史依赖，并检验后续工作是否更容易。代码、数据、资产、编辑工程与运行产物都可能是改造对象。

## 承接目标与路线

从当前请求、项目入口、已接受成果和相关失败记录确定本次对象及改造原因。把观察到的困难与原因解释分开；“补丁多”“代偿过多”是调查线索，不能单独证明基础路线错误。已有正确输入或通过的维护入口优先复用，核对其版本与适用范围。

`workflow-state-distiller` 负责整体目标、当前理解、投入取舍和与用户形成方向决定，`workflow-route-mapper` 保存历史路线、证据及其关系。本 Skill 可在决定前提供机制调查与已授权试验，也承接决定后的改造；新证据改变前提时交回修正当前理解与受影响的路线。候选工具调查结合 `deep-research`，实现结合 `code-development` 或相应领域工具，独立核验结合 `code-review`。复用项目规格、路线节点和测试记录，不另建并行的项目管理流程。

明确哪些成果必须保留、哪些变化已获允许、哪些仍未知。旧系统实际行为是证据；既有缺陷和必要兼容行为分别处理。解释、研究或试样请求按其范围完成，不自动进入正式切换。

## 按问题推进

- **现状或补救关系不清**：读[恢复机制与试验](references/understand.md)。从一条相关使用路径追到状态、数据、调用者和外部约束；查明补救保护什么、谁依赖它。理解与小试验交替推进，深入到足以支持当前选择。
- **更换工具、平台或结构**：读[转换与兼容](references/transition.md)。先检查已有成熟能力和真实接口，以有代表性的困难样本验证替代机制；比较局部重构、渐进替换、集中转换的条件及过渡成本。现成工具不足时围绕明确缺口补足。
- **判定成果能否保住、改造能否结束**：读[验证与退出](references/validation.md)。在修改前保存适用基准和独立预期；沿转换、保存重开、集成和真实使用检查，选择相关环节。临时路径有退出条件，必要边界可保留；用一次代表性后续修改检验承诺的维护收益。

按下一步的实质问题读取相关部分，普通小改只处理受影响边界。已有验收明确的局部改造无需全系统恢复、工具选型或完整迁移计划。参考中的方法按条件选择，不作为必须全部执行的检查套件。

## 取证与完成

有源码时优先结合源码、历史和真实运行。只有结论依赖发布包、二进制、未被源码说明的行为或指定运行证据时才考虑 REA 等逆向工具；它们是可选取证能力，不是启动前提。静态推断、运行观察、目标要求和新设计分别保留。

判断改造既看原有成果是否符合保留要求，也看原先的重复同步、特殊处理或修改传播是否减少。新增适配应能说明对应约束及归属；没有新机制或新证据时，不用反复补偿掩盖同一失败。保留已成立部分，把未解决边界交回路线判断。

交付时简明说明实际改变、保留结果、尚存差异与旧路径去向；依据留在所属项目记录。代码写入、可打开、局部运行和完整使用各按实际证据报告。修改后重新核验受影响的证据与依赖，复用仍适用的结果。

维护或扩展本 Skill 时查[方法依据](references/research-basis.md)，不要求每次任务重新阅读研究来源。
