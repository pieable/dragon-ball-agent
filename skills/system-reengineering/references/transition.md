# 转换与兼容

用于从既有实现转向新结构、库、工具、平台或数据表示。

## 先让新机制面对真实困难

结合当前版本与工具实际可用性，检查候选工具的输入输出、表达能力、运行和编辑约束。选取覆盖关键依赖的代表性样本；从现有成果进入候选，完成相关消费路径，再做一次预期的后续修改。演示项目只证明演示覆盖的能力。

数据与资产映射应保持身份和语义：按实际对象核对 ID、单位、坐标空间、默认值、缺失值、顺序、精度、资源引用、参数及状态归属。记录不能表示、需要变换或需要拒绝的内容。接口名称相同也可能有不同语义；选项能设置不表示目标工具会采用。

创作工程还要区分原生可编辑结构与导出运行数据。检查保存、关闭重开、继续修改和重新导出；只留渲染结果可能失去源结构、关键形或关联。将新产物接回完整作品及目标运行时，检查样本之外受影响的关系。往返转换检查所需语义，不默认要求字节相同或所有方向可逆。

## 按风险选择切面

| 方法 | 选择依据 | 需要处理的代价 |
|---|---|---|
| 局部重构 | 基础能力仍适用，主要问题在职责、状态或依赖边界 | 不把边界一致性本身当目的；实际修改负担需减少 |
| 抽象边界后替换 | 可在调用入口隔离实现，以相同契约接入候选 | 新旧接口映射、行为差异、适配层维护 |
| 按功能/数据/用户路径渐进替换 | 能独立验证和切换，业务需持续运行 | 双系统或双格式一致性、迁移期间变更同步、旧路径退出 |
| 准备后集中转换 | 边界可冻结、转换可重复，长期共存更昂贵 | 集中切换风险、完整调用方及数据检查、恢复演练 |

这些方式可组合。平台搬迁与内部重构可拆开，也可能因必要前置改造而先处理局部。选择当前影响面最清楚且能取得有效反馈的切面，不默认渐进永远更安全，也不因新工具更成熟就全量重写。

替换接口时可用 expand–migrate–contract：先增加兼容能力，迁移消费者，确认旧消费者退出后移除旧入口。目标结构的长期边界和临时兼容桥接分开；每个临时机制应有可观察的退出条件，避免永久双维护。

## 改造中的数据和恢复

保留适用的原始样本与当前基准。清楚标识每个阶段谁是数据权威、何时提交转换、哪些读写方仍在使用旧表示。双写不是默认方案；需要双写时明确失败恢复、重试和一致性核对，避免部分成功导致分叉。

回退按实际状态设计：旧代码能否读新数据、切换后新增内容如何处理、外部动作是否已发生。回到旧快照可能丢掉期间的新修改，未经相应授权不能把它作为默认恢复办法。数据不可逆时，考虑兼容读取、前滚修复或经验证的恢复方案；有旧提交只保护源码历史。

选择有后果的失败点验证恢复，例如转换中断、校验失败、保存失败后重试和重开。只保证实际覆盖的故障语义；捕获一个异常不证明断电或并发安全。源代码的小改无需无关的数据库迁移、备份服务或灰度基础设施。

转换过程发现新限制时，把影响到的保留要求、消费者及候选方案一起交回。不要自动牺牲编辑能力、数据语义或已确认体验来让新工具通过。
